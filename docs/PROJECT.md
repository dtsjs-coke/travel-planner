## Architecture Decisions
> 2026-09-09부터 되돌리기 어려운 결정은 [`docs/adr/`](adr/)에 번호를 매겨 개별 파일로 남기고, 여기에는 요약 + 링크만 둔다. 그 이전 결정들은 아래에 인라인으로 그대로 유지한다.

- 백엔드: FastAPI + SQLModel + Alembic, Postgres(Neon)
- 프론트엔드: React + Vite + Tailwind CSS v4 + React Query + dnd-kit + @vis.gl/react-google-maps
- 인증: 개별 계정 없이 공유 비밀번호(passcode) 1개 → 서명된 쿠키 세션
- 호스팅: Vercel(프론트) / Render 무료(백엔드) / Neon 무료(DB) — 각 도구의 목적/선택 이유/실제 등록 과정/트러블슈팅은 [`docs/infra/`](infra/) 참고: [neon.md](infra/neon.md), [render.md](infra/render.md), [vercel.md](infra/vercel.md)
- **Day 자동 생성은 별도 bulk 엔드포인트 대신 `POST /api/trips` 안에서 처리** (2026-09-07 결정). 후보는 (a) `POST /api/trips/{id}/days/bulk` 신설, (b) 프론트에서 단건 API를 날짜 수만큼 반복 호출, (c) 트립 생성이 Day까지 같이 만들기. **(c) 선택** — 이유: ① 프론트가 왕복 1회로 끝나고 부분 실패(트립은 생겼는데 Day는 일부만) 상태가 원천적으로 없음(단일 트랜잭션), ② (b)는 N번 호출 중 실패 시 프론트가 보상 로직을 떠안아야 함, ③ (a)는 지금 호출할 곳이 트립 생성 한 군데뿐이라 엔드포인트만 늘어남. 대신 날짜 범위 → Day 변환 규칙 자체는 `app/services/trip_days.py`로 빼놨으므로, 나중에 (a)가 실제로 필요해지면(예: 기간 PATCH 동기화) 라우터만 추가하면 됨. 안전장치로 여행 1건의 최대 기간을 90일(`MAX_TRIP_DAYS`)로 제한 — 연도 오타 하나로 수천 행이 생겨 무료 티어 DB를 먹는 사고 방지.
- **날짜 범위 검증은 스키마가 아니라 `app/services/trip_days.py`의 순수 함수 `validate_date_range(start, end)`가 단일 소스** (2026-09-07 결정). `POST`는 `TripCreate`의 `model_validator`가, `PATCH`는 `update_trip` 라우터가 각각 이 함수를 호출한다. PATCH는 부분 업데이트라 요청에 한쪽 날짜만 올 수 있어 **DB의 기존 값과 병합한 뒤**에야 최종 기간이 정해지므로, pydantic 스키마(`TripUpdate`)만으로는 검증이 불가능하다. 두 날짜 중 하나라도 없으면 검증을 건너뛰는 정책도 두 경로에서 동일(= Day 자동 생성 조건과 같은 기준).
- **모바일 일정 화면은 "전체 Day 연속 스크롤 + 상단 고정 지도", 데이터는 Day별 병렬 조회(`useQueries`)로 통일** (2026-09-08 결정). 데스크톱은 기존(Day 탭 + 리스트/지도 2단)을 그대로 두고, 모바일만 Day1~DayN 일정을 한 화면에 이어붙여 세로 스크롤하며 상단 고정 지도의 핀이 "지금 보이는 Day"로 자동 전환되게 한다(트리플 앱 방식).
  - **데이터 로딩**: 후보는 (a) 프론트에서 Day마다 `listItems(dayId)`를 React Query `useQueries`로 병렬 호출, (b) `GET /api/trips/{id}/items` 같은 트립 단위 집계 엔드포인트 신설(또는 `GET /api/trips/{id}` 응답의 `days`에 `items` 중첩). **(a) 선택** — 이유: ① 기존 캐시 키 `['days', dayId, 'items']`를 그대로 쓰므로 `AddItemModal`의 `invalidateQueries`, `reorderMutation`의 낙관적 업데이트 등 이미 검증된 코드를 한 줄도 안 건드려도 됨(회귀 위험이 가장 큰 부분이 드래그 정렬인데 그걸 그대로 보존), ② API 계약 변경이 없어 백엔드/프론트 배포 순서 의존성이 사라짐, ③ 요청 수가 Day 수만큼 늘지만 프론트·백엔드가 Vercel `/api/*` rewrite로 same-origin HTTP/2라 멀티플렉싱되고, 실사용 기간은 며칠~2주(=3~14 요청) 수준이며 최악의 경우도 `MAX_TRIP_DAYS`(90)로 이미 상한이 걸려 있음. (b)의 이점(왕복 1회)은 이 규모에서 체감되지 않는 반면 캐시 키 구조 이전 비용은 확실하게 발생한다.
  - **양쪽 화면이 같은 캐시를 공유**: 데스크톱/모바일 모두 `useTripItems(days)` 훅 하나만 쓰고, 이 훅이 내부적으로 `useQueries`를 돌린다. 데스크톱 탭 전환은 이미 받아둔 캐시를 읽으므로 추가 요청이 없어진다(기존보다 오히려 빨라짐). 나중에 (b)가 필요해지면 **이 훅 내부만 갈아끼우면 되고 화면 코드는 그대로**다 — 그래서 훅 경계를 지금 만들어 둔다.
  - **모바일 첫 렌더 레이아웃 시프트 방지**: Day별 응답이 제각각 도착하면 스크롤 컨테이너 높이가 계속 바뀌어 IntersectionObserver 판정과 사용자의 스크롤 위치가 흔들린다. 그래서 모바일 리스트는 **모든 Day 쿼리가 끝난 뒤 한 번에** 렌더한다(`isLoading = results.some(r => r.isPending)`). 데스크톱은 활성 Day만 보므로 이 게이트를 적용하지 않는다.
  - **데스크톱/모바일 분기는 CSS가 아니라 JS 미디어쿼리(`useIsDesktop`, `768px`)로 한다** — Tailwind `hidden md:block`으로 양쪽 트리를 동시에 렌더하면 `<MapView>`(Google Maps) 인스턴스가 2개 마운트되어 **Map load가 2배로 과금**된다. 지도 인스턴스는 항상 1개만 마운트되도록 컴포넌트 자체를 택일 렌더한다.
  - **"현재 보이는 Day" 추적은 IntersectionObserver 스크롤 스파이**로 하고, 판정선은 **상단 고정 블록(지도+Day 칩)의 실제 높이를 `ResizeObserver`로 측정해서** 정한다(`rootMargin: '-<측정높이+16>px 0px -30% 0px'`). vh 단위로 고정하지 않는 이유: 모바일 주소창 유무에 따라 `vh`(large viewport)와 IntersectionObserver root(실제 뷰포트)가 어긋나고, Day 칩 줄 높이도 폰트/기기마다 달라 매직넘버가 쉽게 깨진다. 여러 섹션이 동시에 밴드에 걸리면 `boundingClientRect.top`이 가장 작은 섹션(= 밴드 상단을 점유한, 지도 바로 밑에 있는 Day)을 활성으로 본다. 가상 스크롤링은 도입하지 않는다(트립당 아이템 수백 개 미만 전제).
- **기간 PATCH 시 Day 동기화는 "추가만 하고 삭제는 사용자 확인 후 프론트가"** (2026-09-09 결정, 상세는 [ADR-0001](adr/0001-patch-trip-date-day-sync.md)). `PATCH /api/trips/{id}`가 날짜 필드를 포함하고 두 날짜가 다 있으면, 새 범위에 없는 Day만 추가하고(`app/services/trip_days.py`의 `diff_days_for_range()` — 기존 `build_days_for_range()` 재사용) **범위 밖 Day는 절대 자동 삭제하지 않는다**(Day → ItineraryItem이 CASCADE라 일정이 통째로 날아감). 대신 응답 `TripUpdateResult`에 `out_of_range_days`(`DayRead` + `item_count`)와 `added_day_ids`를 실어 프론트가 경고 모달을 띄우고, 사용자가 확인하면 **기존 `DELETE /api/days/{id}`**로 개별 삭제한다(새 엔드포인트 0개). 후보 (b) `force=true` 한 방 처리는 파괴적 동작을 일반 수정 요청에 묶어 클라이언트 실수 한 줄이 곧 데이터 손실이 되고 경고하려면 어차피 사전 조회가 필요해서 기각, (c) 그냥 남겨두고 UI 표시만은 정리 수단이 없어 기각(단 (a)에서 사용자가 삭제를 거절하면 결과가 (c)와 같음). 응답은 `TripDetailRead`의 상위집합이라 기존 프론트 코드와 호환된다. 이름만 바꾸는 PATCH는 Day를 건드리지 않고(요청에 날짜 키가 있을 때만 동기화), 범위 밖 Day를 안 지우는 대신 트립당 총 Day를 `MAX_TRIP_TOTAL_DAYS`(=180)로 제한해 기간 이동 PATCH 반복 시 무한 누적을 막는다.
- **`Day(trip_id, date)`에 DB 유니크 제약을 걸고, 위반은 409로 변환하되 자동 재시도는 하지 않는다** (2026-09-09 결정, 상세는 [ADR-0002](adr/0002-day-unique-constraint-and-conflict-handling.md)). "한 여행에 같은 날짜 Day는 하나"는 도메인 불변식인데 애플리케이션 레벨 중복 체크(`diff_days_for_range`)는 자기 트랜잭션이 읽은 스냅샷만 보므로 동시 PATCH를 막지 못한다. 라우터가 `async def`가 아니라 `def`라 FastAPI가 스레드풀에서 병렬 실행하므로 Render 인스턴스가 1개여도 실제로 동시 실행된다. 그래서 `models.py`의 `__table_args__`에 `uq_day_trip_id_date`를 두고 Alembic(`73a697fa5fee`)으로 적용한다 — 이 마이그레이션은 기존 중복이 있으면 어떤 행인지 찍고 **일부러 실패**한다(자동 삭제 시 CASCADE로 일정이 날아가므로 사람이 판단). 충돌 시 `update_trip`은 트랜잭션 전체를 롤백하고 409를 주며 **자동 재시도하지 않는다**: 상대 요청이 기간까지 바꿨을 수 있어 재시도가 곧 상대 변경을 덮어쓰는 last-write-wins가 되기 때문(ADR-0001의 "파괴적/모호한 판단은 사람이"와 같은 기준). `create_day`/`update_day`도 409(유니크 제약 도입으로 같은 날짜 수동 추가가 201→409로 바뀜). `create_trip`은 새 `trip.id`라 충돌이 구조적으로 불가능해 처리하지 않는다. **`MAX_TRIP_TOTAL_DAYS`(180)의 동시 우회는 락 대신 알려진 한계로 문서화**했다 — 유니크 제약 때문에 같은 방향 동시 확장은 이미 409로 걸리고, 서로소 방향일 때만 최대 270일까지 넘친 뒤 다음 요청부터 기존 422가 막아 자가 수복되며, `SELECT ... FOR UPDATE`는 SQLite에서 무시돼 로컬 검증이 불가능하기 때문(검증할 수 없는 락 < 문서화된 한계).
- **여행 체크리스트는 `Trip` 직속 새 테이블(`checklist_item`)로 두고, 정렬 컬럼 없이 생성 순서(`id`)로만 조회한다** (2026-09-09 결정, 상세는 [ADR-0003](adr/0003-trip-checklist-model.md)). "여권 챙기기" 같은 여행 전체 준비물이라 `Day`에 매달면 기간 PATCH로 Day가 범위 밖이 되거나 삭제될 때(ADR-0001) 준비물이 함께 사라진다. **순서 변경(드래그/이동 버튼)은 이번 스코프에서 제외** — `ItineraryItem`의 dnd-kit 정렬은 "하루 동선의 방문 순서"라 순서 자체가 데이터의 의미지만 준비물 목록은 그렇지 않고, 모바일에서 체크박스 탭과 드래그 제스처가 경합하는 비용까지 든다. 나중에 필요해지면 `position int DEFAULT 0` 컬럼 + `ORDER BY position, id`면 되고 **기존 행은 `id` 보조 정렬 덕에 현재 순서가 그대로 유지돼 백필이 불필요**하므로, 지금 안 넣는 쪽의 되돌리기 비용이 더 싸다. 체크 토글은 전용 엔드포인트가 아니라 일반 `PATCH /api/checklist/{id}`로 처리한다(`POST .../toggle`은 현재 상태를 모른 채 뒤집어서 **멱등하지 않고**, 재시도/더블탭이 상태 반전 2회가 된다). 안전장치로 트립당 항목 100개(`MAX_TRIP_CHECKLIST_ITEMS`) + 텍스트 200자 상한을 둔다 — Day 상한과 달리 자동 일괄 생성 사고를 막는 게 아니라 클라이언트 루프 버그/대용량 붙여넣기로부터 무료 티어 DB를 지키는 가드레일이며, 개수와 길이는 세트로만 의미가 있다.
- **일정의 Day 이동은 `PATCH /api/items/{id}` 확장이 아니라 전용 엔드포인트 `POST /api/items/{id}/move`, 삽입 위치는 항상 목적지 맨 뒤** (2026-09-10 결정, 상세는 [ADR-0004](adr/0004-move-item-between-days.md)). `update_item`은 `model_dump(exclude_unset=True)`를 `setattr`로 도는 일반 루프인데 여기에 `day_id`를 넣으면 "이 필드만 position 재계산 + 원본 Day 재번호 + 트립 검증을 유발"하는 특수 분기가 생기고, 실수로 보내면 데이터가 눈에 안 보이는 곳으로 가는 조작이 일반 편집 요청에 묻어간다(ADR-0001의 `force=true` 기각과 같은 기준). 기존 `reorder`가 이미 "동사형 POST" 패턴이라 표면도 일관된다. **삽입 위치(`target_position`)는 받지 않는다** — 받으면 목적지 Day 전체를 밀어내는 재배치 로직이 `reorder`와 중복되고, 정작 그 값을 채울 UI가 데스크톱(Day 탭이라 목적지 목록이 화면에 없음)·모바일 어디에도 없다. 필요해지면 바디 필드 추가로 하위호환되게 넣을 수 있다. **다른 트립의 Day로 이동은 422로 거부**(존재하지 않는 404와 구분) — 막지 않으면 A 여행 일정이 B 여행에 섞이는데, 프론트 캐시 키가 트립 단위라 사용자 눈에 띄지도 않는 조용한 오염이 된다. 같은 Day로의 이동은 no-op 200(멱등 — 여기서 맨 뒤로 붙이면 재시도/더블탭이 같은 Day 순서를 몰래 바꾼다, ADR-0003의 토글 엔드포인트 기각과 같은 기준). **스키마 변경 없음**(기존 `day_id`/`position` 재사용). 구현상 함정 하나: `item.day_id`를 먼저 바꾼 뒤 최대 position을 SELECT하면 **autoflush가 그 변경을 먼저 밀어넣어 자기 자신을 최댓값으로 집어삼킨다**(빈 Day로 옮겼는데 position이 0이 아니라 "옛 position + 1") — 읽기를 전부 끝낸 뒤에 수정해야 한다.
- **모바일에서만 Day 간 드래그 앤 드롭을 지원하고, `DndContext`는 화면 컴포넌트가 소유한다** (2026-09-10 결정, 상세는 [ADR-0005](adr/0005-mobile-cross-day-drag-and-drop.md)). ADR-0004가 기각했던 "Day 간 드래그"를 **모바일에 한해** 도입한다 — 연속 스크롤 뷰(2026-09-08 결정) 덕에 목적지 Day 섹션이 실제로 화면에 나타나기 때문이며, 데스크톱은 Day 탭이라 그 조건이 없어 그대로 둔다(ADR-0004의 API 결정은 뒤집히지 않음). 전제조건으로 `DndContext`/센서/`onDragEnd`를 `ItineraryList`에서 **상위 뷰로 올렸다**: 모바일은 Day1~DayN 전체를 감싸는 DndContext 1개, 데스크톱은 활성 Day 하나만 감싸는 DndContext 1개(= 변경 전과 트리 모양 동일 → 회귀 없음). `SortableContext`는 Day별로 유지. 드롭 결과 해석은 `lib/dndDrop.ts`의 순수 함수 `resolveDrop()` **단일 소스**(정렬 규칙이 두 벌로 갈라지는 걸 막고, 브라우저 없이 검증 가능). **빈 Day에만** 컨테이너 droppable(`day:<id>`)을 등록해 "드롭 대상이 없어 영원히 옮겨올 수 없는 Day"를 없애고, 항목이 있는 Day는 항목 droppable만으로 충분하므로 경합이 없어 **커스텀 collision 캐스케이드 없이 기존 `closestCenter`를 유지**한다. 다른 Day로 드롭하면 그 Day **맨 뒤**에 붙는다(기존 `move` API 그대로, `target_position` 추가하지 않음) — 정확한 위치 삽입은 드래그 중 목적지 항목들을 비켜서게 하는 로컬 상태 사본이 필요해지고 그게 이미 잘 도는 같은-Day 정렬(M3에서 가장 손보기 어려웠던 부분)의 회귀 위험을 사기 때문. 그래서 삽입선 대신 **목적지 Day 섹션 전체를 하이라이트**해 보여주는 것과 실제 동작을 일치시킨다. 자동 스크롤은 dnd-kit `DndContext`의 내장 auto-scroll(기본 활성)을 쓰고 직접 구현하지 않는다. `TouchSensor`(150ms/5px)와 핸들 전용 리스너는 M3에서 검증된 값이라 이번 구조 변경과 함께 건드리지 않는다. `MoveItemControl`(하단 시트)은 **유지** — 먼 Day로의 드래그는 자동 스크롤이 붙어도 비싸고, 드래그는 실패 가능한 제스처라 단독 수단이 될 수 없다.
- **지출 결제자는 참가자 테이블 없이 `ItineraryItem.paid_by` 문자열 컬럼 하나, 정산은 저장하지 않고 매번 계산** (2026-09-10 결정, 상세는 [ADR-0006](adr/0006-expense-payer-and-settlement.md) — **이 중 참가자 이름의 저장/변경 방식은 2026-09-11 ADR-0007이 대체, 아래 항목 참고**). 이 앱은 개별 계정이 없고 **희경/재승 두 사람이 공유 비밀번호로 쓰며 참가자를 늘릴 계획이 없다**(사용자 확인). 그래서 `Participant` 테이블·CRUD·관리 화면을 만들지 않고 `app/services/settlement.py`의 상수 `PARTICIPANTS = ("희경", "재승")`를 유일한 소스로 두고, 결제자는 nullable 문자열 컬럼 `paid_by`(NULL = 미지정)로 표현한다. `Settings`(환경변수)로 빼지 않은 이유: 이름은 배포 환경에 따라 달라지는 값이 아니라 DB에 그대로 저장되는 데이터라, env로 만들면 로컬/운영이 어긋나 **한쪽에서만 422**가 나고, 이름을 바꾸면 어차피 기존 행 `UPDATE`가 필요해 "env 한 줄" 이점이 성립하지 않는다. `paid_by_index: int`(0/1)도 기각 — 상수 순서를 바꾸면 기존 데이터 의미가 조용히 뒤집힌다. DB CHECK 제약은 걸지 않는다(이름 변경이 마이그레이션 사안이 되는데, 이건 도메인 불변식이 아니라 "지금 이 앱을 쓰는 사람 목록"이다 — Day 유니크 제약(ADR-0002)과 성격이 다르다). **명시적 `null` 처리는 `title`/`text`와 반대로 허용**한다: 컬럼이 nullable이고 "결제자를 미지정으로 되돌리기"가 정상 조작이라 `{"paid_by": null}`이 200이며, 빈 문자열도 None으로 정규화한다(프론트 `<select>`의 "미지정" 옵션 value가 보통 `""`). **정산 계산**은 2명 고정이라 최소 송금 알고리즘 없이 "총액의 절반을 기준으로 덜 낸 사람이 더 낸 사람에게 차액의 절반"이며(참가자가 3명 이상이면 조용히 틀린 답을 주는 대신 `transfer: null`), 결과를 저장하지 않고 매 요청 계산한다(파생값이라 저장하면 원본과 어긋난 상태를 관리해야 함). **결제자 미지정 지출은 정산에서 제외**하고 `unassigned_*`로 보고만 한다(누가 냈는지 추측하지 않음 — ADR-0001의 "모호한 판단은 사람이"와 같은 기준). **통화가 섞이면 환율 변환 없이** 기준 통화(`Trip.currency`) 항목만 합산하고 나머지는 `excluded_currencies`/`has_mixed_currency`로 경고한다(`cost_currency`가 비어 있으면 기준 통화로 간주 — 지금까지 이 필드를 채우는 UI가 없어 전부 NULL이라 "통화 미상" 취급 시 모든 지출이 빠진다). 곁다리로 `cost_amount` 음수/NaN을 막았고, 그 과정에서 드러난 **"NaN이 담긴 요청은 422 응답 직렬화 중에 터져 500이 되던"** 기존 경로도 `app/main.py`의 `RequestValidationError` 핸들러로 막았다.
- **참가자 이름은 런타임 설정(`app_settings` 싱글턴 테이블)이고, `ItineraryItem.paid_by`에는 표시 이름이 아니라 고정 슬롯 키를 저장한다** (2026-09-11 결정, 상세는 [ADR-0007](adr/0007-runtime-participant-names.md) — **ADR-0006의 결정 1·2를 대체**). 사용자가 "닉네임을 마스터 환경설정에서 바꿀 수 있게"를 요청하면서 ADR-0006의 전제("이름 변경 = 드문 배포 이벤트")가 사라졌다. 검토한 두 안: **(A)** `paid_by`에 표시 이름을 계속 저장하고 이름 변경 시 매칭되는 지출 행을 일괄 `UPDATE`, **(B)** `paid_by`에 슬롯 키(`participant_1`/`participant_2`)를 저장하고 이름은 설정에서 조회. **(B) 채택** — 결정적 이유는 실패 모드의 비대칭이다. (A)에서 이름 변경은 상한 없는 데이터 재작성이고 재작성을 놓친 행은 `compute_settlement`에서 "모르는 이름 → 미지정"으로 빠져 **에러 없이 금액이 정산에서 사라진다**. 또 한쪽을 상대 이름으로 바꾸면 두 사람 지출이 **복구 불가능하게 병합**된다 — 이름 변경이 아무나 누르는 버튼이 된 이상 이론적 시나리오가 아니다. (B)에서는 이름 변경이 정의상 지출 데이터를 건드릴 수 없고 설정 1행만 바뀐다. 부수적으로 `paid_by` pydantic 검증이 DB를 모르는 **정적 상수 비교**로 남는다((A)였다면 validator가 DB를 읽어야 해서 검증이 라우터로 흩어진다). 감수하는 것: DB 콘솔에서 `paid_by='participant_1'`이 바로 안 읽히고(`app_settings` 한 행 함께 조회 필요), 프론트가 키→이름 변환을 한 번 해야 한다. ADR-0006이 기각했던 `paid_by_index: int`와 다른 점은 저장값이 **순서 기반 숫자가 아니라 이름 붙은 키 문자열**이라는 것(배열을 재정렬해도 `participant_1`은 계속 `participant_1`). 설정은 `.env`/`Settings`가 아니라 **DB**에 둔다(환경변수는 재배포해야 바뀌고 배포 환경마다 달라지는 값 — 이번 요구와 정반대). 싱글턴은 `id=1` 고정 PK로 강제하고, **조회는 행을 만들지 않는다**(읽기 요청이 조용히 쓰기 트랜잭션이 되는 걸 막음). 이름 검증은 빈 값/공백/명시적 null/모르는 키/20자 초과/두 이름 중복을 전부 422로 거부하며, `paid_by`(명시적 null = "미지정으로 되돌리기" = 200)와 **반대 방향**인 이유는 "컬럼이 nullable인가, null이 의미 있는 상태인가"라는 같은 기준을 적용한 결과다. 정산 응답에는 이름을 싣고 일정 응답에는 키만 싣는데, 기준은 **"이름을 오래 사는 캐시에 복사하지 않는다"** — 정산은 매번 계산하는 파생 읽기 모델이지만 일정은 저장된 엔티티라 이름을 복사하면 이름 변경 후 낡은 값이 캐시에 남는다.
- **ICS 내보내기는 "일정 1건 = VEVENT 1개", 시각은 floating time, UID는 DB id 고정, 라이브러리 없이 직접 생성** (2026-09-11 결정, 상세는 [ADR-0008](adr/0008-ics-calendar-export.md)). 조사해보니 `start_time`/`end_time` 컬럼은 M1부터 있지만 **값을 입력하는 UI가 프론트 어디에도 없어서 실제 데이터는 전부 NULL**이고(`cost_amount`가 ADR-0006 직전까지 그랬던 것과 같은 상태), `Trip`에 시간대 필드도 없다. 그래서 **시간 없는 일정은 종일 이벤트**(`DTSTART;VALUE=DATE` + DTEND는 **다음 날** — 비포함 경계라 같은 날짜면 길이 0이 된다), 시간이 있으면 그 시각 그대로(종료 시각이 없거나 시작보다 이르면 +1시간)로 간다. **"09:00부터 1시간씩 자동 배정"은 기각** — 사용자가 입력한 적 없는 값을 지어내는 것이고 나중에 진짜 시각과 구분할 수 없게 된다(ADR-0001/0006의 "모호한 판단은 사람이"와 같은 기준). **"Day 하나를 이벤트 하나로 묶고 설명에 일정 나열"도 기각** — VEVENT는 LOCATION을 하나만 가지므로 애써 저장한 주소/좌표(M4~M5의 핵심)가 통째로 날아가고, 캘린더에서 주소를 눌러 길찾기로 넘어가는 게 내보내기의 실질적 가치다. 대신 종일 이벤트끼리는 캘린더가 표시 순서를 보장하지 않아 `position`(이 앱에서 순서는 데이터의 의미 자체)이 사라지므로, **제목 앞에 그날의 순번을 붙인다**(`"1. 성산일출봉"`, Day마다 1부터). 시각은 `Z`도 `TZID`도 없는 **floating time** — 해외 여행 앱인데 시간대를 저장하지 않으므로 `Asia/Seoul` 하드코딩은 도쿄에서 조용히 1시간 어긋나고, floating은 "읽는 쪽 로컬 시간대에서 적힌 그대로"라 의미가 가장 가까우며 결과도 같거나 낫다(VTIMEZONE도 불필요). UID는 `item-{item_id}@travel-planner-dtsjs.vercel.app` 고정이라 **다시 내보내 가져와도 중복이 아니라 갱신**이다(`SEQUENCE`는 리비전 카운터가 없어 생략 — `updated_at` epoch 초는 INTEGER 상한을 2038년에 넘겨 조용히 깨진다). `icalendar` 라이브러리는 **도입하지 않는다**(의존성 최소주의) — 어려운 건 문법이 아니라 CRLF/TEXT 이스케이프(`\` `;` `,` 줄바꿈, 백슬래시 먼저)/75옥텟 폴딩 세 가지뿐이고 전부 순수 함수로 검증 가능하다. **폴딩은 넣었다** — 한글은 UTF-8에서 3옥텟이라 주소/메모 25자만 넘어도 초과해서 이 앱에선 예외가 아니라 기본 상태다(옥텟으로 세되 멀티바이트 문자 중간에서 자르지 않는 것이 핵심). `GEO`(float 쌍)와 `URL`(URI)은 TEXT가 아니라 **이스케이프하면 안 된다**. 프론트는 blob이 아니라 **평범한 `<a href>` 링크**로 받는다(운영은 Vercel rewrite로 same-origin, 로컬은 크로스 오리진이지만 링크 클릭이 최상위 내비게이션이라 `SameSite=Lax` 쿠키가 실림 / 모바일에서 blob 다운로드가 OS 캘린더로 안 넘어가는 경우가 있음). 빈 여행은 에러가 아니라 VEVENT 0개짜리 달력(RFC 5545 §3.6에서 살짝 벗어나지만 의도적으로 사용성을 택함). **앱에서 지운 일정은 캘린더에서 안 지워진다**(METHOD:CANCEL은 내보내기 이력 테이블이 필요해 기각)는 알려진 한계다.

## Environment Variables

### backend/.env
- `DATABASE_URL` — 로컬 개발은 SQLite(`sqlite:///./dev.db`), 배포는 Neon Postgres 연결 문자열
- `SECRET_KEY` — 세션 쿠키 서명용 랜덤 문자열
- `SHARED_PASSCODE` — 공유 접속 비밀번호
- `GOOGLE_PLACES_SERVER_KEY` — Places API 서버 프록시용 키 (절대 프론트엔드에 노출 금지)
- `CORS_ORIGINS` — 허용할 프론트엔드 origin (콤마 구분)

### frontend/.env
- `VITE_API_BASE_URL` — 백엔드 API 기본 URL. **로컬**: `http://localhost:8000`. **Vercel(프로덕션)**: 빈 문자열 — `frontend/vercel.json`의 `/api/*` rewrite가 Render로 프록시해주므로 상대경로로 호출해야 same-origin이 되어 크로스 도메인 쿠키 차단 문제(삼성 인터넷 등)를 피할 수 있음.

- `VITE_GOOGLE_MAPS_MAP_ID` — Advanced Marker 렌더링에 필요한 Map ID (Raster 타입). 비밀값 아님 — 브라우저 번들에 그대로 노출되는 공개 식별자.

## Gotchas (발생했던 문제들, 재발 방지용)
- Google Maps 브라우저 키의 HTTP 리퍼러 제한에서 **와일드카드 패턴이 기대대로 안 먹힐 수 있음** (`localhost:*/*`, `*localhost:*/*` 둘 다 실패 경험). 새 도메인 추가할 때 와일드카드보다 **정확한 전체 URL**(`http://localhost:5173/*`, 배포 후엔 `https://실제도메인/*`)을 우선 시도할 것.
- `.env` 파일은 서버/dev 프로세스 **시작 시점에만** 읽힘 — 실행 중에 값 추가/수정했다면 반드시 재시작해야 반영됨 (백엔드 uvicorn, 프론트 vite 둘 다 해당).
- **`ENVIRONMENT=production`을 Render에 빼먹으면 로그인이 무한 실패한 것처럼 보임**: `app/auth.py`가 `settings.environment == "production"`일 때만 세션 쿠키를 `Secure=True, SameSite=None`으로 발급한다. 이 값이 안 맞으면 `SameSite=Lax`로 발급되는데, 프론트(vercel.app)와 백엔드(onrender.com)가 서로 다른 도메인이라 브라우저가 크로스 도메인 요청에 Lax 쿠키를 아예 안 실어보낸다 → `/api/auth/login`은 200 성공해도 `/api/auth/me`가 계속 401 → 로그인이 안 되는 것처럼 보임. **원인**이었던 건 아니고 사전에 값 세팅해서 예방됐지만, 재발 방지용으로 기록.
- **Vercel Deployment Protection(구 Vercel Authentication)을 꺼야 함**: 기본값이 켜져있으면 방문자가 사이트 접속 시 Vercel 계정 로그인을 강제로 요구받는다(우리 앱은 공유 비밀번호 방식이라 방문자가 Vercel 계정을 가질 필요가 없음). Project Settings → Deployment Protection에서 off로 변경 필요.
- **Vite SPA를 Vercel에 올릴 때 `vercel.json` rewrite 필수**: 없으면 `/trips/2`처럼 클라이언트 라우팅 경로를 새로고침할 때 Vercel이 실제 파일을 못 찾아 404를 반환한다(실기기 테스트에서 PC/폰 둘 다 재현). `frontend/vercel.json`에 모든 경로를 `/index.html`로 rewrite하도록 추가해서 해결.
- **모바일에서 `AddItemModal`(구글 검색 탭)에 검색창이 화면 밖으로 밀리고 한글 입력이 깨짐(ㅓㅏㄴㄷㅗㅇ)**: 1차 수정(내부 컨테이너 `overflow-hidden`→`overflow-y-auto`)만으로는 부족했음 — 바깥 배경 레이어(`fixed inset-0 ... items-center`)에 스크롤이 없고 세로 중앙 정렬이라, 키보드가 올라와 보이는 영역이 줄면 모달 자체가 화면 밖으로 밀려도 스크롤해서 볼 방법이 없었음. 바깥 레이어도 `overflow-y-auto` + 모바일에서 `items-start`(위쪽 정렬, `sm:` 이상에서만 중앙 정렬)로 변경해서 **해결 확인 완료** (실기기 재테스트 통과). 레이아웃 흔들림이 안드로이드 한글 IME 조합을 끊어서 자모가 안 합쳐지고 깨진 채로 보였던 것으로 추정 — "직접 입력" 탭(지도 없어서 내용이 짧음)은 처음부터 정상이었던 게 이 가설을 뒷받침함.

## Known Issues (미해결, 낮은 우선순위)
- **삼성 인터넷 브라우저에서 로그인 후 여행 목록이 안 보이고 추가 버튼도 안 먹음** (크롬, 카카오톡 인앱 브라우저는 정상). 추정 원인: 프론트(`vercel.app`)·백엔드(`onrender.com`)가 다른 도메인이라 세션 쿠키가 크로스 사이트 쿠키로 보였고, 삼성 인터넷의 기본 트래킹 방지 기능이 차단하는 것으로 의심. **시도한 해결책이 효과 없었음**: `frontend/vercel.json`에 `/api/*` → Render 프록시 rewrite 추가 + `VITE_API_BASE_URL`을 빈 문자열로(같은 도메인화 시도) 했지만 재현됨. 정확한 원인 미확정. 사용자 판단으로 우선순위 낮춰 보류 — 크롬으로 정상 사용 가능하니 당장 막힌 건 아님. 나중에 재조사할 경우: 삼성 인터넷 개발자 옵션 활성화 후 실제 네트워크 요청이 프록시 경로(`vercel.app/api/...`)로 가는지, Set-Cookie 헤더가 응답에 실제로 붙어오는지부터 확인할 것.
