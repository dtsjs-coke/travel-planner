# ADR-0007: 참가자 이름을 런타임 설정으로 — `paid_by`에 표시 이름 대신 슬롯 키 저장

- **날짜**: 2026-09-11
- **상태**: Accepted
- **작성**: senior-dev (오케스트레이터 위임)
- **관계**: [ADR-0006](0006-expense-payer-and-settlement.md)의 결정 1·2(참가자 이름을 코드 상수로 두고
  `paid_by`에 표시 이름 문자열을 저장)를 **대체한다**. ADR-0006의 나머지 결정(정산 계산 방식, 명시적 null
  처리, 통화 혼합, 엔드포인트 형태)은 그대로 유효하다.

## 배경

ADR-0006은 하루 전(2026-09-10) 결정됐고, 그 핵심 전제는 이것이었다:

> 참가자는 "희경"/"재승" 2명 고정이며 **참가자 관리 기능은 만들지 않는다**. 두 이름은
> `app/services/settlement.py`의 상수 `PARTICIPANTS`가 유일한 소스이고, 이름을 바꾸려면
> 상수 수정 + `UPDATE itinerary_item` + 프론트 선택지 수정이 **한 번의 배포**로 묶인다.

그 전제 위에서는 "이름 문자열을 그대로 저장"이 합리적이었다. 이름 변경이 **드물고, 사람이 손으로
하는, 배포 이벤트**였기 때문이다. 그리고 같은 이유로 `paid_by_index: int`(0/1)를 기각했다 —
"상수 배열의 순서를 바꾸면 기존 데이터 의미가 조용히 뒤집힌다"는 우려였다.

그런데 사용자가 곧바로 다음을 요청했다(2026-09-11):

> 1. "희경, 재승 닉네임은 **마스터 환경설정에서 변경 가능**하게 해주고"
> 2. "마스터 환경설정은 **웹 메인페이지에 보이게** 해줘"

이로써 **"이름 변경 = 드문 배포 이벤트"라는 전제가 사라졌다.** 이름 변경은 로그인한 사람이면
언제든 누를 수 있는 **평범한 런타임 기능**이 된다. 전제가 바뀌었으니 그 위에 세운 결정도 다시
검토해야 한다. 참가자 수는 여전히 **정확히 2명 고정**이다(추가/삭제는 범위 밖 — 사용자 확인).

### 지금 이 결정이 공짜인 이유 (중요)

`paid_by` 컬럼은 **어디에도 데이터가 없다**. 마이그레이션 `093074f849bc`는 운영 Neon에 아직
적용되지 않았고, 로컬 `dev.db`에는 적용됐지만 값이 전부 NULL이다(일정 3건, 확인함). 비용/결제자를
입력하는 UI도 아직 없다. 즉 **저장 표현을 바꾸는 데 변환할 행이 0건**이다. 이 비용은 앞으로
올라가기만 한다.

## 결정

### 1. 참가자 이름은 DB 설정(`AppSettings` 싱글턴 테이블)에 둔다 — `Settings`(환경변수)가 아니다

```python
# app/models.py
class AppSettings(SQLModel, table=True):
    __tablename__ = "app_settings"
    id: int | None = Field(default=None, primary_key=True)   # 항상 1
    participant_1_name: str = "희경"
    participant_2_name: str = "재승"
    updated_at: dt.datetime = ...
```

`app/config.py`의 `Settings`(pydantic-settings, `.env`)와 **다른 것**임을 분명히 한다. 그쪽은
DB URL·시크릿·CORS처럼 **배포 환경마다 달라야 하고 재배포해야 바뀌는** 값이다. 참가자 이름은
정반대로 **두 환경이 같아야 하고 화면에서 실시간으로 바뀌어야** 하므로 `.env`에 둘 수 없다
(ADR-0006이 env를 기각했던 근거는 지금도 유효하다 — 로컬/운영이 어긋나면 한쪽에서만 422).

- **싱글턴 행(`id=1` 고정)**: "설정은 하나뿐"을 코드 관례가 아니라 기본키로 강제한다. 조건 없는
  `SELECT ... LIMIT 1`을 쓰면 언젠가 두 번째 행이 생겨도 아무도 눈치채지 못한다. 두 요청이 동시에
  첫 행을 만들려 하면 한쪽만 성공하고, 진 쪽은 PK 충돌을 잡아 재조회한다.
- **조회는 행을 만들지 않는다.** 행이 없으면 `AppSettings()` 모델 기본값을 그대로 쓴다. 정산 조회
  같은 읽기 경로가 조용히 INSERT를 하면 읽기 요청이 쓰기 트랜잭션이 되고 동시 조회가 500이 될 수
  있다. 행은 실제로 이름을 바꿀 때만 만든다(마이그레이션이 기본값 행을 시드하므로 실제로는 처음부터 있다).
- **여행(Trip)별이 아니라 앱 전역이다.** 같은 두 사람이 모든 여행을 함께 쓰므로, 여행마다 이름을
  따로 두면 이름 변경이 "여행 수만큼의 조작"이 된다.
- **컬럼 2개짜리 타입 있는 테이블**이지, `(key, value)` 키-밸류 테이블이 아니다(아래 기각 대안 참고).

### 2. `ItineraryItem.paid_by`에는 표시 이름이 아니라 **참가자 슬롯 키**를 저장한다

```python
# app/services/settlement.py
PARTICIPANT_1 = "participant_1"
PARTICIPANT_2 = "participant_2"
PARTICIPANT_KEYS: tuple[str, ...] = (PARTICIPANT_1, PARTICIPANT_2)
```

`paid_by`에 들어가는 값은 `"희경"`이 아니라 `"participant_1"`이다. 이름은 `AppSettings`에서
읽어 **표시할 때만** 붙인다. 이름 변경은 설정 행 한 줄 UPDATE이고, **지출 데이터는 한 행도
건드리지 않는다**.

`ADR-0006`이 기각했던 `paid_by_index: int`와는 다르다. 그때의 기각 근거는 "**상수 배열의 순서**에
의미가 매달려 있어서 순서를 바꾸면 기존 데이터가 조용히 뒤집힌다"였는데, 여기서는

- 저장되는 값이 **이름 붙은 키 문자열**이라 순서라는 개념이 없고(배열을 재정렬해도 `participant_1`은
  계속 `participant_1`이다),
- DB를 콘솔에서 직접 봐도 `1`이 아니라 `participant_1`이 보이며 `app_settings` 한 행만 조회하면
  누구인지 알 수 있다.

"DB를 직접 열었을 때 바로 읽힌다"는 이점은 (A)보다 분명히 손해다. 그 손해를 감수하는 이유는 아래 근거.

### 3. 정산 계산은 참가자를 **인자로 받는다** (숨은 전역 없음)

```python
compute_settlement(rows, trip_currency, participants: Sequence[Participant]) -> SettlementResult
```

`Participant = (key, name)`. 라우터가 `load_participants(db)`로 읽어 넘긴다. 기본값을 두지 않은
이유: 이름이 DB에 있는 런타임 값이 된 이상, 순수 함수가 "어딘가에서 알아서 가져오는" 전역을 가지면
DB 없이 테스트할 수 없어진다(ADR-0006이 이 모듈을 순수하게 유지한 이유가 그대로 유효하다).

집계는 **키 기준**, 응답은 **키 + 이름 둘 다**:

```jsonc
"per_person": [{"participant": {"key": "participant_1", "name": "희경"}, "paid": 10000.0, "item_count": 2}],
"transfer": {"from_participant": {"key": "...", "name": "..."},
             "to_participant":   {"key": "...", "name": "..."}, "amount": 5000.0}
```

ADR-0006에서는 이 자리가 문자열(`"participant": "희경"`)이었다. **깨는 변경이지만 소비자가 없다** —
정산 화면이 아직 구현되지 않았다.

### 4. 이름은 정산 응답에는 싣고, 일정(`ItineraryItemRead`) 응답에는 싣지 않는다

`GET /api/days/{id}/items`는 `paid_by`를 **키로만** 준다. 프론트가 `GET /api/settings`(캐시)로 이름을
붙인다. 반면 정산 응답에는 계산 시점의 이름을 함께 싣는다.

일관성이 없어 보이지만 기준이 있다:

| | 일정 (`ItineraryItemRead`) | 정산 (`SettlementRead`) |
|---|---|---|
| 성격 | **저장된 엔티티**의 표현 | 요청마다 새로 계산하는 **파생 읽기 모델** |
| 프론트 캐시 수명 | 길다(수정 전까지 유지) | 짧다(비용이 바뀔 때마다 무효화) |
| 이름을 실으면 | 이름 변경 후 **낡은 이름이 캐시에 남는다** | 다음 조회에 자연히 갱신된다 |

즉 **이름을 오래 사는 캐시에 복사하지 않는다**는 규칙이다. 덕분에 이름을 바꾼 뒤 프론트가
일정 캐시를 통째로 무효화할 필요가 없다(`['settings']`만 무효화하면 화면 전체가 새 이름이 된다).

### 5. 설정 API: `GET /api/settings`, `PATCH /api/settings` — 둘 다 세션 인증 필수

```
GET   /api/settings   → 200 {"participants": [{"key": "participant_1", "name": "희경"}, ...]}
                      → 401
PATCH /api/settings   body {"participants": {"participant_1": "새이름"}}   // 바꿀 슬롯만
                      → 200 (갱신된 전체 목록)
                      → 401 / 422
```

- **조회에도 인증을 요구한다.** 이 앱은 공유 비밀번호를 모르면 아무것도 못 보는 구조인데 설정만
  공개하면 인증 경계에 예외가 하나 생기고, 참가자 이름은 실명이기도 하다.
- **PATCH 바디는 `{슬롯 키: 이름}` 부분 맵**이다. 플랫한 `{"participant_1_name": ...}` 대신 맵을 쓴
  이유: 슬롯 키가 이미 `GET` 응답의 어휘라, 프론트가 받은 키를 그대로 돌려보내면 되고 별도 필드명을
  외울 필요가 없다.
- **응답은 언제나 전체 목록**이다(부분 갱신이어도). 프론트가 PATCH 결과를 그대로 캐시에 넣을 수 있다.
- 라우터/서비스 모듈 이름은 `settings.py`가 아니라 **`app_settings.py`**로 둔다. `app.config.settings`와
  이름이 겹치면 정반대의 두 개념이 같은 단어로 읽힌다. 경로는 사용자 관점의 `/api/settings` 그대로.

### 6. 이름 검증: 빈 값/공백 거부, 20자 상한, **명시적 null은 422**, 두 이름 중복 금지

이 저장소에서 세 번 밟은 "필드 생략 vs 명시적 null" 함정을 이번엔 이렇게 정리한다:

| 요청 | 결과 | 이유 |
|---|---|---|
| `{"participants": {}}` 또는 바디 `{}` | 200, 변경 없음 | "안 바꿈"의 올바른 표현 |
| `{"participants": {"participant_1": "새이름"}}` | 200, 그 슬롯만 변경 | 부분 갱신 |
| `{"participants": {"participant_1": null}}` | **422** | 이름 컬럼은 NOT NULL이고 "이름 없음" 상태가 이 앱에 없다 |
| `{"participants": {"participant_1": "  "}}` | **422** | 빈 이름은 화면에서 사람을 식별 불가능하게 만든다 |
| `{"participants": null}` | **422** | 위와 같음 |
| `{"participants": {"participant_9": "X"}}` | **422** | 슬롯이 2개뿐임을 명시 |

`paid_by`(명시적 null = "미지정으로 되돌리기" = 200)와 **반대 방향**인데, 판단 기준은 ADR-0006과
동일하다: **컬럼이 nullable인가, null이 의미 있는 상태인가.** `paid_by`는 둘 다 예이고 이름은 둘 다
아니다. 타입을 `dict[str, str]`로 선언한 것만으로 pydantic이 null을 걸러낸다(따로 검사하지 않는다).

**길이 상한 20자**: 이 값은 결제자 선택박스와 정산 표에 그대로 렌더링되므로 상한이 없으면 한 사람이
레이아웃을 깨뜨릴 수 있다. (`Trip.name`/`ItineraryItem.title`에 상한이 없는 건 Backlog Tier 2로 남아
있지만, 새로 만드는 필드까지 같은 빚을 지지는 않는다.)

**두 사람 이름이 같아지면 422.** 데이터가 깨지지는 않지만("희경이 희경에게 5,000원 송금") 화면이
무의미해지고 사용자가 의도했을 리 없다. 이 검사는 다른 슬롯의 현재 값을 알아야 하므로 스키마가 아닌
서비스 레이어에서 하고, 라우터가 422로 변환한다. 부분 갱신을 **적용한 결과**를 만들어 한 번에 검사하므로
**두 이름을 서로 맞바꾸는 요청도 정상 통과**한다(순서대로 검사하면 중간 상태가 중복이라 거부된다).

### 7. 마이그레이션은 기존 체인에 이어 붙인다 — `093074f849bc`를 고쳐 쓰지 않는다

```
d6eea980ecbe (checklist) → 093074f849bc (paid_by 컬럼) → 0e8fd49e8ad8 (app_settings + 시드 행)
```

`093074f849bc`가 운영에 미적용이라 "합쳐서 하나로 만들까"를 검토했지만 하지 않았다. 그 리비전은 이미
로컬 `dev.db`에 적용돼 있어서, 내용을 바꾸면 로컬만 조용히 스키마 드리프트가 생긴다(적용된 리비전을
사후 편집하는 건 alembic에서 가장 흔한 사고 유형이다). **컬럼 자체는 그대로 두고 의미만 바뀌므로
새 마이그레이션은 `paid_by`를 아예 건드리지 않는다** — 변환할 데이터가 0건이기 때문이다(위 배경 참고).

새 마이그레이션은 기본값 행(`id=1`, "희경"/"재승")을 시드한다. 운영 DB를 콘솔에서 열었을 때 현재
이름이 행으로 보이게 하기 위함이며, 행이 없어도 앱은 모델 기본값으로 동작한다(두 경로 모두 검증함).

## 근거 — (A) 문자열 유지 + 일괄 UPDATE vs (B) 슬롯 키 분리

| | **(A)** `paid_by`에 표시 이름 유지, 이름 변경 시 일괄 `UPDATE` | **(B)** 슬롯 키 저장 + 이름은 설정에서 조회 **(채택)** |
|---|---|---|
| 이름 변경 시 쓰는 행 수 | 설정 1행 + **매칭되는 지출 전부** (상한 없음) | 설정 **1행** |
| 지금 필요한 데이터 변환 | 없음(데이터가 0건이므로) | 없음(같은 이유) |
| 변경이 부분 실패하면 | 설정은 새 이름, 지출은 옛 이름 → 그 지출이 **정산에서 조용히 사라짐**(모르는 이름 = 미지정) | 실패할 다중 쓰기가 없음 |
| 이름을 서로 맞바꾸기 | 중간 임시값 없이는 두 사람 지출이 **뒤섞임** | 설정 값 두 개를 바꾸면 끝 |
| 한쪽을 상대 이름으로 변경 | 두 사람 지출이 **한 사람으로 병합, 복구 불가** | 그냥 거부하면 되는 표시 문제 |
| 동시 변경/입력 경합 | 이름 변경 트랜잭션 중에 들어온 새 지출은 옛 이름으로 저장될 수 있음 | 지출은 항상 키로 저장되므로 경합 자체가 없음 |
| `paid_by` pydantic 검증 | 허용값이 DB에 있으므로 **validator에서 DB를 읽어야 함**(구조상 불가에 가까움 → 라우터로 검증 이동) | `PARTICIPANT_KEYS` 정적 검사 그대로 유지 |
| DB 콘솔 가독성 | `paid_by = '희경'` 바로 읽힘 | `participant_1` → `app_settings` 한 행 조회 필요 |
| 프론트가 다루는 개념 | 이름 하나 | 키 + 이름 (선택박스 `value`/`label`로 이미 익숙한 형태) |
| 이름 변경 후 프론트 캐시 | 일정 캐시에 **옛 이름이 남아** 전부 무효화 필요 | `['settings']`만 무효화하면 전부 갱신 |

**(A)를 기각한 결정적 이유는 실패 모드의 비대칭이다.** (A)에서 이름 변경은 개수 상한이 없는
데이터 재작성이고, 재작성을 놓친 행은 `compute_settlement`에서 "모르는 이름 → 미지정"으로 빠진다 —
즉 **에러 없이 금액이 정산에서 사라진다.** 이 앱에서 가장 눈에 안 띄는 실패 모드이고, ADR-0006 스스로
같은 종류의 위험(통화 대소문자 불일치)을 "가장 눈에 안 띄는 실패 모드"라며 저장·계산 양쪽에서 막았다.
게다가 "한쪽 이름을 상대 이름으로 바꾸기"는 **복구 불가능한 병합**을 일으키는데, 이름 변경이 아무나
언제든 누르는 버튼이 된 이상 이건 이론적 시나리오가 아니다.

(B)에서는 이름 변경이 **지출 데이터를 정의상 건드릴 수 없다**. 최악의 경우도 "표시 이름이 이상하다"이며,
다시 바꾸면 원상복구된다.

두 번째 이유는 코드베이스 구조와의 마찰이다. (A)에서는 `paid_by`의 허용값이 DB에 있으므로
`app/schemas.py`의 `_normalize_paid_by()` validator가 DB 세션을 필요로 하는데, pydantic validator에서
DB를 읽을 깔끔한 방법이 없다. 결국 검증을 라우터로 옮기고 `items.py`의 POST/PATCH 두 곳에 흩뿌리게
된다. (B)는 검증이 정적 상수 비교로 남아 지금 구조가 그대로 유지된다.

(A)의 유일한 실질 이점은 **DB 콘솔 가독성**이다. 이건 진짜 손해이고 ADR-0006이 인덱스 방식을 기각한
근거이기도 했다. 다만 (ㄱ) 저장값이 숫자가 아니라 `participant_1`이라 "사람 슬롯"임이 읽히고,
(ㄴ) 매핑이 `app_settings` 한 행이라 한 번의 조회로 끝나며, (ㄷ) 잃는 것이 조회 편의인 반면 얻는 것이
데이터 무결성이므로, 이번 전제에서는 교환이 성립한다.

### 참가자를 추가/삭제하는 CRUD는 여전히 만들지 않는다

사용자 요구는 **이름 변경**뿐이다(2명 고정은 유지). 슬롯이 2개로 고정이므로 `Participant` 테이블도,
추가/삭제 API도, "참가자를 지우면 그 사람의 지출은 어떻게 되나"(FK RESTRICT? 고아 지출?)라는 질문도
생기지 않는다. ADR-0006의 이 판단은 그대로 유효하며, 오히려 슬롯 키 방식이 "참가자는 2개 슬롯"이라는
사실을 스키마에 더 정직하게 드러낸다.

## 결과

### 좋아지는 것
- 이름 변경이 **설정 한 행 UPDATE**로 끝난다. 과거 지출이 자동으로 새 이름으로 집계된다.
- 이름을 바꿔도 지출 데이터가 **구조적으로 손상될 수 없다**. 잘못 바꿨으면 다시 바꾸면 된다.
- 이름 변경에 배포가 필요 없다(코드에 이름이 남아 있지 않다 — 기본값 제외).
- `paid_by` 검증이 DB를 모르는 정적 검사로 남아 `schemas.py` 구조가 그대로다.
- 프론트는 이름 변경 후 `['settings']` 캐시만 무효화하면 되고, 일정 캐시는 건드릴 필요가 없다.

### 감수하는 것
- **DB를 직접 열면 `paid_by = 'participant_1'`이라 누구인지 바로 안 보인다.** `app_settings` 한 행을
  함께 봐야 한다. 이번 교환에서 실제로 잃는 것.
- **프론트가 키→이름 변환을 한 번 해야 한다.** `GET /api/settings`를 한 번 받아 맵으로 들고 있어야
  하며, 이 조회가 실패하면 결제자를 이름으로 표시할 수 없다(키를 그대로 보여주는 폴백 필요).
- **정산 응답 형태가 깨지는 변경**이다(`participant`가 문자열 → 객체). 소비자가 아직 없어 지금은 공짜지만,
  프론트 구현 후에는 같은 변경이 비싸진다.
- **참가자 이름 변경 이력이 남지 않는다.** 누가 언제 바꿨는지 모른다(`updated_at`만). 감사 로그는 요구에 없다.
- **슬롯 키를 나중에 바꾸기는 어렵다.** `participant_1`이 데이터에 박히므로, 키 자체를 바꾸려면 그때는
  진짜 데이터 마이그레이션이 필요하다. 그래서 키를 의미 없는 중립적 이름으로 골랐다(`hee`/`js` 같은
  사람 유래 키를 쓰면 같은 문제가 반복된다).
- **에러 `detail`은 계속 영어다**(ADR-0002~0006과 같은 정책).

## 기각한 대안

- **(A) 표시 이름 유지 + 이름 변경 시 지출 일괄 `UPDATE`** — 위 비교표. 이름 변경이 상한 없는 데이터
  재작성이 되고, 놓친 행은 에러 없이 정산에서 사라지며, 상대 이름으로 바꾸면 복구 불가능하게 병합된다.
- **이름을 `.env`/`Settings`(환경변수)로** — ADR-0006에서 이미 기각한 그대로, 그리고 이번 요구("화면에서
  바꾸기")를 아예 충족하지 못한다. 재배포 없이 못 바꾸는 값이다.
- **`(key, value)` 키-밸류 설정 테이블** — 타입이 사라져 값마다 파싱/검증 분기가 생기고, 응답 스키마가
  `dict[str, str]`로 흐물흐물해진다. 지금 설정 항목은 타입이 확정된 2개뿐이고, 늘어도 컬럼 추가가 더 싸다.
- **`paid_by_index: int`(0/1)** — ADR-0006의 기각을 유지한다. 숫자는 DB에서 의미가 전혀 안 읽히고,
  "몇 번째"라는 순서 개념에 의미가 붙는다. 슬롯 **키 문자열**은 그 두 문제가 모두 없다.
- **참가자 이름을 `Trip`별로** — 같은 두 사람이 모든 여행을 쓰므로 이름 변경이 여행 수만큼 반복된다.
  "마스터 환경설정"이라는 요구 자체가 전역 설정을 가리킨다.
- **`Participant` 테이블 + 추가/삭제 CRUD** — 요구는 이름 변경뿐이다(2명 고정 유지). ADR-0006의 기각 근거
  그대로.
- **`ItineraryItemRead`에 `paid_by_name`을 함께 싣기** — 프론트가 변환을 안 해도 되지만, 오래 사는 일정
  캐시에 이름이 복사되어 이름 변경 후 낡은 값이 남는다. 그러면 이름 변경이 다시 "여러 캐시를 무효화하는
  작업"이 되어 (B)로 얻은 이점이 줄어든다.
- **기존 마이그레이션 `093074f849bc`를 수정해 하나로 합치기** — 로컬에 이미 적용된 리비전이라 편집하면
  스키마 드리프트가 생긴다. 새 리비전을 이어 붙이는 비용이 거의 0이다.
- **이름 변경 이력 테이블** — 요구에 없다. 2인용 앱에서 감사 로그는 과설계.
