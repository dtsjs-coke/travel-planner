# ADR-0004: 일정(ItineraryItem)을 다른 Day로 옮기는 API 설계

- **날짜**: 2026-09-10 (작업 자체는 2026-09-09 세션의 연속)
- **상태**: Accepted
- **작성**: senior-dev (오케스트레이터 위임)
- **관계**: 기존 `POST /api/days/{day_id}/items/reorder`(같은 Day 내부 정렬)와 역할을 나눠 갖는다.
  Day 삭제 시 일정이 CASCADE로 사라지는 문제(ADR-0001)에 대한 사용자 측 우회 수단이기도 하다.

## 배경

사용자 요청: **"여행 일정(장소)을 다른 날로 옮길 수 있게 해달라."**

지금까지 일정의 소속 Day를 바꿀 방법이 전혀 없었다.

- `PATCH /api/items/{id}`는 `ItineraryItemUpdate`에 `day_id`가 없어서 제목/메모 등만 고칠 수 있다.
- `POST /api/days/{day_id}/items/reorder`는 **그 Day에 이미 있는 항목 집합**을 통째로 받아
  순서를 다시 매기는 API다(`set(ordered_item_ids) != set(현재 항목)`이면 400). 정의상 Day 간
  이동을 표현할 수 없다.
- 그래서 사용자는 "지우고 다른 날에 다시 추가"밖에 못 했다 — 구글 장소에서 가져온 항목이면
  좌표/주소/place_id를 다시 검색해서 붙여야 한다.

실제 여행 계획에서 "이 장소는 첫날 말고 셋째 날에 가자"는 아주 흔한 조작이므로 API가 필요하다.

`ItineraryItem`에 `day_id`(FK)와 `position`이 이미 있어서 **DB 스키마 변경도 마이그레이션도
필요 없다.** 결정해야 할 것은 순전히 API 표면과 검증 정책이다.

## 결정

### 1. 별도 엔드포인트 `POST /api/items/{item_id}/move` (요청 바디 `{"target_day_id": int}`)

`PATCH /api/items/{id}`에 `day_id`를 추가하는 방식을 택하지 않는다(근거 참고).

```
POST /api/items/{item_id}/move
body: {"target_day_id": 42}
→ 200 ItineraryItemRead   (이동된 항목, 갱신된 day_id/position 포함)
→ 401                     (라우터 전체가 require_session으로 보호됨)
→ 404 "Item not found"    (item_id가 없음)
→ 404 "Day not found"     (target_day_id인 Day가 아예 없음)
→ 422 "target day must belong to the same trip as the item"
→ 422                     (바디 누락/타입 오류 — pydantic 기본)
```

### 2. 목적지는 **같은 트립의 Day**여야 한다 — 다른 트립이면 422

`item.day_id`로 원본 Day를 읽어 `source_day.trip_id != target_day.trip_id`면 거부한다.
이걸 막지 않으면 A 여행의 일정이 B 여행 화면에 나타나 두 여행의 데이터가 섞인다. 게다가
프론트는 `['days', dayId, 'items']` 캐시를 트립 단위 화면에서만 구독하므로, 섞인 항목은
사용자가 그 트립을 열기 전까지 **눈에 보이지도 않는다**(조용한 데이터 오염).

**404가 아니라 422**로 구분하는 이유: Day는 실제로 존재한다. "없는 리소스"(404)와 "존재하지만
이 요청에서 유효한 대상이 아님"(422)은 프론트가 다르게 다뤄야 하는 상황이다 — 전자는 목록을
새로고침해야 하고, 후자는 새로고침해도 그대로다.

### 3. 목적지에서의 삽입 위치는 항상 **맨 뒤**, 요청으로 받지 않는다

`target_position` 같은 파라미터를 두지 않는다. 옮긴 뒤 그 Day 안에서의 순서 조정은 이미 있는
`POST /api/days/{day_id}/items/reorder`(dnd-kit 드래그)가 담당한다.

### 4. 원본 Day에 남은 항목들의 `position`을 0..N-1로 다시 매긴다 — `delete_item`과 같은 정책

이동은 원본 Day에서 보면 삭제와 같아서 `position`에 구멍이 생긴다. 기존 `delete_item`이
이미 삭제 후 재번호를 매기고 있으므로 **같은 정책을 그대로 따른다**(정렬 로직이 두 갈래가 되면
안 된다). 이동과 재번호는 **한 번의 `commit()`**으로 처리해 "옮겨졌는데 원본은 구멍난" 중간
상태가 남지 않게 한다.

### 5. 이미 그 Day에 있으면 **아무것도 하지 않고** 현재 상태를 200으로 돌려준다 (멱등)

`item.day_id == target_day_id`면 즉시 반환한다. 여기서 "맨 뒤로 붙이기"를 실행하면 재시도나
더블탭이 **같은 Day 안의 순서를 몰래 바꿔버린다** — 이동 요청의 의도는 순서 변경이 아니다.
ADR-0003에서 토글 전용 엔드포인트를 기각한 것과 같은 기준(멱등성).

### 6. 마이그레이션 없음, 모델 변경 없음

`ItineraryItem.day_id` / `position` 컬럼을 그대로 쓴다. 운영 Neon DB에 적용할 것이 없다.

### 7. 구현 주의: 읽기를 먼저 끝낸 뒤 `item`을 수정한다 (autoflush 함정)

`_next_position(db, target_day_id)`는 목적지 Day의 최대 `position`을 SELECT로 구한다.
그런데 `item.day_id`를 먼저 바꾸고 나서 이 SELECT를 날리면, SQLAlchemy의 **autoflush**가
그 변경을 먼저 DB에 밀어넣어서 **아직 옛 position을 가진 item 자신이 목적지 Day 소속으로
집계된다**. 그 결과 `position`이 "목적지의 맨 뒤"가 아니라 "옛 position + 1"이 된다
(예: 3번째 자리에 있던 항목을 **빈 Day**로 옮기면 `position`이 0이 아니라 3).

그래서 `remaining` 조회와 `_next_position()`을 **모두 마친 뒤에** `item`을 수정한다.
이 순서 의존성은 코드만 봐서는 드러나지 않으므로 라우터에 주석으로 못박아 두었고,
검증 스크립트에도 "빈 Day로 이동 → position == 0" 케이스를 남겼다.

> 이 함정은 실제로 발생한 버그였다. 이 기능의 첫 구현 시도(2026-09-09, API 레이트리밋으로
> 중단된 세션)가 정확히 이 순서로 작성돼 있었고, 검증 스크립트에서 3건 실패로 드러나 고쳤다.

## 근거

### 왜 `PATCH /api/items/{id}`에 `day_id`를 얹지 않는가

| | (a) `POST /api/items/{id}/move` (채택) | (b) `PATCH /api/items/{id}`에 `day_id` 추가 | (c) reorder API를 트립 단위로 확장 |
|---|---|---|---|
| 부수효과 | 이동 = 명시적 조작 | 제목 수정과 이동이 같은 엔드포인트 | 정렬 API가 소속 변경까지 겸함 |
| `position` 재계산 | 이동 시에만 | **모든** PATCH가 이동 가능성을 검사해야 함 | 매 요청이 전체 재배치 |
| 트립 검증 | 이동 경로에만 | 모든 PATCH에 조건부 분기 | 전체 |
| 기존 코드 영향 | 없음(함수 추가) | `update_item`의 일반 루프(`setattr`)를 특수분기로 오염 | 기존 계약 파괴 |

- **(b) 기각**: `update_item`은 `model_dump(exclude_unset=True)`를 돌며 `setattr`하는 **완전히
  일반적인 루프**다. 여기에 `day_id`가 들어오면 "이 필드만은 position 재계산 + 원본 Day 재번호
  + 트립 검증을 유발한다"는 특수 분기가 붙는다. 게다가 `{"title": "x", "day_id": 3}`처럼
  두 조작이 한 요청에 섞이면 부분 실패 시 어디까지 반영됐는지 설명하기 어렵다. 무엇보다
  **이동은 실수로 보내면 데이터가 눈에 안 보이는 곳으로 가는 조작**이라, 일반 편집 요청에
  묻어가게 두면 안 된다(ADR-0001에서 `force=true` 한 방 삭제를 기각한 것과 같은 기준).
- **(c) 기각**: 기존 `reorder`의 계약("이 Day의 항목 집합과 정확히 일치해야 함")을 깨야 하고,
  프론트의 드래그 낙관적 업데이트(M3에서 가장 손보기 어려웠던 부분)를 통째로 다시 만들어야 한다.
- **(a) 채택**: 기존 `reorder`가 이미 "리소스에 대한 동사형 POST" 패턴이라 API 표면이
  일관된다. 기존 함수를 한 줄도 건드리지 않고 함수 하나만 추가하면 된다.

### 왜 삽입 위치를 받지 않는가 (맨 뒤 고정)

- 사용자가 "다른 날로 옮긴다"고 생각할 때 대개 그 날 **어디에** 넣을지는 아직 정하지 않았다.
  옮긴 뒤 그 Day를 보면서 드래그로 자리를 잡는 게 실제 흐름이다.
- 위치를 받으면 서버는 목적지 Day 전체를 밀어내는 재배치 로직(+ 범위 밖 index 검증)을 떠안는데,
  그건 이미 `reorder`가 하는 일이다. **같은 일을 하는 코드가 두 벌 생긴다.**
- 프론트도 이득이 없다. 데스크톱은 Day 탭 전환이라 목적지 Day의 항목 목록이 화면에 없고,
  모바일 연속 스크롤에서도 "몇 번째 자리"를 지정할 UI가 없다. 지금 이 정보를 제공할 화면이
  아예 없으므로 파라미터만 늘어난다.
- 나중에 정말 필요해지면 `target_position: int | None = None`을 **바디에 추가**하면 되고,
  기존 클라이언트는 그대로 동작한다(생략 = 맨 뒤). 되돌리기 비용이 낮은 쪽이다.

### 왜 원본 Day를 재번호 매기는가 (구멍을 그냥 두지 않고)

`position`은 정렬 키일 뿐이라 `0, 1, 3`처럼 구멍이 있어도 표시 순서는 멀쩡하다. 그래도 메우는 이유:

- 기존 `delete_item`이 이미 메운다. 한쪽만 안 메우면 "언제 구멍이 생기고 언제 안 생기는지"가
  코드를 읽어야만 알 수 있는 상태가 된다.
- 프론트의 낙관적 업데이트는 배열 index를 그대로 `position`으로 간주하는 곳이 있다. 서버가
  0..N-1을 보장해야 서버 값과 클라이언트 추정값이 어긋나지 않는다.

### 왜 no-op을 400/409가 아니라 200으로 처리하는가

"이미 원하는 상태"는 오류가 아니다. 프론트가 드롭다운에서 현재 Day를 다시 고르거나, 네트워크
재시도로 같은 요청이 두 번 도착하는 건 정상적인 경로다. 에러로 만들면 프론트가 "현재 Day는
선택 목록에서 빼기"를 반드시 구현해야 하고(빼먹으면 사용자에게 빨간 에러가 뜬다), 재시도가
실패로 보인다.

## 결과

### 좋아지는 것
- 일정을 지웠다 다시 만들지 않고 다른 날로 옮길 수 있다. 구글 장소 정보(`place_id`/좌표/주소)와
  메모/비용/시간이 전부 보존된다.
- ADR-0001의 "범위 밖 Day 삭제" 흐름에 **일정을 살릴 수단**이 생겼다. 지금까지는 Day를 지우면
  CASCADE로 일정이 함께 사라지는 것 말고 선택지가 없었는데, 이제 옮기고 나서 Day를 지우면 된다.
- DB 변경이 없어 운영(Neon) 마이그레이션이 필요 없고, 백엔드만 배포하면 끝난다.

### 감수하는 것
- **목적지 Day 안의 위치를 한 번에 지정할 수 없다.** 옮긴 뒤 드래그로 조정해야 한다(요청 2회).
- **동시 이동 시 `position` 중복 가능.** 두 요청이 같은 목적지 Day로 동시에 들어오면 둘 다 같은
  `_next_position()` 값을 읽어 같은 `position`을 가질 수 있다. `Day(trip_id, date)`(ADR-0002)와
  달리 `position`에는 유니크 제약을 걸지 않는다 — `reorder`가 중간 상태로 중복 position을
  만들 수 있고, 결과도 "두 항목의 앞뒤가 임의로 정해짐"일 뿐 데이터가 깨지지 않으며, 사용자가
  드래그 한 번 하면 `reorder`가 0..N-1로 정규화한다. 비용 대비 이득이 없어 막지 않는다.
- **프론트 없이는 사용자가 쓸 수 없다**(ui-dev 후속). API 계약은 위 1번 그대로다.
- **에러 `detail`이 영어다** — ADR-0002/0003에서 정한 계약 언어 정책 그대로. 한국어 노출은
  프론트 담당(Backlog Tier 2의 기존 항목).

## 기각한 대안

- **`PATCH /api/items/{id}`에 `day_id` 추가** — 위 표 참고. 이동이라는 파괴적일 수 있는 조작이
  일반 편집 요청에 묻어간다.
- **`POST /api/days/{target_day_id}/items/{item_id}`(목적지 중심 URL)** — REST 관점에서
  "이 Day에 이 항목을 넣는다"가 자연스러워 보이지만, 응답으로 돌려줄 리소스가 옮겨진 item이라
  URL의 주어(Day)와 응답이 어긋난다. 또 프론트가 갖고 있는 건 "지금 조작 중인 item"이고
  목적지는 사용자가 방금 고른 값이라, 코드에서도 item이 주어다.
- **`target_position`을 지금 함께 받기** — 이를 채울 UI가 데스크톱/모바일 어디에도 없다.
  나중에 바디 필드 추가로 하위호환되게 넣을 수 있다.
- **Day 간 dnd-kit 드래그 앤 드롭** — 데스크톱은 Day 탭 전환이라 출발지와 목적지가 동시에
  화면에 없고(드롭 타깃이 존재하지 않음), 모바일은 연속 스크롤이라 이론상 가능하지만 긴 거리를
  드래그하면서 자동 스크롤까지 붙여야 한다. 이번 요구("옮길 수 있게")에 비해 과하다.
  API는 이 방식으로 나중에 바꿔도 그대로 쓸 수 있다(`move` 호출은 동일).
- **트립 간 이동 허용** — 요청에 없다. 여행이 다르면 날짜·통화·동선이 전부 달라서 "옮긴다"의
  의미가 불분명하고, 잘못 보낸 요청 하나가 조용한 데이터 오염이 된다.
- **소속 변경 이력 테이블** — 되돌리기 UI 계획이 없다. ADR-0003에서 소프트 삭제를 기각한 것과 동일.
