# ADR-0006: 지출 결제자 표현 방식과 더치페이 정산 계산

- **날짜**: 2026-09-10
- **상태**: Accepted (참가자 이름의 저장/변경 방식은 [ADR-0007](0007-runtime-participant-names.md)이 대체)
- **작성**: senior-dev (오케스트레이터 위임)
- **관계**: 기존 `ItineraryItem.cost_amount`/`cost_currency`, `Trip.currency` 컬럼(M1부터 있었으나

> **후속**: 이 ADR은 "참가자 이름은 코드 상수이고 바뀌려면 배포가 필요하다"는 전제 위에 서 있었다.
> 사용자가 **이름을 화면(마스터 환경설정)에서 실시간으로 바꿀 수 있게** 해달라고 요청하면서 그 전제가
> 사라졌고, [ADR-0007](0007-runtime-participant-names.md)에서 `PARTICIPANTS` 상수를 없애고
> `paid_by`에 **표시 이름 대신 슬롯 키**(`participant_1`/`participant_2`)를 저장하는 방식으로 바꿨다.
> 아래 결정 중 **1번(참가자 테이블/CRUD 없음)과 2번의 "표시 이름 문자열 저장" 부분은 무효**이며,
> 3~8번(명시적 null 허용, 순수 함수 정산, 2명 차액의 절반, 통화 혼합 처리, 엔드포인트 형태, 음수/NaN
> 차단)은 그대로 유효하다. 기각 근거 중 `paid_by_index`에 대한 판단이 어떻게 달라졌는지도 ADR-0007 참고.
  쓰이지 않던 필드)에 처음으로 의미를 부여한다. 참가자 개념이 없던 이 앱에 "누가 냈는지"가 들어오는
  첫 결정이다.

## 배경

M7 Tier 1 백로그의 마지막 항목: **"예산/지출 추적 + 정산(더치페이)"**.

사용자 확인으로 범위가 확정됐다 — 집계 + 결제자 + **실제 정산까지**. 그리고 결정적인 단순화
조건이 함께 나왔다:

> **이 앱을 쓰는 사람은 "희경"과 "재승" 두 명뿐이고, 앞으로도 늘릴 계획이 없다.
> 참가자 관리 UI 없이 선택박스로 고정해도 된다.**

이건 "지금은 2명이지만 나중에 늘 수도 있으니 일반화해두자"와는 다른 요구다. 이 앱은 애초에
개별 계정이 없고 **공유 비밀번호 하나로 두 사람이 함께 쓰는** 구조라(인증 설계, `docs/PROJECT.md`),
"사용자"라는 개념 자체가 시스템에 없다. 참가자를 데이터로 관리하기 시작하면 이 앱에 없던
사용자 관리 계층이 통째로 생긴다.

기존 스키마 확인 결과:

- `ItineraryItem.cost_amount: float | None`, `cost_currency: str | None` — 컬럼과 pydantic 필드는
  이미 있었고 POST/PATCH가 실제로 저장한다. **다만 값을 입력하는 UI가 없어 전부 NULL**이다
  (`dev.db` 확인: 일정 3건, `cost_amount` 전부 NULL).
- `Trip.currency: str = "KRW"` (NOT NULL).
- 결제자를 표현할 방법은 없다.

## 결정

### 1. 참가자 테이블/관리 API를 만들지 않는다. 두 이름은 코드 상수 하나로 둔다

```python
# app/services/settlement.py
PARTICIPANTS: tuple[str, ...] = ("희경", "재승")
```

이 상수가 **유일한 소스**다. 결제자 값 검증(`app/schemas.py`)과 정산 계산(같은 모듈)이 이것만 본다.
`Participant` 테이블도, 참가자 CRUD 엔드포인트도, 참가자 관리 화면도 만들지 않는다.

### 2. 결제자는 `ItineraryItem.paid_by: str | None` 컬럼 하나 (nullable, NULL = 미지정)

새 테이블도 FK도 없다. 마이그레이션 `093074f849bc`는 nullable 컬럼 추가뿐이라 백필이 없고
기존 데이터에 영향이 없다.

**DB CHECK 제약은 걸지 않는다.** 허용값 검증은 애플리케이션 레벨(pydantic)에서만 한다 —
"한 여행에 같은 날짜 Day는 하나"(ADR-0002, DB 제약을 건 사례)는 데이터가 깨지는 도메인
불변식이지만, 결제자 이름은 **지금 이 앱을 쓰는 사람 목록**이라 성격이 다르다. CHECK를 걸면
이름 하나 바꾸는 데 마이그레이션이 필요해진다.

### 3. `paid_by`는 명시적 `null`을 허용한다 (`title`/`text`와 반대)

이 저장소에서 두 번 밟았던 함정("필드 생략 vs 명시적 null", `ItineraryItemUpdate.title` →
`ChecklistItemUpdate.text`)을 이번엔 **반대 방향으로** 판단해야 한다.

| | `title` / `text` | `paid_by` / `cost_amount` / `cost_currency` |
|---|---|---|
| DB 컬럼 | NOT NULL | nullable |
| 명시적 `null` | 422로 거부 (통과시키면 `setattr(None)` → 500) | **200으로 허용** (= "미지정으로 되돌리기") |
| 필드 생략 | 라우터의 `exclude_unset=True`가 걸러 validator 미호출 | 동일 |

`{"paid_by": null}`은 "결제자를 지웠다"는 정상적인 수정이다. 빈 문자열/공백도 `None`으로
정규화한다 — 프론트 `<select>`의 "미지정" 옵션 value가 보통 `""`인데, 그걸 422로 튕기면 화면
쪽에 "빈 문자열이면 필드를 빼고 보내기" 변환 코드가 생긴다.

허용 목록에 없는 이름은 422이며, 메시지에 허용값을 함께 준다.

### 4. 정산 계산은 순수 함수, 저장하지 않고 매번 계산한다

`app/services/settlement.py`의 `compute_settlement(rows, trip_currency)`는 DB도 HTTP도 모른다
(`trip_days.py`의 `validate_date_range`/`diff_days_for_range`와 같은 패턴). 결과 테이블을 두지
않는 이유: 정산액은 일정의 비용/결제자가 바뀔 때마다 달라지는 **파생값**이라, 저장하면 원본과
어긋난 상태를 관리해야 한다. 데이터 규모가 트립당 일정 수십 건이라 매번 계산해도 비용이 없다.

분류 규칙은 순서대로:

1. `cost_amount`가 NULL이면 지출이 아니다 (비용을 입력하지 않은 일반 일정) — 완전히 무시.
2. 통화가 기준 통화(`Trip.currency`)와 다르면 **제외**하고 따로 보고한다 (아래 6번).
3. `paid_by`가 참가자 목록에 없으면(미지정 또는 알 수 없는 이름) **정산에서 제외**하고
   `unassigned_amount`/`unassigned_item_count`로 보고한다.

### 5. 2명 고정이므로 "차액의 절반" 한 줄 계산 — 최소 송금 알고리즘 없음

```
total = 희경이 낸 돈 + 재승이 낸 돈
share = total / 2
덜 낸 사람 → 더 낸 사람에게 |낸 돈 - share| 만큼 송금
```

응답의 `transfer`는 `{from_participant, to_participant, amount}` 하나이며, 이미 균형이거나
지출이 없으면 `null`이다(오류가 아니다).

**참가자가 3명 이상이면 이 함수는 `transfer`를 계산하지 않고 `null`을 준다.** 위 공식이
2명일 때만 성립하기 때문이다. 조용히 틀린 답을 주느니 "계산하지 않음"을 명시한다 — 만약
누군가 `PARTICIPANTS`에 이름을 추가하면 그 순간 정산 화면이 비어서 바로 드러난다.

### 6. 통화가 섞이면 환율 변환 없이 **기준 통화 항목만** 합산하고 경고한다

기준 통화는 `Trip.currency`다. `cost_currency`가 비어 있으면 **기준 통화로 간주한다** —
지금까지 이 필드를 채우는 UI가 없어서 전부 NULL이고, "통화 미상"으로 취급하면 앞으로 입력될
모든 지출이 정산에서 빠진다.

기준과 다른 통화의 지출은 `excluded_currencies`(통화별 합계 + 건수)와 `has_mixed_currency`
플래그로 보고만 한다. **환율 변환은 하지 않는다** — 환율 API(외부 의존 + 키 관리 + 무료 티어
한도)와 "어느 시점 환율인가"라는 답 없는 질문이 따라온다. 이번 요구에 없다.

통화 코드는 저장 시점(`"krw " → "KRW"`)과 계산 시점 양쪽에서 대문자/trim 정규화한다.
대소문자 차이 하나로 같은 통화가 "다른 통화"로 분류돼 합계에서 통째로 빠지는 게 이 설계에서
가장 눈에 안 띄는 실패 모드다.

### 7. `GET /api/trips/{trip_id}/settlement` — 읽기 전용 엔드포인트 하나

```
GET /api/trips/{trip_id}/settlement
→ 200 SettlementRead
→ 401 (라우터 전체가 require_session)
→ 404 "Trip not found"
```

```jsonc
{
  "trip_id": 1,
  "currency": "KRW",
  "participants": ["희경", "재승"],          // 프론트가 이름을 하드코딩하지 않아도 되게 함께 준다
  "per_person": [
    {"participant": "희경", "paid": 10000.0, "item_count": 2},
    {"participant": "재승", "paid": 20000.0, "item_count": 1}
  ],
  "total": 30000.0,
  "per_person_share": 15000.0,
  "transfer": {"from_participant": "희경", "to_participant": "재승", "amount": 5000.0},
  "unassigned_amount": 7000.0,               // 결제자 미지정 지출 (정산에서 제외됨)
  "unassigned_item_count": 1,
  "excluded_currencies": [{"currency": "JPY", "amount": 800.0, "item_count": 1}],
  "has_mixed_currency": true
}
```

빈 트립도 에러가 아니다: 합계 0, `per_person`은 두 사람 모두 0으로 포함, `transfer: null`.
없는 트립은 404다(빈 결과로 숨기지 않는다 — `list_checklist_items`와 같은 기준).

새 라우터 파일 `app/routers/settlement.py`로 분리했다. `trips.py`는 트립 CRUD + Day 동기화만으로도
이미 크고, 정산은 `ItineraryItem`을 읽는 별개 관심사다(체크리스트를 별도 라우터로 뺀 것과 같은 기준).

### 8. 곁다리로 막은 것: 음수/NaN 비용

`cost_amount`에 `>= 0` + 유한수 검증을 추가했다. 지금까지 검증이 없었는데, 이 값이 **처음으로
합산되기 시작**하므로 음수 하나가 "누가 누구에게 얼마"를 통째로 뒤집는다.

NaN을 막으면서 기존에 숨어 있던 500 경로가 드러났다: 파이썬 `json.loads`는 JSON 표준에 없는
`NaN`/`Infinity` 리터럴을 기본으로 받아들이는데, FastAPI 기본 422 핸들러가 `exc.errors()`의
`input`에 그 값을 그대로 실어 응답하려다 `json.dumps`에서 터진다 → 클라이언트는 422가 아니라
**처리되지 않은 500**을 받는다. `app/main.py`에 기본 핸들러와 동일하되 비유한 float만 문자열로
바꾸는 `RequestValidationError` 핸들러를 추가했다(응답 형태 `{"detail": [...]}`는 그대로라
프론트 `extractErrorMessage()`에 영향 없음).

## 근거

### 왜 `Participant` 테이블을 만들지 않는가

| | (a) `paid_by` 문자열 컬럼 (채택) | (b) `Participant` 테이블 + FK | (c) `paid_by_index: int` (0/1) |
|---|---|---|---|
| 새 테이블/API | 없음 | 테이블 1 + CRUD 4개 + 관리 화면 | 없음 |
| 마이그레이션 | nullable 컬럼 1개 | 테이블 + FK + 시드 데이터 | 컬럼 1개 |
| DB를 직접 열었을 때 | `paid_by = '희경'` 바로 읽힘 | JOIN 필요 | `1`이 누군지 코드를 봐야 앎 |
| 이름 변경 비용 | 상수 1줄 + `UPDATE` 1회 | 행 1건 UPDATE | 상수 1줄 |
| 사용자 요구와의 거리 | 정확히 일치 | 요구하지 않은 관리 기능 | 일치하나 가독성 손해 |

- **(b) 기각**: 사용자가 명시적으로 "참가자 관리 UI 없이 고정해도 된다"고 했다. 이 앱엔 계정
  개념이 없어서 참가자 테이블을 만드는 순간 "누가 이 참가자를 추가/삭제할 수 있는가"(공유
  비밀번호를 아는 사람은 전부 가능)라는 답할 필요 없는 질문이 생긴다. 참가자 삭제 시 기존 지출을
  어떻게 할지(FK RESTRICT? CASCADE? 고아 지출?)도 전부 지금은 없어도 되는 문제다.
- **(c) 기각**: 이름을 인덱스로 저장하면 DB를 직접 들여다볼 때(운영 Neon 콘솔에서 종종 그런다)
  의미를 읽을 수 없고, 상수 배열 순서를 바꾸는 순간 **기존 데이터의 의미가 조용히 뒤집힌다**.
  문자열은 최악의 경우에도 "모르는 이름 → 미지정 취급"으로 안전하게 퇴화한다.
- **(a) 채택**: 지금 필요한 것을 정확히 만든다. 나중에 정말 참가자 관리가 필요해지면 `Participant`
  테이블을 추가하고 `paid_by` 문자열을 FK로 옮기는 마이그레이션(2행짜리 데이터)을 하면 된다 —
  되돌리기 비용이 **지금 안 만드는 쪽**이 훨씬 싸다.

### 왜 `Settings`(환경변수)가 아니라 코드 상수인가

`config.py`의 `Settings`로 빼서 `.env`로 관리하는 안을 검토했고 기각했다.

- 참가자 이름은 **배포 환경에 따라 달라지는 값이 아니다.** `Settings`에 있는 값들(DB URL, 시크릿,
  CORS origin, 패스코드)은 전부 로컬/운영이 달라야 하는 것들인데, 이름은 두 환경이 같아야 한다.
- 오히려 위험하다: 로컬 `.env`와 Render 환경변수가 어긋나면 **한쪽에서만 422**가 나고, 그 원인이
  코드 어디에도 안 보인다.
- "env 한 줄로 이름 변경"이 성립하지 않는다. 이름은 DB에 문자열로 저장되므로, 바꾸면 기존 행을
  `UPDATE`해야 한다. 즉 어차피 **배포 + 데이터 수정**이 한 묶음이며, 그렇다면 상수도 같은 커밋에
  들어가는 게 맞다.
- 상수를 서비스 모듈에 두면 스키마 검증과 계산이 같은 것을 보고, 응답의 `participants` 필드로
  프론트에도 흘려보낼 수 있다.

### 왜 결제자 미지정 지출을 정산에 넣지 않는가

넣으려면 "누가 냈는지"를 서버가 추측해야 한다(반반 부담? 마지막 결제자?). 어느 쪽도 근거가 없고,
틀리면 **사용자가 눈치채기 어려운 방식으로 금액이 어긋난다**. 대신 `unassigned_amount`로 돌려줘서
프론트가 "결제자를 지정하지 않은 지출 N건(7,000원)이 정산에서 빠졌습니다"라고 안내하게 한다 —
빠뜨린 입력은 사람이 보고 채우는 게 맞다(ADR-0001의 "파괴적/모호한 판단은 사람이"와 같은 기준).

`PARTICIPANTS`에 없는 이름(이름을 바꾼 뒤 남은 옛 데이터 등)도 같은 통에 넣는다. 500이 나거나
정산이 조용히 틀리는 것보다, "미지정 지출이 있다"고 보이는 게 낫다.

### 왜 float를 그대로 쓰는가 (Decimal/정수 최소단위가 아니라)

돈 계산에 float는 원칙적으로 나쁘지만:

- `cost_amount`는 이미 `float` 컬럼이다. 바꾸려면 마이그레이션 + 기존 데이터 변환 + 프론트 계약
  변경이 따라온다(지금 값이 전부 NULL이라 데이터 변환 자체는 공짜지만, 나머지는 아니다).
- 오차가 실제로 문제가 되려면 수천 건의 누적 합산이 필요한데, 여기는 트립당 수십 건이고
  두 사람이 눈으로 확인하는 금액이다.
- 응답 금액을 소수 둘째 자리에서 반올림해 `0.30000000000000004` 같은 표시 사고만 막는다.

정말 정확한 원 단위 정산이 필요해지면 그때 정수 최소단위로 옮기면 된다. 지금 하는 건 과설계다.

### 왜 정산 결과를 저장하지 않는가

"2026-09-10에 정산 완료" 같은 **정산 이력**은 요구에 없다. 저장하면 "언제 무효화하는가"(일정 비용
수정/삭제/Day 이동/Day 삭제 CASCADE — 전부 정산액을 바꾼다)를 관리해야 하고, 그 무효화를 빠뜨리면
화면에 낡은 금액이 남는다. 매번 계산하면 그 문제가 존재하지 않는다.

## 결과

### 좋아지는 것
- 일정에 비용과 결제자를 남기면 여행 단위 지출 합계와 "누가 누구에게 얼마"가 바로 나온다.
- 새 개념(참가자 관리, 정산 이력)을 하나도 도입하지 않고 기존 모델에 컬럼 하나만 늘렸다.
- 계산이 순수 함수라 브라우저·DB 없이 검증 가능하다(이번 검증의 절반이 그 경로).
- 부수적으로 `cost_amount` 음수/NaN과, NaN 요청이 422 대신 500이 되던 경로를 막았다.

### 감수하는 것
- **이름이 코드에 하드코딩된다.** 바꾸려면 상수 1줄 + `UPDATE itinerary_item SET paid_by=...`
  + 프론트 선택지 문구를 함께 고쳐야 한다(배포 1회). 2인 고정이라는 전제에서 나온 의도된 비용이다.
- **참가자를 3명으로 늘리면 정산 계산을 다시 설계해야 한다.** `transfer`가 `null`이 되어 즉시
  드러나지만, 그때는 이 ADR을 대체하는 새 ADR이 필요하다.
- **환율 변환이 없어 통화가 섞이면 일부 지출이 정산에서 빠진다.** 경고 플래그로 알릴 뿐이다.
- **결제자별 "무엇을 샀는지" 목록은 응답에 없다.** 합계와 건수만 준다 — 항목 목록은 이미 Day별
  일정 조회로 볼 수 있고, 정산 응답이 트립 전체 항목을 복제할 이유가 없다. 필요해지면 추가한다.
- **동시 수정 경합은 다루지 않는다.** 읽기 전용 계산이라 최악의 경우 "방금 상대가 넣은 지출이
  아직 안 보임"이며, 새로고침하면 맞는다.
- **에러 `detail`이 영어다** — ADR-0002/0003/0004의 계약 언어 정책 그대로. 단, `paid_by` 422
  메시지에는 허용값("희경", "재승")이 그대로 들어간다(값 자체는 한국어).

## 기각한 대안

- **`Participant` 테이블 + 참가자 CRUD API/화면** — 위 표 참고. 사용자가 명시적으로 필요 없다고 했다.
- **`paid_by`를 `Settings`(환경변수)로** — 배포 환경마다 달라질 값이 아니고, 어긋나면 한쪽에서만
  422가 난다. 이름 변경 시 어차피 DB `UPDATE`가 필요해 "env 한 줄" 이점이 성립하지 않는다.
- **`paid_by_index: int`(0/1)** — DB를 직접 볼 때 의미를 읽을 수 없고, 상수 순서를 바꾸면 기존
  데이터 의미가 조용히 뒤집힌다.
- **지출을 `ItineraryItem`과 별개의 `Expense` 테이블로 분리** — "숙소비 12만원"처럼 일정과 1:1이
  아닌 지출(항공권, 환전 수수료)을 담을 수 있다는 장점이 있지만, 그런 지출을 입력할 화면이 없고
  기존 `cost_amount` 컬럼과 두 갈래가 된다("이 여행의 지출"을 두 곳에서 합산해야 함). 일정과 무관한
  지출이 실제로 필요해지면 그때 별도 테이블로 도입하는 게 낫다 — 지금은 `ItineraryItem` 하나가
  "그 날 그 장소에서 쓴 돈"을 자연스럽게 표현한다.
- **정산 결과 저장 + "정산 완료" 상태** — 요구에 없고, 무효화 관리 비용만 생긴다.
- **최소 송금 횟수 알고리즘(그래프 정산)** — 2명에게는 항상 송금 1회다. 3명 이상에서만 의미가 있다.
- **환율 변환(외부 API)** — 명백한 과설계. 키/비용/무료 티어 한도 + "어느 시점 환율" 문제.
- **`cost_amount`를 정수 최소단위/Decimal로 변경** — 위 근거 참고. 규모 대비 이득 없음.
- **`paid_by`에 DB CHECK 제약** — 이름 변경이 마이그레이션 사안이 된다. 도메인 불변식이 아니다.
