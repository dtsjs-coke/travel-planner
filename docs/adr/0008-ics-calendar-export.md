# ADR-0008: 캘린더 내보내기(ICS) — 이벤트 표현, 시간대, UID, 생성 방식

- **날짜**: 2026-09-11
- **상태**: Accepted
- **작성**: senior-dev (오케스트레이터 위임)
- **관계**: 스키마 변경 없음. 기존 `Day.date` / `ItineraryItem.{position, title, start_time,
  end_time, address, lat, lng, notes, url, updated_at}`를 **읽기만** 한다. 이 앱의 데이터를
  처음으로 **외부 시스템(구글 캘린더)이 소유하는 사본**으로 내보내는 결정이다 — 그래서
  "다시 내보냈을 때 어떻게 되는가"가 이 ADR의 중심 질문이다.

## 배경

M7 Backlog Tier 2의 **"캘린더 내보내기 (ICS → 구글 캘린더)"**. 여행 일정을 `.ics` 파일로
받아 구글 캘린더 등에 가져올 수 있게 한다.

코드 조사 결과 두 가지가 이 설계를 결정했다.

**1. 지금 저장된 일정에는 시간이 없다.** `ItineraryItem`에 `start_time`/`end_time` 컬럼과
pydantic 필드가 M1부터 있고 POST/PATCH가 저장도 하지만, **그 값을 입력하는 UI가 어디에도
없다**(`AddItemModal.tsx`/`ItineraryItemCard.tsx` 모두 없음 — 프론트 전체에서 `start_time`이
등장하는 곳은 `api/items.ts`와 `types/models.ts`의 타입 선언뿐). `cost_amount`가 ADR-0006
직전까지 전부 NULL이었던 것과 같은 상태다. 즉 **오늘 내보내면 100% 시간 없는 일정**이고,
"시간이 있으면 그 시각을 쓴다"는 경로는 미래를 위한 것이다.

**2. 여행지 시간대를 저장하는 곳이 없다.** `Trip`에는 `name`/`destination`/`start_date`/
`end_date`/`currency`뿐이다. `destination`은 자유 텍스트라 시간대로 쓸 수 없다.

## 결정

### 1. VEVENT는 **일정(ItineraryItem) 하나당 하나**. 시간이 없으면 종일 이벤트

| | (a) 일정 1건 = 이벤트 1개 **(채택)** | (b) Day 1개 = 이벤트 1개, 설명에 목록 | (c) 09:00부터 1시간씩 자동 배정 |
|---|---|---|---|
| LOCATION/GEO | 일정마다 정확히 실림 | **불가능**(VEVENT에 LOCATION은 1개) | 실림 |
| 시간 있는 일정 | 그 시각 그대로 | 설명 텍스트에 묻힘 | 충돌 처리 필요 |
| 같은 날 표시 | 종일 이벤트가 여러 개 쌓임 | 깔끔 | 깔끔 |
| 사실성 | 있는 것만 말함 | 있는 것만 말함 | **없는 정보를 지어냄** |

- **(c) 기각** — 09:00~10:00 "성산일출봉"은 사용자가 입력한 적 없는 값인데 캘린더에서는
  입력값과 구분되지 않는다. 이 저장소가 반복해서 지켜온 기준("모호한 판단은 사람이",
  ADR-0001 / ADR-0006의 미지정 지출)과 정면으로 어긋난다. 게다가 나중에 시간 입력 UI가
  생기면 "가짜 09:00"과 "진짜 09:00"이 이미 캘린더에 섞여 있어 되돌릴 수도 없다.
- **(b) 기각** — 가장 큰 손실은 **LOCATION/GEO**다. 이 앱은 구글 Places로 `place_id`/좌표/
  주소를 애써 저장하는데(M4~M5의 핵심), 캘린더 이벤트에서 주소를 눌러 길찾기로 넘어가는 것이
  내보내기의 실질적 가치다. VEVENT는 LOCATION을 하나만 가지므로 Day를 묶는 순간 그 가치가
  통째로 사라진다. 시간이 있는 일정을 설명 텍스트 속 문자열로 강등시키는 것도 퇴보다.
- **(a) 채택** — DB 행과 캘린더 이벤트가 1:1이라 UID 설계(아래 3번)가 자명해지고, 각 일정이
  자기 주소/좌표/메모/링크를 그대로 가진다.

규칙:

- `start_time`이 있으면 **시각 있는 이벤트**. `DTEND`는 `end_time`이 있고 `start_time`보다
  늦으면 그 값, 아니면 `start_time + 1시간`.
- `start_time`이 없으면 **종일 이벤트**: `DTSTART;VALUE=DATE:YYYYMMDD` +
  `DTEND;VALUE=DATE:<다음 날>`(RFC 5545에서 DTEND는 **비포함** 경계라 같은 날짜를 넣으면
  길이 0이 된다).
- `end_time`만 있고 `start_time`이 없으면 종일로 본다(시작 없는 종료는 표현할 수 없다).

### 2. SUMMARY 앞에 그날의 순번을 붙인다 (`"1. 성산일출봉"`)

(a)를 택하면 대가가 하나 생긴다: **같은 날짜의 종일 이벤트 사이에는 캘린더가 보장하는
표시 순서가 없다.** 구글 캘린더는 대체로 제목순으로 늘어놓는다. 그런데 이 앱에서 그날의
방문 **순서(`position`)는 데이터의 의미 자체**다 — dnd-kit 드래그 정렬(M3)과 Day 간 이동
(ADR-0004/0005)이 전부 그 순서를 다루기 위해 존재한다. 내보내면서 그걸 잃으면 안 된다.

ICS에는 "이 이벤트들의 순서" 같은 속성이 없으므로, 순서를 **사람이 읽는 텍스트로** 옮긴다.
시각이 있는 일정에도 똑같이 붙인다 — 한 Day 안에서 번호가 1,2,3으로 이어지는 편이,
시각 유무에 따라 번호가 나타났다 사라지는 것보다 읽기 쉽다. 번호는 Day마다 1부터 다시 센다.

되돌리기 비용이 거의 없는 선택이다(포매터 한 줄).

### 3. 시각은 **floating local time** — `Z`도 `TZID`도 붙이지 않는다

```
DTSTART:20261101T123000        ← 채택 (시간대 정보 없음)
DTSTART;TZID=Asia/Seoul:...    ← 기각
DTSTART:20261101T033000Z       ← 기각
```

`Trip`에 시간대 필드가 없고, 이 앱은 **해외 여행을 계획하는 앱**이다. `Asia/Seoul`을
하드코딩하면 도쿄 여행에서 조용히 1시간, 방콕이면 2시간 어긋난다 — 그리고 그건 사용자가
현지에서 일정을 놓친 뒤에야 알게 되는 종류의 오류다. UTC는 더 나쁘다(입력한 적 없는 변환을
서버가 수행한다).

RFC 5545의 floating time은 "**읽는 쪽의 로컬 시간대에서 적힌 그대로의 시각**"이다. 사용자가
"12:30 점심"이라고 적었다면 그건 현지 시각 12:30이라는 뜻이므로, 의미상 가장 가깝다.

**감수하는 한계**: 구글 캘린더는 가져오기 시점에 floating time을 그 캘린더의 기본
시간대(거의 확실히 `Asia/Seoul`)로 고정해버린다. 즉 현재 구현에서 해외 여행의 시각 일정은
결국 KST로 굳는다 — **다만 이건 `TZID=Asia/Seoul`을 박아도 똑같은 결과**이고, floating 쪽이
"우리는 시간대를 모른다"는 사실을 정직하게 표현하며 VTIMEZONE 블록도 필요 없다. 시간대가
실제로 문제가 되려면 먼저 **시간 입력 UI**와 **`Trip.timezone` 필드**가 생겨야 하고, 그때는
이 ADR을 대체하는 새 ADR이 필요하다.

종일 이벤트(`VALUE=DATE`)에는 시간대 개념이 아예 없다. **지금 저장된 모든 일정이 여기
해당하므로, 오늘 시점에서 이 결정은 실질적으로 무해하다.**

### 4. UID는 `item-{item_id}@travel-planner-dtsjs.vercel.app` — DB id 기반 고정값

```
UID:item-42@travel-planner-dtsjs.vercel.app
```

같은 일정은 언제 몇 번을 다시 내보내도 같은 UID다. 구글 캘린더를 포함한 대부분의 클라이언트는
가져오기 시 UID로 기존 이벤트를 찾아 **갱신**하므로, 일정을 고치고 다시 받아 가져와도
중복 이벤트가 생기지 않는다. 오른쪽(도메인)은 RFC 5545가 요구하는 전역 유일성을 위해
우리가 소유한 배포 도메인을 쓴다.

`LAST-MODIFIED`에 `updated_at`을, `DTSTAMP`에 생성 시각을 싣는다.

**`SEQUENCE`는 넣지 않는다(= 기본값 0).** 이 모델에는 리비전 카운터가 없다. `updated_at`을
epoch 초로 변환해 넣는 방법을 검토했지만, RFC 5545의 INTEGER 상한(2,147,483,647)을 2038년에
넘어 **그때부터 조용히 깨지는** 값이 된다. 리비전 번호가 실제로 필요해지면 컬럼을 추가하는 게
맞지, 타임스탬프를 정수로 우겨넣을 자리가 아니다.

**감수하는 한계**: 앱에서 일정을 **삭제**해도 이미 가져간 캘린더의 이벤트는 사라지지 않는다.
파일에 "없음"은 "지워라"가 아니기 때문이다(ICS 가져오기 전반의 성질). 지우려면 `METHOD:CANCEL`
+ `STATUS:CANCELLED` 이벤트를 따로 보내야 하는데, 그러려면 "지난번에 무엇을 내보냈는지"를
서버가 기억해야 한다(내보내기 이력 테이블). 요구에 없고, 되돌리기 비용이 큰 상태를 늘린다.

### 5. `GET /api/trips/{trip_id}/export.ics` — 저장 없이 매 요청 생성

```
GET /api/trips/{trip_id}/export.ics
→ 200  text/calendar; charset=utf-8
       Content-Disposition: attachment; filename="trip-3.ics"; filename*=UTF-8''%EC%A0%9C%EC%A3%BC.ics
→ 401  (라우터 전체가 require_session)
→ 404  {"detail": "Trip not found"}
```

파일을 어디에도 저장하지 않는다(정산을 저장하지 않는 것과 같은 이유 — 원본이 바뀌면 즉시
낡는 파생물이다). 없는 여행은 404이고, **일정이 하나도 없는 여행은 200 + VEVENT 0개**다.

한글 여행 이름은 `filename=`에 담을 수 없으므로(HTTP 헤더는 ASCII) RFC 6266/5987의
`filename*=UTF-8''...`로 보내고, 못 읽는 클라이언트를 위해 `filename="trip-{id}.ics"` ASCII
대체값을 함께 준다.

**프론트는 `fetch`+blob이 아니라 평범한 `<a href>` 링크로 받는다.** 근거:

- **운영**: `VITE_API_BASE_URL`이 빈 문자열이고 Vercel `vercel.json`의 `/api/*` rewrite가
  Render로 프록시하므로, 브라우저 입장에서 `/api/trips/3/export.ics`는 **same-origin GET**이다.
  same-origin 요청에는 SameSite 정책과 무관하게 쿠키가 실린다.
- **로컬(5173 → 8000)**: 크로스 오리진이지만 쿠키가 `SameSite=Lax`이고, 링크 클릭은 최상위
  내비게이션 GET이라 Lax 쿠키가 실린다.
- blob 방식은 파일 전체를 메모리에 올리고 `createObjectURL`/`revokeObjectURL` 수명을 관리해야
  하며, **모바일 브라우저에서 blob 다운로드가 OS 캘린더 앱으로 넘어가지 않는 경우가 있다**.
  이 앱은 모바일 사용 비중이 크다(연속 스크롤 뷰를 따로 만들 정도로). `Content-Disposition`이
  붙은 평범한 링크는 그 경로가 가장 잘 동작한다.

**감수하는 한계**: 링크 방식이라 세션이 만료된 상태로 누르면 화면 대신 `{"detail":"Not
authenticated"}` JSON이 보인다. 세션이 90일이고 그 상태면 페이지 자체가 이미 동작하지 않는
상황이라 실제 노출 가능성이 낮아, 이 엣지 때문에 blob 방식의 비용을 지불하지 않는다.

### 6. ICS 생성은 표준 라이브러리로 직접 — `icalendar` 의존성을 추가하지 않는다

`requirements.txt`는 9줄이고 전부 "없으면 앱이 안 도는 것"들이다. 우리가 만드는 ICS는
VCALENDAR 1개 + VEVENT N개, 속성 10종이며 `RRULE`/`VALARM`/`VTIMEZONE`/참석자/파싱이 전혀
없다. 어려운 건 문법이 아니라 **세 가지 세부 규칙**인데, 전부 순수 함수로 짜고 검증할 수 있다.

1. **CRLF 줄바꿈** — LF만 쓰면 일부 파서가 파일 전체를 한 줄로 본다.
2. **TEXT 이스케이프** (`\` `;` `,` 줄바꿈) — 백슬래시를 **가장 먼저** 치환해야 한다.
   "성산일출봉, 아침" 같은 제목 하나가 이스케이프 없이 나가면 속성이 두 값으로 쪼개져
   이벤트가 깨진다. 반대로 `GEO`(float 쌍)와 `URL`(URI)은 TEXT가 아니라 **이스케이프하면 안
   된다** — 라이브러리 없이 짤 때 가장 틀리기 쉬운 지점이라 속성별로 명시했다.
3. **75옥텟 줄 접기(folding)** — **넣기로 했다.** 현대 캘린더 앱 대부분은 없어도 파싱하지만,
   한글은 UTF-8에서 3옥텟이라 주소/메모가 25자만 넘어도 초과한다. 즉 이 앱에서는 예외가
   아니라 **기본 상태**다. 구현 비용은 15줄이고, 핵심은 "문자 수가 아니라 옥텟을 세되 멀티바이트
   문자 중간에서 자르지 않는다"는 것 하나다. 넣지 않으면 관대하지 않은 파서 하나를 만났을 때
   원인을 찾기 매우 어렵다.

`icalendar`는 `python-dateutil`/`tzdata`까지 끌고 오면서 위 세 가지를 대신 해줄 뿐,
"무엇을 이벤트로 만들 것인가"(이 ADR의 1~4번)는 여전히 우리 몫이다. 이 규모에서는 의존성이
비용이다.

### 7. 라우터는 `app/routers/export.py`로 분리

`trips.py`는 트립 CRUD + Day 동기화만으로 이미 크고, 내보내기는 `Day`/`ItineraryItem`을 읽어
**다른 포맷으로 렌더링**하는 별개 관심사다(`checklist.py`/`settlement.py`를 뺀 것과 같은 기준).
Day가 최대 180개일 수 있으므로 일정은 Day별 N+1이 아니라 `day_id IN (...)` 한 번에 읽는다.

## 근거

### 왜 빈 여행에 404/422가 아니라 빈 달력을 주는가

"일정이 없다"는 오류가 아니라 정상 상태다(여행을 막 만든 직후가 그렇다). 버튼을 눌렀을 때
에러가 나면 사용자는 자기가 뭘 잘못했는지 찾게 되지만, 빈 달력이 받아지면 "아직 일정을 안
넣었구나"가 바로 읽힌다. `compute_settlement`가 지출 0건에 404가 아니라 합계 0을 주는 것과
같은 기준이다.

엄밀히 말하면 RFC 5545 §3.6은 VCALENDAR가 최소 1개의 컴포넌트를 포함하길 요구하므로 이건
표준에서 살짝 벗어난다. 대안은 (i) 에러를 내거나 (ii) 더미 이벤트를 하나 지어내는 것인데,
(i)은 위 이유로 기각, (ii)는 없는 데이터를 만드는 것이라 결정 1번의 (c)를 기각한 이유와 같다.
**의도적으로 표준보다 사용성을 택했고, 여기에 기록해 둔다.**

### 왜 DESCRIPTION에 비용/결제자를 넣지 않는가

`cost_amount`/`paid_by`를 설명에 적을 수는 있지만, 그 정보의 자리는 정산 화면(ADR-0006/0007)이다.
캘린더로 나가는 순간 그 값은 **갱신되지 않는 사본**이 되고, 결제자는 슬롯 키라 이름을 함께
복사해야 하는데 그건 ADR-0007이 명시적으로 금지한 것이다("이름을 오래 사는 캐시에 복사하지
않는다" — 캘린더는 우리가 무효화할 수 없는 가장 오래 사는 캐시다). DESCRIPTION에는 사용자가
직접 쓴 `notes`만 싣는다.

### 왜 새 DB 필드가 하나도 없는가

이 기능은 **순수 변환**이다. 내보내기 이력을 저장하면 "언제 무효화하는가"(일정 수정/삭제/
Day 이동/트립 삭제)가 따라오고, 그건 4번에서 기각한 CANCEL 기능이 실제로 필요해질 때
한꺼번에 설계할 문제다.

## 결과

### 좋아지는 것
- 여행 일정을 구글 캘린더/애플 캘린더로 가져가서 평소 쓰는 캘린더 위에서 볼 수 있다.
- 일정마다 주소/좌표가 실려 캘린더에서 바로 길찾기로 넘어간다.
- UID가 고정이라 일정을 고친 뒤 다시 받아 가져와도 **중복이 아니라 갱신**이다.
- DB 스키마 변경과 마이그레이션이 **없다** → 운영 Neon에 적용할 것이 없고, 백엔드 배포만으로
  반영된다(ADR-0004와 같은 성질).
- 의존성이 늘지 않았다.

### 감수하는 것
- **앱에서 지운 일정이 캘린더에서는 안 지워진다** (4번).
- **해외 여행의 시각 일정은 가져오는 캘린더의 시간대로 굳는다** (3번). 지금은 시각을 입력할
  UI 자체가 없어 실제 영향이 없다.
- **같은 날 종일 이벤트가 여러 개 쌓인다.** 월간 보기에서는 "+N개"로 접힌다. 제목 앞 번호로
  순서는 읽을 수 있게 했다.
- **빈 달력은 RFC 5545 §3.6에서 살짝 벗어난다** (위 근거 참고).
- **세션 만료 시 링크가 JSON 에러를 보여준다** (5번).
- **에러 `detail`이 영어다** — ADR-0002~0006의 계약 언어 정책 그대로.

## 기각한 대안

- **Day 1개 = 이벤트 1개, DESCRIPTION에 그날 일정 나열** — LOCATION/GEO를 통째로 버린다.
  결정 1번 표 참고.
- **시간 없는 일정에 09:00부터 1시간씩 자동 배정** — 사용자가 입력한 적 없는 시각을 지어내고,
  나중에 진짜 시각과 구분할 수 없게 된다.
- **`TZID=Asia/Seoul` 하드코딩 / UTC 변환** — 해외 여행에서 틀린다. floating과 결과가 같거나
  나쁘면서 VTIMEZONE 블록만 늘어난다.
- **`SEQUENCE`에 `updated_at`의 epoch 초** — INTEGER 상한을 2038년에 넘어 조용히 깨진다.
- **`icalendar` 라이브러리 도입** — 의존성 3개를 늘려 얻는 게 escape/fold/CRLF 15줄뿐이다.
- **`fetch` + Blob 다운로드** — 모바일에서 OS 캘린더로 넘기는 경로가 불안정하고, 메모리에
  올리고 objectURL 수명을 관리해야 한다. 세션 쿠키는 링크로도 실린다.
- **`.ics` 파일을 서버에 저장 / 구독 URL(webcal) 제공** — 구독은 "갱신이 자동"이라는 큰 장점이
  있지만, 토큰 기반 무인증 접근 경로(구글 서버가 세션 쿠키 없이 주기적으로 긁는다)를 새로
  만들어야 한다. 공유 비밀번호 하나로 보호되는 이 앱에 **인증 우회 URL**을 추가하는 결정이라
  별도 판단이 필요하고, 이번 요구("파일로 내보내기")를 넘어선다.
- **삭제된 일정에 `METHOD:CANCEL` 전송** — 내보내기 이력 테이블이 필요하다. 요구에 없다.
- **비용/결제자를 DESCRIPTION에 포함** — ADR-0007의 "이름을 오래 사는 캐시에 복사하지 않는다"에
  어긋난다.
