# ADR-0015: 여행 가이드 페이지 — "필수 방문"은 일정 항목의 불리언 컬럼, "팁/추천 메모"는 Trip의 텍스트 컬럼

- **날짜**: 2026-10-21
- **상태**: Accepted
- **작성**: senior-dev (오케스트레이터 위임)
- **관계**: [ADR-0011](0011-itinerary-place-details.md)의 "상세보기 필드는 일정 행의 nullable 컬럼 + 입력 검증으로만
  길이 상한"을 그대로 따른다. [ADR-0003](0003-trip-checklist-model.md)이 기각했던 `Trip.memo` 단일 텍스트 컬럼은
  **용도가 달라서**(체크 토글이 필요 없는 읽을거리) 이번에는 채택한다 — 그 ADR을 뒤집는 것이 아니다(아래 근거 참고).
  [ADR-0007](0007-runtime-participant-names.md)의 "두 사람이 공유하는 값은 DB에" 원칙을 따른다.
  [ADR-0014](0014-travel-toolbox-free-apis-and-paid-feature-toggle.md)와 무관하게 **외부 API/과금 경로가 하나도 늘지 않는다**.

## 배경

사용자가 바탕화면의 단일 정적 HTML(포르투갈 8박9일 인터랙티브 플래너, Leaflet)의 **구조**를 이 앱에 반영해 달라고
했다. 확정된 범위:

1. 기존 Day 편집 화면은 그대로 두고, 여행별 **읽기 전용 "여행 가이드" 페이지**(`/trips/:tripId/guide`)를 추가한다.
   Day 칩 + 장소 카드 리스트(좌) / 경로선이 그려진 지도(우), 일정 요약표 모달, 필수 명소만 필터, 지도 레이어
   전환(일반/위성), 여행 팁 모달.
2. 대부분은 기존 데이터(Trip/Day/ItineraryItem의 좌표·시간·카테고리·지역·메모·Day 라벨)로 구성할 수 있지만,
   원본 HTML의 두 가지는 지금 데이터 모델에 대응하는 값이 없다:
   - 장소별 **"필수 방문(Must-Visit)"** 표시 — 큰 마커/별표/빨간 테두리, "필수 명소만" 필터의 기준.
   - 여행 전체에 대한 **"팁/추천 메모"** — 원본의 팁 모달("칼사다 돌길은 비 오면 미끄러움", "사전 예약 필수 스팟" 등).
3. 사용자 조건: **희경·재승이 공유해서 보는 값**이어야 하고(브라우저 저장 X), DB 추가는 **이 두 칸까지만**.
   Day별 제목/설명 컬럼 같은 확장은 이번 범위가 아니다.

스키마 변경 + 운영 Neon 마이그레이션이 들어가는 결정이라 근거를 남긴다.

## 결정

### 1. `itinerary_item.is_must_visit` — `bool NOT NULL DEFAULT false`

| 항목 | 값 |
|---|---|
| 모델 | `ItineraryItem.is_must_visit: bool = False` |
| DB | `BOOLEAN NOT NULL`, `server_default=sa.text('false')` (기존 행은 전부 false) |
| 생성 | `ItineraryItemCreate.is_must_visit: bool = False` — 생략 가능, `null`은 타입 자체가 422 |
| 수정 | `ItineraryItemUpdate.is_must_visit: bool \| None = None` — 생략 = 안 바꿈, **명시적 `null`은 422** |
| 응답 | `ItineraryItemRead.is_must_visit: bool` (목록/생성/수정/이동/재정렬 응답 전부) |

- 이름은 기존 `ChecklistItem.is_checked`와 같은 `is_` 접두 불리언 관례를 따른다.
- 명시적 `null` 거부는 `ChecklistItemUpdate.is_checked`와 **같은 방어**다 — NOT NULL 컬럼에 `setattr(None)`이
  이어져 500이 나던 `title` 버그(2026-09-08)의 재발 방지 패턴.
- 토글 전용 엔드포인트는 만들지 않는다. 기존 `PATCH /api/items/{id}`에 필드만 얹는다(ADR-0003 결정 6과 같은 이유:
  `PATCH {"is_must_visit": true}`는 멱등하고, `POST .../toggle`은 재시도/더블탭에 상태가 두 번 뒤집힌다).

### 2. `trip.travel_tips` — `str | None` (nullable 텍스트, 길이 상한 5000자는 입력 검증으로만)

| 항목 | 값 |
|---|---|
| 모델 | `Trip.travel_tips: str \| None = None` |
| DB | `VARCHAR`(`AutoString`, 길이 무제한) nullable — 기존 행은 NULL(= 아직 안 적음), 백필 없음 |
| 수정 | `TripUpdate.travel_tips` — `_normalize_optional_text` 재사용: 양끝 trim, **줄바꿈 보존**, 빈 문자열/공백/`null` = 지움, 5000자 초과 422 |
| 생성 | `TripCreate`에는 **넣지 않는다**(여행 생성 화면에 입력칸이 없다. POST에 실어 보내면 pydantic 기본 설정상 조용히 무시) |
| 응답 | `TripRead.travel_tips` — 상속 구조상 `GET /api/trips`(목록), `GET /api/trips/{id}`, `POST`, `PATCH` 응답 전부에 실린다 |

- 상한 5000자(`MAX_TRIP_TRAVEL_TIPS_LENGTH`): 일정 하나의 메모(`MAX_ITEM_NOTES_LENGTH` 2000자)보다 넉넉하다 —
  여행 전체에 대한 여러 단락짜리 글이기 때문. 원본 HTML의 팁 모달 본문이 태그를 걷어낸 텍스트 기준 약 1300자라 4배 가까운 여유.
  무료 티어 DB에 수 MB짜리 붙여넣기가 들어오는 것을 막는 가드레일이며, 목록 응답에도 실리므로 곧 "여행 1건당
  목록 응답 증가분"의 상한이기도 하다.
- DB 컬럼 길이 제약은 걸지 않는다(ADR-0003 결정 4, ADR-0011과 같은 정책 — 상한은 UX 판단이라 바꿀 때 마이그레이션이
  필요하면 안 된다).
- 날짜 PATCH와 같은 요청에 섞여 와도 된다. 날짜 검증이 실패하면(422) 메모도 함께 저장되지 않는다(기존
  "검증 먼저, setattr 나중" 순서 그대로). 메모만 바꾸는 PATCH는 Day 동기화를 건드리지 않는다(날짜 필드가 없으므로).

### 3. 편집 진입점 — "가이드 페이지는 읽기 전용"의 유일한 예외는 팁 메모

- **필수 방문 토글은 Day 편집 화면의 기존 `ItineraryItemDetailModal`에** 둔다. 일정 항목의 속성을 고치는 곳이 이미
  거기이고, 가이드 페이지에 토글을 두면 "보기 전용 화면에서 실수로 데이터가 바뀌는" 경로가 생긴다.
- **팁 메모 편집은 가이드 페이지의 팁 모달 안 "편집" 버튼**으로 둔다. 이 값은 가이드 페이지에서만 보이는 값이라
  다른 화면에 편집칸을 두면 "어디서 보이는지 모르는 값을 고치는" UI가 된다. 모달 안에서 명시적으로 편집 모드로
  들어가야 하므로 읽기 전용 원칙의 의도(실수 방지)는 유지된다.

### 4. 배포 순서

마이그레이션 `b7d3e9a41c06`은 **추가 전용**이라 Render Start Command(`alembic upgrade head && uvicorn ...`,
`docs/infra/render.md`)로 자동 적용돼도 안전하다 — 마이그레이션 직후 아직 옛 코드가 돌아도 옛 INSERT는 새 컬럼을
생략하고 `server_default`/NULL로 채워진다. 단, **프론트가 백엔드보다 먼저 배포되면** 팁 저장 PATCH가 옛 백엔드에서
조용히 무시돼(422 아님) "저장했는데 비어 있는" 상태가 보일 수 있다 → 백엔드와 같은 push로, 혹은 백엔드를 먼저 내보낸다.

## 근거

### 왜 브라우저 저장(localStorage)이 아닌가 — 기각

필수 방문/팁은 **여행 계획 데이터**다. 희경이 표시한 "필수 방문"이 재승 폰에서 안 보이면 이 기능은 목적을 잃는다.
localStorage는 기기·브라우저마다 따로라 두 사람 사이 공유가 원천적으로 불가능하고, 같은 사람도 PC↔폰에서 값이
갈린다. 이 앱이 참가자 이름을 DB(`app_settings`)로 옮긴 이유(ADR-0007)와 정확히 같다. 사용자도 "공유" 조건을
명시했다. (반면 **지도 레이어 선택**, 필수 명소만 필터 on/off 같은 "보기 설정"은 개인 화면 상태라 저장하지 않는다 —
명세 참고.)

### 왜 필수 방문은 컬럼인가 (별도 테이블이 아니라)

| | (a) `itinerary_item.is_must_visit` 컬럼 (채택) | (b) `must_visit(item_id)` 별도 테이블 | (c) 범용 `item_tag(item_id, tag)` 테이블 |
|---|---|---|---|
| 조회 | 기존 `GET /api/days/{id}/items`에 그대로 실림 | 조인 or 별도 API + 프론트 병합 | 조인 or 별도 API + 프론트 병합 |
| 수정 | 기존 PATCH에 필드 1개 | INSERT/DELETE 엔드포인트 2개 | 태그 CRUD 엔드포인트 |
| 이동/삭제 | 행과 함께 따라감(아무 처리 불필요) | FK CASCADE로 따라감 | FK CASCADE로 따라감 |
| 프론트 캐시 | 기존 `['days', id, 'items']` 하나 | 쿼리 키 하나 추가 + 무효화 동기화 | 동일 + 태그 이름 관리 |

- 값이 항목당 **정확히 하나의 참/거짓**이고 항목과 생명주기가 같다(이동하면 따라가고 지우면 사라진다).
  이건 컬럼의 정의 그 자체다.
- (b)는 "있으면 true"인 1:0..1 관계를 테이블로 표현하는 것뿐이라 얻는 것 없이 엔드포인트·쿼리 키·캐시 동기화만 늘어난다.
- (c) 범용 태그는 "나중에 '예약 필수', '비 오면 패스' 같은 태그가 늘면?"을 대비한 일반화인데, 지금 요구는 하나뿐이고
  사용자가 범위를 이 두 칸으로 못박았다. **나중에 태그가 정말 필요해지면** 그때 `item_tag` 테이블을 만들고
  `is_must_visit=true` 행을 `tag='must_visit'`로 옮기는 마이그레이션 하나로 이행할 수 있다(데이터 손실 없음).
  지금 미리 일반화하면 "태그 이름 목록 관리 UI"까지 따라온다.

### 왜 팁은 Trip의 텍스트 컬럼인가 (별도 테이블/체크리스트 재사용이 아니라)

| | (a) `trip.travel_tips` 텍스트 1칸 (채택) | (b) `trip_tip(trip_id, title, body, position)` 테이블 | (c) 기존 `checklist_item` 재사용 |
|---|---|---|---|
| 원본 HTML과의 대응 | 모달 하나에 자유 서식 글 — 그대로 | 카드 단위로 쪼갠 구조 | 체크박스 목록 — 성격이 다름 |
| 스키마/API | 컬럼 1개 + 기존 PATCH | 새 테이블 + CRUD 4개 + 정렬 | 0 |
| 편집 UX | textarea 하나 | 항목 추가/삭제/순서 UI | 기존 체크리스트 UI |

- **ADR-0003이 `Trip.memo`를 기각한 이유는 "체크 토글이 필요한 준비물 목록"이었기 때문**이다. 팁은 정반대다 —
  체크할 대상이 아니라 **읽을거리**이고, 순서·서식을 쓴 사람이 정하는 한 덩어리 글이다. 그 ADR이 지적한
  "체크 상태를 텍스트 안에 인코딩하는 파싱 부담"이 여기엔 없다.
- (c) 체크리스트 재사용은 스키마 변경 0이라 가장 싸 보이지만, "여권 챙기기 ☑"와 "칼사다 돌길 미끄러움"이 같은
  목록에 섞이고 200자 상한(ADR-0003)이라 단락 글을 못 담는다. 기능 의미가 오염된다.
- (b)는 원본처럼 팁을 카드별로 예쁘게 나누는 데는 유리하지만, 두 사람이 쓰는 앱에서 팁 카드의 추가/삭제/정렬 UI는
  얻는 가치에 비해 비싸고 사용자가 정한 범위("텍스트 1칸")를 넘는다. 줄바꿈이 보존되므로 "■ 이동 팁" 같은
  소제목을 텍스트로 적는 것만으로 원본 모달의 정보 구조는 충분히 재현된다.

### 왜 Trip이 아니라 Day에 메모를 두지 않는가

원본 HTML의 Day 메타 카드(제목/설명)는 이번 범위에서 **기존 `Day.label` + 날짜 + 그날 항목들의 `region_name`
요약**으로 구성한다(사용자 확정). 팁은 여행 전체에 대한 글이라 Day에 매달 이유가 없고, Day에 붙이면 기간 PATCH로
그 Day가 범위 밖이 될 때 사라지는 문제(ADR-0003과 같은 이유)가 생긴다.

## 결과

### 좋아지는 것
- 원본 HTML의 핵심 구조(필수 방문 강조/필터, 팁 모달)를 **공유 데이터로** 재현할 수 있다.
- 두 값 모두 기존 조회/수정 API에 필드만 얹었으므로 프론트의 기존 react-query 캐시(`['trips', id]`,
  `['days', id, 'items']`)를 그대로 쓴다. Day 편집 화면에서 필수 방문을 켜면 가이드 페이지가 같은 캐시로 즉시 반영된다.
- 외부 API 호출·과금 경로가 하나도 늘지 않는다(지도 표시는 기존 Maps JS 로드 그대로).

### 감수하는 것
- **팁 메모는 last-write-wins다.** 두 사람이 동시에 편집하면 나중에 저장한 쪽이 앞의 내용을 통째로 덮는다(텍스트
  한 덩어리라 부분 병합이 없다). 두 사람이 같은 순간에 같은 여행의 팁을 고칠 확률이 낮고, 낙관적 잠금(`updated_at`
  비교 → 409)은 이번 범위 대비 과하다. 완화책으로 프론트는 **편집 모드에 들어갈 때 최신 값을 다시 받아** 초안을
  채운다(명세 참고). 실제로 덮어쓰기 사고가 보고되면 `TripUpdate`에 `expected_updated_at`을 추가하는 방식으로 확장한다.
- **`GET /api/trips` 목록 응답이 여행당 최대 5000자 커진다.** 여행이 수십 건 수준인 2인용 앱이라 무시할 만하다.
  목록에서 빼려면 `TripRead`/`TripDetailRead` 분리가 필요한데, 지금은 그 복잡도가 이득보다 크다.
- **필수 방문은 "누가 표시했는지"를 남기지 않는다.** 공유 계획의 속성이지 개인 즐겨찾기가 아니다(개인별이 필요하면
  별도 테이블 (b)/(c) 방향 — 지금 요구 아님).
- **운영 Neon에 마이그레이션 `b7d3e9a41c06`이 필요하다** — Render 시작 명령으로 배포 시 자동 적용된다(추가 전용,
  기존 데이터 영향 없음). downgrade는 필수 방문 표시와 팁 본문을 잃는다.

## 기각한 대안

- **브라우저 저장(localStorage/IndexedDB)** — 두 사람 간 공유 불가(위 근거). 사용자 조건 위반.
- **필수 방문 별도 테이블 / 범용 태그 테이블** — 1:0..1 불리언에 테이블은 과설계(위 표). 태그가 실제로 필요해지면 이행 경로가 있다.
- **팁을 별도 `trip_tip` 테이블 / 기존 체크리스트에 섞기** — 각각 범위 초과 / 기능 의미 오염(위 표).
- **`app_settings`(전역 싱글턴)에 팁 저장** — 팁은 여행마다 다르다(포르투갈 팁이 다음 일본 여행에 보이면 안 된다).
- **필수 방문을 `place_category`나 `notes`에 "★" 문자열로 인코딩** — 스키마 변경 0이지만 `place_category`는
  ADR-0013의 숙박 판별 신호라 오염되면 정렬이 틀어지고, 필터는 문자열 파싱에 의존하게 된다.
- **가이드 페이지에서 필수 방문 토글** — 읽기 전용 화면에서 데이터가 바뀌는 경로가 생긴다. 편집은 편집 화면에서.
- **팁 PATCH용 별도 엔드포인트(`PUT /api/trips/{id}/tips`)** — 기존 `PATCH /api/trips/{id}`가 부분 업데이트라 필드 하나로 충분하다.
