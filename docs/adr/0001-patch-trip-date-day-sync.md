# ADR-0001: 여행 기간(PATCH) 수정 시 Day 동기화 방식

- **날짜**: 2026-09-09
- **상태**: Accepted (동시성 관련 보완은 [ADR-0002](0002-day-unique-constraint-and-conflict-handling.md) 참고)
- **작성**: senior-dev (오케스트레이터 위임)

> **후속**: 이 ADR은 동시 요청 경로를 다루지 않았다. 두 사람이 거의 동시에 같은 트립의 기간을 늘리면
> 같은 날짜에 Day가 중복 생성될 수 있다는 점(qa-reviewer 지적)을
> [ADR-0002](0002-day-unique-constraint-and-conflict-handling.md)에서 DB 유니크 제약 +
> 409 변환으로 보완했다. 아래 결정 자체는 그대로 유효하다.

> 참고: 이 ADR 이전(2026-09-08까지)의 아키텍처 결정들은 `docs/PROJECT.md`의
> "Architecture Decisions" 섹션에 인라인으로 기록돼 있다. 이 파일부터는 되돌리기
> 어려운 결정을 `docs/adr/NNNN-*.md`로 분리하고, PROJECT.md에는 요약 + 링크만 남긴다.

## 배경

`POST /api/trips`는 2026-09-07부터 `start_date`+`end_date`를 받으면 같은 트랜잭션에서
그 범위의 Day를 자동 생성한다(PROJECT.md "Day 자동 생성은 별도 bulk 엔드포인트 대신
`POST /api/trips` 안에서 처리"). 그러나 **생성 시점에만** 동작해서,
`PATCH /api/trips/{id}`로 기간을 바꿔도 Day는 늘지도 줄지도 않았다. 임시 조치로 프론트
수정 폼에 "기간을 바꿔도 이미 만들어진 날짜는 유지됩니다" 안내 문구만 넣어둔 상태였다.

이번에 실제 동기화를 구현하면서 결정해야 할 핵심 질문은 **"새 범위 밖으로 밀려난 기존
Day를 어떻게 처리할 것인가"**다. Day는 `ItineraryItem`을 CASCADE로 물고 있어서
(`models.py`의 `ForeignKey("day.id", ondelete="CASCADE")`), Day 하나를 지우면 그날 짜둔
일정이 전부 사라진다. 되돌릴 방법(휴지통, 소프트 삭제)은 이 앱에 없다.

## 결정

**PATCH는 "추가만 하고 절대 삭제하지 않는" 비파괴 연산으로 고정한다. 대신 응답에
"범위 밖이 된 Day + 각 Day의 일정 개수"를 담아, 삭제는 프론트가 사용자 확인을 받은 뒤
기존 `DELETE /api/days/{id}`로 개별 실행한다** (후보 (a) 2단계 방식).

구체적으로:

1. **동기화 트리거**: 요청 본문에 `start_date` 또는 `end_date` 키가 **있을 때만**
   동기화한다(`model_dump(exclude_unset=True)` 기준). 이름만 바꾸는 PATCH는 Day를
   전혀 건드리지 않는다.
2. **두 날짜가 다 있을 때만** 동기화한다. 기존 `validate_date_range()` / `create_trip`의
   "한쪽이라도 없으면 Day를 다루지 않는다" 정책과 같은 기준이다. 날짜를 지우는
   PATCH(`{"start_date": null, "end_date": null}`)도 Day를 지우지 않고 그대로 둔다.
3. **검증 순서는 그대로**: 라우터가 `patch` + DB 기존값을 병합해
   `validate_date_range()`(역전 / `MAX_TRIP_DAYS`=90일 초과 → 422)를 먼저 호출하고,
   **통과한 뒤에** 동기화한다. 기존 흐름에 로직을 끼워넣지 않고 뒤에 이어붙였다.
4. **추가**: 새 범위 안인데 Day가 없는 날짜만 만든다. 계산은 `app/services/trip_days.py`의
   순수 함수 `diff_days_for_range()`가 하며, 내부적으로 기존 `build_days_for_range()`를
   재사용한 뒤 이미 있는 날짜를 걸러낸다(수동 생성 Day와 중복되지 않음).
5. **삭제 금지**: `diff_days_for_range()`는 애초에 "삭제 대상"을 계산하지 않는다.
   범위 밖 Day는 `out_of_range`로 분류해 응답에 싣기만 한다.
6. **응답 계약**: `PATCH /api/trips/{id}`의 `response_model`을 `TripRead` →
   `TripUpdateResult`로 바꾼다. `TripDetailRead`(= `TripRead` + `days`)를 상속한
   **상위집합**이라 기존 필드는 그대로 있고, 다음 두 필드가 추가된다.
   - `added_day_ids: list[int]` — 이번 PATCH로 생성된 Day
   - `out_of_range_days: list[OutOfRangeDayRead]` — `DayRead` + `item_count: int`
7. **총 Day 개수 상한**: 범위 밖 Day를 지우지 않으므로 기간을 통째로 옮기는 PATCH를
   반복하면 Day가 무한정 누적된다(`MAX_TRIP_DAYS`는 한 번의 요청만 막는다). 트립당 총
   Day 수를 `MAX_TRIP_TOTAL_DAYS = MAX_TRIP_DAYS * 2 = 180`으로 제한하고, 초과 시
   롤백 후 422 + "delete out-of-range days first" 안내를 준다.

## 근거

### 왜 (a) 2단계인가

| | (a) 2단계 (응답에 경고 정보 → 별도 삭제 API) | (b) `force=true` 쿼리 파라미터 | (c) 그냥 남겨두고 UI 표시만 |
|---|---|---|---|
| 데이터 손실 위험 | 낮음. PATCH 자체가 절대 삭제하지 않음 | **높음**. 클라이언트가 습관적으로 `force=true`를 붙이면 무경고 삭제 | 없음 |
| 새 엔드포인트 | **불필요** — `DELETE /api/days/{id}` 이미 존재 | 불필요 | 불필요 |
| 프론트가 "무엇을 지울지" 아는 방법 | 서버 응답 그대로 | 사전 조회(dry-run)가 또 필요 → 결국 2회 왕복 | 직접 계산 가능하나 정리 수단 없음 |
| 정리 수단 제공 | 있음 | 있음 | **없음** (범위 밖 Day가 영구히 쌓임) |
| 왕복 횟수 | 1회 (삭제 확정 시 +N) | 1~2회 | 1회 |

- **(b) 기각**: `force=true`의 근본 문제는 "위험한 동작을 안전한 동작과 같은 요청에
  묶는다"는 점이다. 프론트 코드에서 한 번 `force: true`가 상수로 박히면 그 순간부터
  경고 없이 일정이 사라진다. 게다가 사용자에게 "일정 2개가 사라집니다"라고 경고하려면
  **어차피 삭제 전에 무엇이 지워지는지 물어봐야 해서** 왕복 1회의 이점도 사라진다.
  이 앱은 두 사람이 함께 쓰는 공유 여행 계획이라, 한쪽의 실수가 상대방의 작업을 날린다.
- **(c) 기각**: 자동 삭제를 안 한다는 점은 좋으나, 5일 여행을 3일로 줄인 사용자에게
  영원히 정리할 방법을 주지 않는다. "범위 밖"으로 표시만 된 Day가 Day 탭·모바일 연속
  스크롤 목록에 계속 남아 `getDayLabel()`의 Day 순번까지 어긋나게 만든다.
  다만 **(c)는 (a)에서 사용자가 "삭제 안 함"을 선택했을 때의 결과와 동일**하므로,
  (a)를 택하면 (c)는 자동으로 폴백 동작으로 포함된다.
- **(a) 채택**: 서버는 "사실"(무엇이 범위 밖이고, 거기 일정이 몇 개인지)만 알려주고
  파괴적 결정은 사람이 내린다. 삭제 실행은 이미 있고 이미 검증된
  `DELETE /api/days/{id}`를 재사용하므로 새 엔드포인트가 0개다. PROJECT.md의 기존
  결정("나중에 bulk 라우터가 실제로 필요해지면 그때 추가")과도 일관된다 — 지금은
  필요하지 않다.

### 왜 응답을 `TripDetailRead` 상위집합으로 확장했나

기존 프론트 `updateTrip()`은 응답을 `Trip`으로 받는다. 필드를 **추가만** 하면
axios/TS 양쪽에서 기존 코드가 그대로 동작하므로 백엔드/프론트 배포 순서에 의존성이 없다
(2026-09-08 `useQueries` 결정 때와 같은 판단 기준). 별도의
`GET /api/trips/{id}/day-sync-preview` 같은 미리보기 엔드포인트를 만들지 않은 이유도
같다 — 동기화는 어차피 PATCH가 실행돼야 확정되므로, 미리보기는 실제 결과와 어긋날 수
있는 두 번째 진실 소스가 된다.

`days`(동기화 후 전체 목록)를 함께 돌려주는 것은 `POST /api/trips`가 이미
`TripDetailRead`를 주는 것과 같은 패턴이라, 프론트가 PATCH 후 별도 GET을 하지 않아도 된다.

### 왜 "날짜 필드가 요청에 있을 때만" 동기화하나

기간을 안 건드리는 PATCH(이름 변경 등)에서까지 동기화를 돌리면, 이 기능 이전에 만들어져
날짜는 있지만 Day가 없는 여행(현재 dev/운영 데이터에 실제로 존재)이 이름 한 글자 고쳤다는
이유로 갑자기 Day 수십 개를 갖게 된다. 사용자가 의도하지 않은 부수효과이므로,
"날짜를 보냈다"를 명시적 동기화 신호로 삼는다. 같은 날짜를 다시 보내는 경우는 멱등이다
(추가 0건, 범위 밖 0건).

## 결과

### 좋아지는 것
- 기간을 늘리면 Day가 자동으로 따라 늘어난다 — 지금까지 사용자가 손으로 Day를 추가해야 했다.
- 일정이 붙은 Day가 서버 판단으로 사라지는 경로가 **구조적으로 존재하지 않는다**.
- Day 생성 규칙(`build_days_for_range`)과 검증 규칙(`validate_date_range`)의 단일 소스가
  유지된다. 새 규칙 `diff_days_for_range`도 같은 파일의 순수 함수라 테스트가 쉽다.

### 감수하는 것
- **프론트 작업 없이는 미완성이다.** 백엔드만 배포하면 기간을 줄여도 사용자는 아무 경고를
  못 보고 범위 밖 Day가 조용히 남는다(= 종전 동작과 같음, 나빠지지는 않음). 확인 모달은
  ui-dev 후속 작업이다.
- 사용자가 확인 모달에서 "삭제"를 골랐을 때 프론트가 `DELETE /api/days/{id}`를 N번 호출한다.
  일부만 성공하는 부분 실패가 가능하다 — 다만 Day 삭제는 각각 독립적이고, 실패하면 남아
  있을 뿐이라 다음에 다시 지우면 된다(POST의 Day 일괄 생성과 달리 원자성이 필요 없다).
  N이 커지면(수십 개) 그때 bulk 삭제 엔드포인트를 검토한다.
- `MAX_TRIP_TOTAL_DAYS`(180)에 걸리면 PATCH가 422로 막힌다. 90일짜리 여행을 두 번 이상
  통째로 옮기는 비현실적 시나리오에서만 발생하고, 에러 메시지가 정리 방법을 안내한다.

## 기각한 대안

- **(b) `force=true`로 한 번에 삭제까지** — 위 표 참고. 파괴적 동작을 일반 수정 요청에
  묶는 설계는 클라이언트의 실수 한 줄이 곧바로 데이터 손실이 된다.
- **(c) 범위 밖 Day를 영구히 남기고 UI 표시만** — 정리 수단이 없어 Day 목록이 계속
  더러워진다. (a) 안에 "사용자가 삭제를 거절한 경우"로 이미 포함돼 있다.
- **범위 밖 Day를 자동 삭제하되 일정이 없는(빈) Day만** — "일정 없는 Day는 지워도 안전"이
  참인 것 같지만, 사용자가 `label`을 직접 붙여둔 Day("귀국일" 등)를 날린다. 무엇보다
  "어떤 건 지워지고 어떤 건 안 지워진다"는 규칙은 사용자가 예측할 수 없다.
- **`Day.deleted_at` 소프트 삭제 도입** — 되돌리기 UI를 만들 계획이 없는데 모든 Day 조회
  쿼리에 필터 조건이 붙고 Alembic 마이그레이션까지 필요하다. 이 규모에 과설계.
- **미리보기 전용 엔드포인트(`GET .../day-sync-preview`)** — 진실 소스가 둘로 갈라진다.
  PATCH 응답 하나로 충분하다.
