# ADR-0003: 여행 체크리스트(ChecklistItem) 데이터 모델과 정렬 정책

- **날짜**: 2026-09-09
- **상태**: Accepted
- **작성**: senior-dev (오케스트레이터 위임)
- **관계**: 독립 결정. Trip 삭제 시 CASCADE 정책은 기존 `Day`/`ItineraryItem`과 동일하게 따른다.

## 배경

`docs/PROJECT.md` Backlog Tier 1의 "일정 메모/체크리스트" 항목을 착수한다. 백로그에는
"Trip 또는 Day 레벨 자유 텍스트"로만 적혀 있었는데, 사용자에게 범위를 확인한 결과 실제 요구는
다음과 같았다.

- **여행(Trip) 단위**다. "여권 챙기기", "환전 해오기"처럼 여행 전체에 걸친 준비물/할 일이지
  특정 날짜에 귀속되는 메모가 아니다.
- **자유 텍스트 한 덩어리가 아니라 진짜 체크리스트**다. 항목을 여러 개 추가하고, 각각
  완료/미완료를 토글하고, 삭제할 수 있어야 한다.

이건 새 테이블이 필요한 작업이라 되돌리기 어렵다(스키마 변경 + Alembic 마이그레이션 +
운영 Neon DB 적용). 그래서 컬럼 구성을 지금 정해두고 근거를 남긴다.

## 결정

### 1. `ChecklistItem` 테이블 (`checklist_item`)

| 컬럼 | 타입 | 비고 |
|---|---|---|
| `id` | int PK | |
| `trip_id` | int FK → `trip.id`, `ondelete="CASCADE"`, NOT NULL | `Day.trip_id`와 완전히 같은 선언 방식 |
| `text` | str NOT NULL | 입력 검증에서 trim + 빈 값 거부 + 200자 상한 |
| `is_checked` | bool NOT NULL, 기본 `False` | |
| `created_at` | datetime, `default_factory=utcnow` | `Trip`/`ItineraryItem`과 같은 패턴 |

`Day`가 아니라 `Trip`에 직접 매단다. Day에 붙이면 기간 PATCH로 그 Day가 범위 밖이 됐을 때
(ADR-0001) 준비물이 사용자 눈에서 사라지거나, 사용자가 범위 밖 Day를 지우면 CASCADE로 함께
삭제된다 — "여권 챙기기"가 날짜 조정 때문에 사라지는 건 명백한 오동작이다.

### 2. 정렬 컬럼(`position`/`sort_order`)을 두지 않는다 — 이번 스코프에 순서 변경 없음

조회는 항상 `ORDER BY id`(= 생성 순서)다. 드래그 정렬도, 위/아래 이동 버튼도 넣지 않는다.

### 3. `updated_at`을 두지 않는다

`ItineraryItem`에는 있지만 이 앱의 어떤 화면도 그 값을 읽지 않는다. 체크리스트는 토글이
가장 잦은 조작이라 매 토글마다 의미 없는 타임스탬프 갱신 코드가 붙는다. 필요해지면
그때 추가한다(컬럼 추가는 데이터 손실 없는 마이그레이션이다).

### 4. 항목 수 상한 `MAX_TRIP_CHECKLIST_ITEMS = 100`, 텍스트 길이 상한 200자

- 개수 상한은 `create_checklist_item`에서 `COUNT` 후 초과 시 422.
- 길이 상한은 pydantic 검증(`MAX_CHECKLIST_TEXT_LENGTH`)으로만 두고 **DB 컬럼 길이 제약은
  걸지 않는다**(제약을 바꾸려면 또 마이그레이션이 필요한데, 이 값은 UX 판단에 가깝다).

### 5. Trip 삭제 시 CASCADE — 기존과 동일

`ondelete="CASCADE"`를 FK에 선언하고, SQLite에서는 `app/db.py`의 기존
`PRAGMA foreign_keys=ON` 리스너가, Postgres에서는 엔진이 강제한다. Day/ItineraryItem과
같은 경로라 별도 장치가 없다(검증 완료).

### 6. API: 새 라우터 `app/routers/checklist.py`, 토글 전용 엔드포인트 없음

```
GET    /api/trips/{trip_id}/checklist   → 200 list[ChecklistItemRead]  (없는 트립이면 404)
POST   /api/trips/{trip_id}/checklist   → 201 ChecklistItemRead
PATCH  /api/checklist/{item_id}         → 200 ChecklistItemRead        (text / is_checked 부분 수정)
DELETE /api/checklist/{item_id}         → 204
```

`/api/days/{day_id}/items` + `/api/items/{item_id}`와 같은 중첩 규칙이고, 라우터는
`days.py`/`items.py`처럼 prefix 없이 `dependencies=[Depends(require_session)]`로 통째로 보호한다.
체크 토글은 별도 엔드포인트(`POST .../toggle`)가 아니라 일반 PATCH로 처리한다.

### 7. 텍스트 검증은 `ItineraryItemUpdate.title`에서 겪은 버그를 그대로 방어한다

`ChecklistItemUpdate`의 validator는 **필드 생략과 명시적 `null` 전송을 구분**한다. 생략은
라우터의 `model_dump(exclude_unset=True)`가 걸러내 validator 자체가 호출되지 않고, validator가
호출됐다는 건 값이 명시적으로 왔다는 뜻이므로 `None`/빈 문자열/공백을 전부 422로 거부한다.
`is_checked`도 NOT NULL이라 **같은 방어를 적용한다**(`{"is_checked": null}` → 422).

## 근거

### 왜 순서 변경 기능을 넣지 않는가

| | (a) 생성 순서 고정 (채택) | (b) 위/아래 이동 버튼 | (c) dnd-kit 드래그 정렬 |
|---|---|---|---|
| 스키마 | 정렬 컬럼 불필요 | `position` 컬럼 필요 | `position` 컬럼 필요 |
| API | CRUD 4개 | + 이동 or reorder 엔드포인트 | + reorder 엔드포인트 |
| 프론트 | 리스트 렌더만 | 버튼 2개 + 낙관적 업데이트 | dnd-kit 센서/충돌 처리 + 낙관적 업데이트 |
| 체크 토글과의 상호작용 | 없음 | 없음 | 체크박스 탭과 드래그 제스처가 경합 |

- **(c) 기각**: `ItineraryItem`에 dnd-kit 정렬이 이미 있다는 건 "패턴이 있으니 재사용하자"의
  근거가 되지만, 그 화면은 **하루 동선의 방문 순서**라 순서 자체가 데이터의 의미다. 준비물
  목록은 순서에 의미가 없다 — "여권"이 "환전"보다 위에 있어야 할 이유가 없다. 게다가 모바일에서
  각 행에 체크박스(탭)와 드래그 핸들(롱프레스/드래그)이 공존하면 제스처가 경합해서, `TouchSensor`
  활성화 지연 튜닝이라는 실제 비용이 발생한다(M3에서 이미 겪은 영역). 얻는 가치에 비해 비싸다.
- **(b) 기각**: (c)보다 싸지만 여전히 `position` 컬럼 + 재정렬 API + 낙관적 업데이트가 필요하고,
  버튼을 여러 번 눌러 원하는 위치로 옮기는 UX는 정렬이 정말 필요한 사용자에게도 만족스럽지 않다.
  중간 타협이라 양쪽의 비용만 가져온다.
- **(a) 채택**: 순서가 필요하면 사용자는 **지우고 다시 추가**하면 된다(항목 하나가 한 줄
  텍스트라 재입력 비용이 낮다). "지금 요구되지 않은 기능을 위한 컬럼을 미리 넣지 않는다"는
  이 프로젝트의 기존 판단 기준(PROJECT.md의 "지금 호출할 곳이 한 군데뿐이라 엔드포인트만
  늘어남", ADR-0002의 "도달 불가능한 예외 처리는 넣지 않는다")과 같다.

**나중에 정렬이 필요해지면**: `position int NOT NULL DEFAULT 0` 컬럼을 추가하는 마이그레이션
하나 + `ORDER BY position, id` + `reorder_items`와 같은 형태의 엔드포인트면 된다. 기존 행은
전부 `position=0`이 되지만 `id` 보조 정렬 덕에 **현재 순서가 그대로 유지되므로 데이터 백필이
필요 없다**. 즉 이 결정은 되돌리는 비용이 낮은 쪽이고, 반대로 지금 컬럼을 넣어두면 아무도
쓰지 않는 값이 계속 유지보수 대상으로 남는다.

### 왜 `id` 정렬인가 (`created_at`이 아니라)

`created_at`은 `datetime.utcnow()`라 이론적으로 동률이 가능하고, 동률이면 정렬이 불안정해진다.
`id`는 두 DB(SQLite rowid / Postgres serial) 모두에서 삽입 순서와 단조 증가가 보장되며 유일하다.
`created_at`은 표시/디버깅용으로만 남긴다.

### 왜 개수·길이 상한을 두는가 (Day 상한과 성격이 다르다)

`MAX_TRIP_DAYS`(90)는 "연도 오타 하나로 수천 행"이라는 **자동 일괄 생성 사고**를 막는 장치였다.
체크리스트에는 그런 경로가 없다(항상 사용자가 한 줄씩 만든다). 그래도 상한을 두는 이유는
다르다:

- **개수(100)**: 프론트 재시도 루프 버그 하나가 무료 티어 Neon DB를 채우는 걸 막는 가드레일.
  실사용 준비물 목록이 100개를 넘을 일이 없어 정상 사용자는 절대 만나지 않는다.
- **길이(200자)**: 상한 없는 텍스트 필드는 수 MB짜리 붙여넣기를 그대로 받는다. 개수 상한만
  있으면 "100개 × 무제한 길이"라 개수 상한이 무의미해진다. 두 상한은 세트로 의미가 있다.

참고로 기존 `Trip.name`/`ItineraryItem.title`에는 길이 제한이 없다 — 같은 노출이 있지만
이번 변경 범위 밖이라 손대지 않고 백로그(Tier 2)에 남긴다.

### 왜 토글 전용 엔드포인트를 만들지 않는가

`POST /api/checklist/{id}/toggle`은 요청 바디가 없어 프론트가 짧아 보이지만, **현재 상태를
모른 채 뒤집으므로 멱등하지 않다**. 네트워크 재시도나 더블탭이 그대로 상태 반전 2회가 되고,
두 사람이 같이 쓰는 앱에서 "내가 껐는데 왜 켜져 있지"가 재현 불가능한 형태로 발생한다.
`PATCH {"is_checked": true}`는 멱등하고, 텍스트 수정과 엔드포인트를 공유하며,
`PATCH /api/items/{id}`(`update_item`)의 기존 패턴과 같다.

### 왜 없는 트립 조회에 빈 배열이 아니라 404인가

`GET /api/days/{day_id}/items`(`list_items`)는 없는 Day에도 200 + `[]`를 준다. 여기서는 그
관례를 따르지 않는다 — 빈 배열은 "체크리스트가 비어 있다"와 구분되지 않아서, 프론트가 잘못된
`tripId`로 조회 중인 상태를 조용히 숨긴다. 체크리스트는 "아직 아무것도 없는" 상태가 정상이자
가장 흔한 초기 상태라 이 혼동의 비용이 특히 크다. `list_items`를 지금 함께 고치지는 않는다
(이번 범위 밖의 동작 변경이고, 그 화면은 Day 목록을 이미 알고 들어오므로 위험이 낮다).

## 결과

### 좋아지는 것
- 여행 준비물/할 일을 앱 안에서 관리할 수 있다(지금까지는 수단이 전혀 없었다).
- Trip을 지우면 체크리스트도 함께 사라진다 — 기존 Day/ItineraryItem과 완전히 같은 규칙이라
  삭제 동작에 예외가 늘지 않는다.
- 스키마가 5개 컬럼뿐이라 나중에 정렬/담당자/마감일 같은 확장을 얹기 쉽다.

### 감수하는 것
- **항목 순서를 바꿀 수 없다.** 원하는 순서가 있으면 지우고 다시 추가해야 한다. 사용자가
  실제로 불편을 호소하면 위 "나중에 정렬이 필요해지면" 경로로 추가한다.
- **동시 편집 보호 장치가 없다.** 두 사람이 같은 항목을 동시에 수정하면 last-write-wins다.
  Day와 달리 유니크 제약을 걸 자연키가 없고(같은 텍스트를 두 번 적는 게 오류가 아니다),
  토글은 멱등해서 충돌이 나도 결과가 "둘 중 하나의 값"으로 수렴할 뿐 데이터가 깨지지 않는다.
  ADR-0002가 Day에 제약을 건 이유(중복 Day가 순번 라벨을 망가뜨림)가 여기엔 없다.
- **에러 `detail`이 영어다**(`"Trip not found"`, `"text must not be empty"` 등). ADR-0002에서
  정한 계약 언어 정책 그대로이며, 한국어 노출은 프론트가 담당한다(Backlog Tier 2의 기존 항목).
- **운영 Neon DB에 `alembic upgrade head`가 필요하다**(리비전 `d6eea980ecbe`). 새 테이블
  생성뿐이라 기존 데이터에 영향이 없고, ADR-0002 마이그레이션과 달리 실패할 사전 조건도 없다.
- **프론트 없이는 사용자가 쓸 수 없다.** 백엔드만으로는 기능이 완결되지 않는다(ui-dev 후속).

## 기각한 대안

- **Day 단위 체크리스트 / Day·Trip 양쪽 지원(`day_id` nullable)** — 사용자 요구가 여행 단위로
  확정됐다. nullable FK 두 개는 "둘 중 정확히 하나만 채워져야 한다"는 불변식을 앱 레벨에서
  계속 지켜야 하고, 조회 쿼리도 두 갈래가 된다. 나중에 Day 메모가 필요해지면 그건 별도
  테이블/기능으로 다루는 게 맞다.
- **`Trip.memo` 단일 텍스트 컬럼(자유 메모)** — 마이그레이션이 가장 싸지만 요구된 체크박스
  토글이 불가능하다. 체크 상태를 텍스트 안에 마크다운(`- [x]`)으로 인코딩하는 방식은 파싱과
  동시 수정 충돌(한 사람이 통째로 덮어씀)을 앱이 떠안게 된다.
- **`ChecklistItem`에 `position` 컬럼만 미리 넣고 정렬 API는 나중에** — 아무도 안 쓰는
  컬럼이 항상 0으로 채워진 채 남고, 나중에 쓰려면 어차피 백필 판단이 필요하다. 반면 나중에
  컬럼을 추가하는 비용은 `DEFAULT 0` 마이그레이션 하나뿐이고 `id` 보조 정렬로 기존 순서가
  보존된다. "미리 넣기"의 이득이 실제로 없다.
- **체크 완료 항목을 목록 아래로 자동 이동(서버 정렬 `ORDER BY is_checked, id`)** — 체크하는
  순간 항목이 화면에서 점프해 "방금 뭘 체크했는지" 잃어버린다. 그런 그룹핑이 필요하면 서버
  정렬이 아니라 프론트 표시 옵션으로 두는 게 맞다(서버는 사실만 준다 — ADR-0001과 같은 기준).
- **소프트 삭제(`deleted_at`)** — 되돌리기 UI 계획이 없다. ADR-0001에서 Day에 대해 같은 이유로
  기각한 것과 동일.
