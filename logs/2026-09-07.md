## M7 Tier 1 착수: 여행 생성 시 날짜 범위 → Day 자동 생성 (백엔드) — 같은 날, 이어서

담당: senior-dev (오케스트레이터 위임). 같은 묶음의 "여행 삭제 UI"·"여행 정보 수정 UI"는 프론트 전용이라 ui-dev가 별도로 진행.

### 설계 결정
날짜 범위로 Day를 일괄 생성하는 방식 3개 후보를 비교해 **(c) 트립 생성 API가 Day까지 같이 만드는 방식**을 선택.

| 후보 | 장점 | 단점 | 판정 |
|---|---|---|---|
| (a) `POST /api/trips/{id}/days/bulk` 신설 | 재사용 가능, 기존 라우팅 컨벤션과 일관 | 프론트가 2회 왕복, 그 사이 실패하면 "Day 없는 트립"이 남음. 지금 호출처가 한 곳뿐 | 보류 |
| (b) 프론트에서 단건 API N회 반복 호출 | 백엔드 변경 0 | N번 중 일부 실패 시 프론트가 보상/재시도 로직을 떠안음. 10일 여행이면 요청 10개 | 기각 |
| (c) `POST /api/trips`가 Day까지 생성 | 왕복 1회, 단일 트랜잭션이라 부분 실패 상태가 원천적으로 없음, 프론트 구현이 가장 단순 | 트립 생성에 부수효과가 생김 | **채택** |

- (c)의 "부수효과" 단점은 응답을 `TripRead` → `TripDetailRead`(days 포함)로 바꿔서 완화 — 무엇이 만들어졌는지 응답에 그대로 드러남. `TripDetailRead`는 `TripRead`를 상속하므로 기존 프론트 `Trip` 타입과 호환(필드 추가만 됨).
- 날짜 범위 → Day 변환 규칙은 `app/services/trip_days.py`로 분리. 나중에 (a)가 실제로 필요해지면 라우터만 얹으면 됨(재작업 거의 없음) → 되돌리기 쉬운 결정이라 ADR 대신 `docs/PROJECT.md`의 Architecture Decisions에 요약만 남김.
- **여행 기간을 나중에 PATCH로 바꿔도 Day는 동기화되지 않음** (이번 스코프 밖). 범위 밖으로 밀려난 Day에 이미 일정이 붙어있을 수 있어 자동 삭제가 위험하므로, 후속 백로그 항목으로 `docs/PROJECT.md` Tier 1에 별도 등록.

### 진행한 작업
- `backend/app/services/trip_days.py` **신규** — `build_days_for_range(trip_id, start, end)`(양끝 포함), `MAX_TRIP_DAYS = 90`
  - Day의 `sort_order`는 인덱스가 아니라 0으로 둠. 조회가 `(sort_order, date)` 정렬이라 0이면 날짜순이 되고, 나중에 단건 API로 추가되는 Day(기본값 0)와 정렬 기준이 어긋나지 않음
  - `label`도 `null`로 둠 — 프론트가 `day.label || day.date`로 표시하므로 자동 생성 Day는 날짜가 그대로 보이고, 사용자가 나중에 이름을 붙일 수 있음
- `backend/app/schemas.py` — `TripCreate`에 `model_validator` 추가: `end_date < start_date`면 422, 기간이 `MAX_TRIP_DAYS`(90일) 초과면 422
- `backend/app/routers/trips.py` — `create_trip`이 `db.flush()`로 `trip.id`를 확보한 뒤 Day를 `add_all` → **커밋 1회**(단일 트랜잭션). 응답 모델을 `TripDetailRead`로 변경
- **스키마 변경이 없어 Alembic 마이그레이션 불필요** (기존 `Day` 테이블 그대로 사용)

### API 계약 (ui-dev 전달용)
`POST /api/trips` — 요청은 기존과 동일, `start_date`/`end_date`(`YYYY-MM-DD`)를 **둘 다** 보내면 Day 자동 생성. 하나만 보내거나 안 보내면 Day는 생성되지 않음(`days: []`).
응답 201: 기존 `Trip` 필드 + `days: Day[]` (날짜 오름차순). 오류 422: 날짜 역전 / 90일 초과.

### 검증 (venv312 + curl, 포트 8011)
| 케이스 | 결과 |
|---|---|
| 2026-10-01~10-04 (4일) | 201, Day 4개(10-01~10-04) 생성 |
| 날짜 미입력 | 201, `days: []` |
| start == end (당일치기) | 201, Day 1개 |
| `start_date`만 입력 | 201, `days: []` (둘 다 있어야 생성) |
| end < start | 422 `end_date must be on or after start_date`, **트립 행 생성 안 됨** |
| 365일 범위 | 422 `trip cannot span more than 90 days`, 트립 행 생성 안 됨 |
| 생성 후 `GET /api/trips/{id}` 재조회 | days 날짜순으로 그대로 반환 |
| 검증용 트립 삭제 | 204, Day도 CASCADE 삭제 확인(기존 동작 회귀 없음) |

검증용으로 만든 트립 4건은 모두 삭제했고, 기존 데이터(트립 id 1 "오사카 여행", id 2 "안동 여행")는 그대로임.

## QA 지적 수정: `PATCH /api/trips/{id}` 날짜 범위 검증 누락 — 같은 날, 이어서

담당: senior-dev (오케스트레이터 위임). qa-reviewer가 발견한 이슈 1건 수정.

### 문제
`POST /api/trips`에는 날짜 검증(역전 금지 / 90일 초과 금지)이 들어갔지만 `PATCH /api/trips/{id}`에는 대응하는 검증이 전혀 없었음. QA가 PATCH로 `end_date < start_date`와 366일짜리 기간을 둘 다 200 OK로 통과시키는 걸 재현.

### 설계 판단 (단순 복붙이 안 되는 이유)
`TripCreate`는 요청 바디만 보면 최종 기간이 정해지지만, **PATCH는 부분 업데이트라 요청에 `end_date`만 오고 `start_date`는 안 올 수 있음** → DB에 저장된 기존 값과 합쳐야 최종 기간이 정해진다. 즉 `TripUpdate`에 `model_validator`를 다는 방식으로는 원리적으로 검증이 불가능(스키마는 DB를 모름). 그래서:

- 검증 규칙 자체를 `app/services/trip_days.py`의 **순수 함수 `validate_date_range(start, end) -> None`** 으로 추출 (위반 시 `ValueError`)
- `TripCreate.model_validator`는 이 함수를 호출만 함 → pydantic이 `ValueError`를 422로 변환(기존 에러 메시지·응답 형식 그대로 유지)
- `update_trip` 라우터는 `patch.get("start_date", trip.start_date)` / `patch.get("end_date", trip.end_date)`로 **병합한 값**을 넘겨 호출하고, `ValueError` → `HTTPException(422)`로 변환
- **검증을 `setattr` 루프보다 먼저** 수행 — 잘못된 값이 세션에 올라가지 않게 함
- 정책 일관성: 두 날짜 중 **하나라도 없으면 검증 스킵**(비교 대상이 없음). `start_date`를 `null`로 지우는 patch도 그래서 통과 — `TripCreate` 및 "둘 다 있을 때만 Day 생성" 규칙과 같은 기준
- 에러 응답 형식 차이(POST는 pydantic의 `detail: [{msg}]`, PATCH는 `detail: "문자열"`)는 그대로 둠 — 프론트 `extractErrorMessage()`가 이미 두 형식을 모두 처리하므로 억지로 pydantic 형식을 흉내 낼 이유가 없음
- 되돌리기 쉬운 국소적 리팩터링이라 ADR 대상 아님. `docs/PROJECT.md`의 Architecture Decisions에 요약만 추가

### 변경 파일
- `backend/app/services/trip_days.py` — `validate_date_range(start, end)` 신규 추가
- `backend/app/schemas.py` — `TripCreate._validate_date_range`가 공통 함수 호출하도록 리팩터링, import를 `MAX_TRIP_DAYS` → `validate_date_range`로 변경, `TripUpdate`에 "검증은 라우터에서 하는 이유" 주석 추가
- `backend/app/routers/trips.py` — `update_trip`에 병합 후 검증 추가(위반 시 422)
- 스키마(DB) 변경 없음 → Alembic 마이그레이션 불필요
