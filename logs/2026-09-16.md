# 2026-09-16

## 작업: 일정 AI 정렬 **재작업** — 핀 고정 폐기, 숙소 개수 기반 앵커 (senior-dev)

어제(2026-09-15) 배포한 "AI 정렬"(ADR-0012)을 하루 써본 사용자가 **핵심 UX와 알고리즘이
의도와 다르다**고 지적했다. 새 기능이 아니라 **어제 설계의 재작업**이다. 이 세션은 백엔드 +
설계 문서까지이고, **프론트는 ui-dev 후속**(스펙은 아래 별도 섹션).

### 0. 무엇이 바뀌었나 (한 문단 요약)

"사용자가 카드 메뉴로 시작/끝점을 핀으로 고정한다"는 구조를 통째로 걷어냈다. 사용자는 이미
드래그로 그 항목들을 그 자리에 놓아뒀으므로, **현재 순서의 처음/마지막**을 그대로 앵커로 쓰고
정렬을 누를 때 프론트가 **한 번만 확인**한다. 중간 날짜의 양 끝은 그날 **숙박시설 개수**
(구글 카테고리로 자동 판별)가 정한다. 전날의 끝과 당일 숙소가 다른 곳이면 그 날짜만 **실패**로
보고한다. `route_role` 컬럼은 **드롭**했다.

### 1. ADR — 정정이 아니라 후속 ADR로 남겼다

[`docs/adr/0013-itinerary-route-sort-anchors-by-lodging.md`](../docs/adr/0013-itinerary-route-sort-anchors-by-lodging.md) 신설.

ADR-0012를 직접 고치지 않은 이유:

- 이번 변경은 "설명을 다듬는 정정"이 아니라 **결정을 뒤집는 것**이다(결정 2·3·6). ADR-0010/0011의
  "정정" 섹션들은 전부 *결정을 유지한 채* 구현/서술을 바로잡은 것이라 성격이 다르다.
- 이 저장소에는 이미 같은 상황의 선례가 있다 — **ADR-0007이 ADR-0006의 결정 1·2를 대체**하면서
  원본을 고치지 않고 상단에 후속 포인터만 달았다. 그 패턴을 그대로 따랐다.
- "왜 하루 만에 뒤집었는가"가 그 자체로 남길 가치가 있는 기록이다. 원본을 덮어쓰면 그 맥락이
  사라진다.

ADR-0012 상단에는 **⚠ 경고 블록 + 상태를 `Superseded in part by ADR-0013`으로** 표기했다
(본문은 한 줄도 고치지 않음).

### 2. 확정한 설계 (근거는 전부 ADR-0013에)

| 날짜 | 시작 | 끝 |
|---|---|---|
| **첫날** | 현재 순서의 **첫 항목** (고정) | 현재 순서의 **마지막 항목** (고정) |
| **중간 날 · 숙박 2개↑** | 첫 숙소 (고정) | 마지막 숙소 (고정) |
| **중간 날 · 숙박 1개** | 전날의 끝에서 승계 | 그 숙소 (고정) |
| **중간 날 · 숙박 0개** | 전날의 끝에서 승계 | 알고리즘이 정함 (= 기존 동작) |
| **마지막 날** | 전날의 끝에서 승계 | 현재 순서의 **마지막 항목** (고정) |

판단이 필요했던 지점 3가지와 그 결론:

1. **숙박 3개 이상** → 처음/마지막만 앵커로 쓰고 가운데는 일반 항목. 2개 케이스의 자연스러운
   일반화이고 결과가 결정적이다. "모호하니 실패"는 읽는 방법이 분명한 모양을 막는 것이라 기각.
2. **`route_role` 컬럼** → **실제로 드롭**(마이그레이션 `e57c1b0a92d4`). 읽는 코드가 0줄인 컬럼을
   남기면 나중에 다시 조사하게 되고, 값이 살아 있던 기간이 **하루**라 잃을 데이터가 실질적으로 없다.
3. **연속성 "같은 장소" 판정** → `place_id`가 같으면 즉시 같은 곳, 아니면 **직선 200m 이내**.
   ADR-0010이 기각한 "가까우면 같은 숙소로 통일"과 다른 점은 **틀렸을 때의 방향이 안전**하다는
   것이다(여기서는 판정이 갈려도 결과가 "사용자에게 묻는다"이지 데이터를 덮어쓰는 게 아니다).

숙박 판별은 `place_category`(ADR-0011이 등록 시점에 **추가 비용 0**으로 저장해 둔 구글
`primaryTypeDisplayName`) 키워드 매칭 + AI 추천이 붙인 `category == "lodging"`. **외부 호출은
여전히 0회**다. 수동 입력 항목은 카테고리가 없어 숙소로 인식되지 않는데(사용자가 알고 선택한
트레이드오프), 상세보기에서 카테고리에 "호텔"이라고 적으면 그대로 숙소가 되는 **탈출구가 이미
있다**.

채워진 행은 **0건**이었다.

### 5. 알려진 한계 (전부 ADR-0013 "감수하는 것"에 기록)

- 카테고리가 없는 수동 항목은 숙소로 인식되지 않는다(그 Day는 숙박 0개로 퇴화 — 실패가 아니다).
- 확인 대화상자는 프론트에만 있다(API를 직접 부르면 확인 없이 정렬된다 — 외부 호출 0회인
  연산이라 막을 실익이 없다).
- 200m 임계값은 통계가 아니라 판단이다(`place_id`가 갈릴 때만 쓰이는 2차 판정).
- ADR-0012의 기존 한계(직선 거리 / 전역 락 단일 프로세스 / undo 없음)는 그대로.

### B. 추가할 것 — 실행 전 확인 대화상자 (이번 변경의 핵심)

`ItinerarySortModal`의 "정렬 시작" 버튼을 누르면, **선택된 날짜에 첫날 또는 마지막 날이
포함된 경우에 한해** 서버 호출 **전에** Yes/No 확인 단계를 먼저 보여준다.

- **"아니오" → 요청을 보내지 않고 취소**(모달은 열어둔 채 선택 화면으로 복귀). "예" → 그제서야
  `sortItinerary()` 호출.
- `window.confirm()`이 아니라 **모달 안의 인라인 확인 단계**를 권장한다(이 페이지의 다른 확인
  UI와 톤을 맞추고, 아래처럼 실제 장소 이름을 보여줄 수 있다).
- 문구에 **실제 항목 제목을 넣을 것.** 모달은 이미 `itemsByDayId`를 받고 있으므로 추가 조회가
  필요 없다. 예:

  > **출발/도착 지점을 확인해주세요**
  > - 여행 출발: **Day1 9/10(목)** 의 첫 일정 — "김포공항"
  > - 첫날 종점: **Day1 9/10(목)** 의 마지막 일정 — "○○호텔"
  > - 여행 도착: **Day5 9/14(월)** 의 마지막 일정 — "제주공항"
  >
  > 이 세 곳이 실제 출발/도착 지점이 맞나요? 아니라면 취소하고 일정 목록에서 드래그로 순서를
  > 바꾼 뒤 다시 실행해주세요.
  >
  > [아니오, 취소] [예, 정렬합니다]

- **선택에 첫날도 마지막 날도 없으면 확인 없이 바로 실행한다**(중간 날짜만 고른 경우 — 그
  세 지점과 무관하다).
- 첫날이 선택됐지만 마지막 날이 아니면 첫 두 줄만, 반대면 마지막 줄만 보여준다.
- 항목이 1개 이하인 Day는 어차피 `skipped`이므로 그 줄은 생략해도 된다(선택).

### C. 결과 배너 (`ItinerarySortResultBanner`) — 구조 변경 없음

`sorted_days`/`skipped_days`/`failed_days`/`warnings` 구조와 "서버가 준 한국어 `message`를
그대로 표시" 정책은 **그대로**다. 새 `reason_code` 2개(`lodging_continuity_mismatch`,
`lodging_no_coordinates`)도 `failed_days`(빨강, 조치 필요)에 그대로 들어온다 — **코드별 분기를
새로 만들 필요 없다.** 메시지가 이미 해결 방법을 담고 있다.

## qa-reviewer 검증 (일정 AI 정렬 재작업, ADR-0013)

senior-dev의 101개 체크를 신뢰하지 않고 **독립적으로 새로 작성한 테스트**로 재검증했다.
`get_db`를 임시 SQLite(세션 스크래치패드 경로)로 오버라이드해 실행 — `dev.db`/운영 DB 무접촉,
외부 API 호출 0회. 백엔드 로직 63건 + 동시성/멱등성/부분성공 8건 = **총 71개 체크 전부 통과**.
검증 스크립트는 이 저장소 관행대로 세션 임시 디렉토리에만 두고 커밋 대상에 넣지 않았다.

### 1. 앵커 판정 표 재현 — 전부 일치
- 첫날: 현재 순서 첫 항목=시작(고정)/마지막 항목=끝(고정), 가운데는 앵커에서 최근접 순 정렬 확인.
- 중간 날 숙박 2개: 첫 숙소=시작(고정), 마지막 숙소=끝(고정) 확인.
- 중간 날 숙박 1개: 그 숙소=끝(고정), 시작=전날 끝에서 승계 확인.
- 중간 날 숙박 0개: 시작만 승계, 끝은 알고리즘이 최근접으로 자유 결정 확인.
- 마지막 날: 시작=전날 승계, 끝=현재 순서 마지막 항목(고정) 확인. 마지막 날에 숙박이 있어도
  도착점이 아니면 시작 앵커로 쓰이고 연속성 검사 대상이 되는 것도 확인.
- 숙박 3개 초과(4개 테스트): 처음/마지막만 앵커, 가운데 숙박은 일반 항목으로 정렬 대상에
  섞이는 것 확인(끝에 고정되지 않음).

### 2. 연속성 판정 — 경계값 정밀 검증
`route_order.haversine_km()`를 직접 호출해 테스트 좌표의 실제 거리를 재확인(부동소수 오차
<0.001m 수준): **199.000m→불일치 아님, 200.000m→불일치 아님(경계 `<=` 포함), 201.000m→
`lodging_continuity_mismatch`로 실패** 확인. `place_id` 일치 시 5km 떨어져 있어도 즉시 같은
곳으로 판정되는 것, 실패한 날짜는 원래 순서(`position` 무변경)가 그대로 유지되는 것도 확인.

### 3. 숙박 판별 근거 — 코드 레벨로 직접 확인
`is_lodging_item()`은 **오직 `item.category=="lodging"`(AI 생성) 또는 `place_category` 키워드
매칭**만 본다 — `item.title`은 함수 어디에서도 읽지 않는다. 제목에 "Winner Restaurant",
"Dinner Show Hotel Plaza"를 넣고 `place_category`는 무관한 값("식당"/"공연장")으로 채운
테스트에서 숙박으로 오인되지 않고 최근접 순서대로 배치되는 것을 확인 — **오탐 방지는 제목이
아니라 애초에 제목을 보지 않는 설계**다. `place_category="inner_courtyard"`/`"winner"`는
부분 문자열 매칭에서 제외(숙박 아님), `place_category="inn"`(정확히 일치)만 숙박으로 인정되는
것도 확인.

### 4. `route_role` 완전 제거 확인
`backend/app/models.py`/`schemas.py`에 `route_role` 필드 없음(주석으로만 존재 이유 남김).
`PUT /api/days/{day_id}/route-endpoints` 호출 결과 **404**(라우트 자체가 등록돼 있지 않음).

**[사소] 로그 3절(검증 항목표)의 "삭제된 PUT이 405" 표기는 실측과 다르다.** 실제로는 404다
(같은 경로에 다른 메서드가 남아있는 게 아니라 경로 자체가 사라졌으므로 FastAPI/Starlette가
404를 반환한다). 기능적으로는 문제 없음 — 두 코드 모두 "그 엔드포인트는 더 이상 없다"는
동일한 결론이고 클라이언트(프론트)도 이 경로를 아예 호출하지 않으므로 영향 없음. 단순 기록
오류이니 다음에 이 로그를 참고할 때 헷갈리지 않도록 남긴다.

### 5. 회귀 — 전부 정상
정렬 스타일 3종(nearest/farthest/balanced 첫 방문지 선택 로직 확인), 동시 요청 4건(서로 다른
스타일) 전부 200 + 모든 Day의 position이 0..n-1 순열 유지, 재실행 시 `changed=false` 멱등,
한 요청에 sorted+skipped+failed 혼재 부분 성공, 토글 OFF→403→ON 복구, 타 여행 Day 혼입→422
(무변경), 빈 day_ids→422, 없는 trip→404, 미인증→401, 좌표 없는 항목 제외+경고 문구+개수 집계,
숙소 좌표 없음→`lodging_no_coordinates` 실패 — 전부 기대대로 동작.
