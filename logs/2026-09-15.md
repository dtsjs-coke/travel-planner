재정렬**하는 기능. 여행 목록의 "AI 추천"(새 여행 생성, ADR-0009/0010)과는 **다른 기능**이다.

### 0. 먼저 확정한 것 — 이 기능에 LLM은 필요 없다

등록된 일정에는 이미 `lat`/`lng`가 있다(구글 검색으로 추가한 경우). "고정된 시작점에서 출발해
어떤 순서로 도는가"는 순수 기하 문제라, AI 추천이 쓰던 `app/services/route_order.py`
(haversine + 최근접 이웃, **순수 함수**)를 재사용하면 **Gemini/Places 호출이 0회**인 사실상 무료
기능이 된다. 사용자에게 설명하고 동의를 받은 상태로 위임이 왔고, 그대로 구현했다.

이 판단의 직접적 결과 하나: **좌표 없는 수동 항목을 자동 geocode하지 않는다.** 그러면 버튼 한
번이 유료 호출 N회가 되어 "사실상 무료"라는 설명이 거짓이 된다. 대신 정렬에서 빼고 경고한다.

### 1. 핵심 설계 — 규칙을 한 문장으로 묶었다

요구사항이 여러 갈래(첫날만 수동 지정 / 둘째 날부터 승계 / 띄엄띄엄 선택 / 달력 기준 연속성)로
보였지만, 실제로는 **한 문장**으로 정리된다:

> 어떤 날의 시작 앵커는 **(a) 그 Day에 지정된 `start` 항목**, 없으면 **(b) 달력상 전날의 마지막 장소**다.

여기서 나머지가 전부 따름정리로 나온다.

- 여행 **첫날은 (b)가 존재할 수 없으므로 (a)가 필수** → "첫날만 시작점/끝점을 직접 지정"
- 둘째 날부터는 (b)가 있으므로 지정이 필요 없고, **끝점은 그날 마지막 방문지**가 된다
  (요구사항 8의 해석을 재검토했고 유지 — 날마다 끝점을 요구하면 "버튼 한 번" 목적이 사라진다.
  다만 원하면 어느 Day에든 `end`를 찍을 수 있고, 같은 규칙으로 그대로 동작한다)
- (b)가 "**달력상** 전날"이라 Day1+Day3만 골라도 Day3의 앵커는 (선택되지 않은) Day2의 끝 장소다
- (a)도 (b)도 못 구하면 **그 날짜만 실패**로 보고한다(부분 성공)

**빈 Day를 건너뛰어 이어 붙이지 않는다**는 것도 여기서 결정됐다. Day2가 비었으면 Day3는 Day1의
끝을 쓰지 않고 실패한다 — 사용자가 Day2에 일정을 넣을 생각이었는데 빠뜨렸을 가능성이 높고,
조용히 건너뛰면 그 사실이 영영 드러나지 않는다(요구사항 6이 "일정을 확인하거나 추가해달라는
안내"를 요구한 지점).

### 2. 정렬 스타일 3종 — **첫 방문지를 고르는 방법만** 다르다

| 스타일 | 값 | 첫 방문지 | 그 뒤 |
|---|---|---|---|
| 가까운곳 먼저 | `nearest` | 앵커에서 최단 | 최근접 이웃 |
| 먼곳 먼저 | `farthest` | 앵커에서 최장 | 최근접 이웃 |
| 적당하게 | `balanced` | 거리순 하위 중앙값 | 최근접 이웃 |

- "먼곳 먼저"를 **매 단계 최장 선택**으로 만들면 지그재그가 되어 하루 이동거리가 폭증한다.
  사용자 의도는 "가장 먼 곳을 먼저 찍고 돌아온다"이지 "매번 멀리 간다"가 아니다.
- "적당하게"를 **2-opt(총 이동거리 최소화)**로 만들면 세 옵션이 "취향 둘 + 정답 하나"가 되어
  나머지 둘을 고를 이유가 사라진다. 세 옵션은 같은 축 위의 세 지점이어야 차이를 예측할 수 있다.
- `nearest`는 **기존 `order_day_places`의 계산과 완전히 같다**(최근접 이웃의 첫 선택은 정의상
  최단 후보). 그래서 AI 추천 경로는 인자를 넘기지 않고 그대로 동작한다(무회귀).
- 동점은 전부 현재 `position` 순으로 깨진다 → **결정적**. 재시도·동시 요청이 순서를 흔들지 않는다.

### 3. 시작/끝점을 어디에 저장할 것인가 (검토한 3안)

| 안 | 판단 |
|---|---|
| 기존 `category`에 `start`/`end`를 얹기 | **기각**. 거기엔 AI의 동선 역할 코드(`arrival`/`lodging`…)가 들어 있고 ADR-0010의 거점 검증이 그 의미에 의존한다. `models.py`가 이미 "이 컬럼은 장소 분류가 아니다"라는 경고를 달고 있다 — 세 번째 의미를 더하지 않는다. |
| `Day`에 FK 컬럼 2개(`route_start_item_id`/`route_end_item_id`) | **기각**. "Day당 하나"가 구조적으로 보장되는 게 장점이지만 순환 FK(day→item→day) + SQLite `day` 테이블 재생성(유니크 제약 보유) 비용을 문다. 결정적으로 유일한 이점("한 항목이 시작이자 끝")이 **실재하지 않는다** — 항목의 `position`은 하나뿐이라 목록의 맨 앞이면서 맨 뒤일 수 없다. |
| **`ItineraryItem.route_role` 새 컬럼** | **채택**. nullable 문자열 하나, FK/순환/테이블 재생성 없음. |

지정은 `PATCH /api/items/{id}`가 아니라 **Day 단위 PUT**으로 받는다 — "Day당 start 하나, end 하나"를
지키려면 다른 항목의 같은 역할을 **같은 트랜잭션에서 지워야** 하는데, 그건 단일 항목 PATCH가
할 일이 아니다(ADR-0004가 `day_id`를 `update_item`에 넣기를 거부한 것과 같은 기준). 그래서
`ItineraryItemCreate/Update` 스키마에는 `route_role`이 **일부러 없고** 읽기 응답에만 있다.
다른 Day로 옮기면(`POST /api/items/{id}/move`) 역할은 **지워진다**(역할은 그 Day의 자리다).

### 4. 엣지 케이스 / 에러 처리 (사용자가 명시 요청)

| 상황 | 처리 |
|---|---|
| 선택된 날짜에 일정 0개 | 200, `skipped_days`(`no_items`) — 조치 불필요 |
| 1개 | 200, `skipped_days`(`single_item`) — 그 항목이 다음 날 앵커가 된다 |
| 그 날 전체가 좌표 없음 | `failed_days`(`no_coordinates`) + "구글 검색으로 등록해달라" |
| 좌표 없는 항목이 섞임 | 정렬에서 제외 후 뒤쪽에 그대로 둠 + `warnings`에 건수 보고 |
| 시작점으로 지정한 항목에 좌표가 없음 | `failed_days`(`start_point_no_coordinates`) |
| 달력상 전날 Day 자체가 없음 | `failed_days`(`missing_previous_day`, 없는 날짜를 문구에 표시) |
| 전날에 일정이 없음 / 좌표가 없음 | `failed_days`(`previous_day_empty` / `previous_day_no_coordinates`) |
| 다른 여행의 Day가 섞임 / 없는 Day | **하나라도 섞이면 아무것도 안 하고 422**(`move_item`과 같은 기준) |
| 첫날 시작/끝점 미지정 | **422**(요청 전체 차단) — 단 **선택에 첫날이 포함될 때만** 검사 |
| 기능이 꺼져 있음 | **403** (정렬 API + 시작/끝점 지정 API 둘 다) |
| 동시 요청 | 엔드포인트 **전역 `threading.Lock`**으로 직렬화, 뒤 요청은 대기 후 재계산 |
| 저장 원자성 | 모든 날짜 계산이 끝난 뒤 **단 한 번의 `commit()`** |

동시성을 락으로 간 이유: `position`에는 유니크 제약이 없어 DB가 막아주지 않고(같은 position이
여럿 남을 수 있다), 라우터가 `def`라 FastAPI가 스레드풀에서 실제로 병렬 실행한다(ADR-0002에서
확인한 사실). 409로 거절하지 않고 **기다렸다 재계산**하는 이유는 이 연산이 결정적이라 이어서
도는 게 항상 옳은 결과를 만들기 때문이다(재시도가 last-write-wins가 되던 ADR-0002와 상황이 다름).
**한계**: 프로세스 안에서만 유효 — Render 무료 티어는 단일 인스턴스라 현재는 충분하다.

### 5. 기능 토글

ADR-0007의 "설정 항목이 늘면 key-value가 아니라 **컬럼을 추가한다**"를 그대로 따라
`app_settings.route_sort_enabled: bool = True`를 추가했다. **기본값 true**인 이유는 이 토글이
"새로 켜는 스위치"가 아니라 **끄는 스위치**이기 때문(기능이 무료라 기본으로 꺼두면 새 환경에서
고장난 것처럼 보인다). 프론트에서 버튼을 숨기는 것만으로는 부족하므로 **서버가 403으로 막는다**.
403인 이유: 401(인증은 이미 통과)도 503(AI 추천의 `GEMINI_API_KEY` 미설정과 같은 칸에 묶여
안내를 구분할 수 없다)도 아니라, **사용자가 스스로 끈 상태**다.

### 7. 검증 — 87개 체크 통과 (외부 API 호출 0회, `dev.db` 무접근)

임시 SQLite로 `get_db`를 오버라이드한 TestClient + 순수 함수 직접 호출. 두 번 실행해 같은 결과를
확인했다(결정성).

- **순수 함수(9)**: 세 스타일이 서로 다른 순서를 내는지, 기존 무인자 호출 == `nearest`인지,
  고정 시작/끝점이 모든 스타일에서 지켜지는지, 앵커가 없으면 입력 순서가 유지되는지,
  좌표 없는 항목이 뒤로 빠지는지, 같은 입력에 같은 출력인지.
- **기본 시나리오(13)**: 첫날 미지정 422 → 지정 후 200, 3일 연속 정렬, **전날 끝점이 다음 날
  시작 앵커가 되는 연속성**, position 0..N-1 정규화, 재실행 시 `changed=false`(멱등),
  스타일을 바꾸면 실제 DB 순서가 바뀌는지.
- **띄엄띄엄 선택(4)**: Day1+Day3만 선택했을 때 **선택되지 않은 Day2는 손대지 않으면서**
  Day3의 앵커로는 쓰이는지.
- **연속성 끊김(11)**: Day2가 비면 Day3만 실패하고 Day1·Day4는 성공하는지, 실패 안내문이 한국어로
  날짜(12/2)를 포함하는지, 달력상 전날 Day가 아예 없는 경우(12/24).
- **좌표/개수 엣지(8)**: 좌표 없는 항목 위치·건수 보고·경고 문구, 1개뿐인 Day, 좌표 전무한 Day와
  그 다음 날의 연쇄 실패, 자동 geocode가 일어나지 않았는지(좌표가 여전히 NULL).
- **소속/권한(9)**: 다른 여행 Day 혼입 422(그리고 **아무것도 바뀌지 않음**), 없는 day_id/trip,
  빈 `day_ids`, 모르는 style, 시작=끝 동일 항목, 다른 Day 항목 지정.
- **지정 교체/해제/이동(5)**: 이전 시작점의 역할이 지워지는지, 둘 다 해제, **이동 시 역할 해제**,
  첫날 항목이 1개면 지정 없이도 실행되는지.
- **토글(11)**: 기본 true, 참가자만 PATCH해도 토글 유지, 명시적 null 422, 끄면 두 API 모두 403,
  꺼져도 다른 API는 정상, 다시 켜면 200, 미인증 401.
- **동시 요청(6)**: 서로 다른 스타일 4건을 스레드로 동시 발사 → 전부 200, 모든 Day의 position이
  **0..N-1 온전한 순열**(중복/구멍 없음), 항목 수 불변, 고정 시작/끝점 유지.
- **회귀(11)**: 일정 목록/생성/수정/삭제, `PATCH`로는 `route_role`을 못 바꾸는지, 드래그 정렬
  (reorder), 정산 조회, ICS 내보내기, 설정 행이 여전히 하나인지.

## ui-dev 후속 스펙 (프론트)

### A. API 계약

```
PUT  /api/days/{day_id}/route-endpoints
     body {"start_item_id": number|null, "end_item_id": number|null}   // PUT = 전체 교체
     → 200  ItineraryItemRead[]      (그 Day의 전체 일정 — reorder와 같은 형태, 캐시 통째 교체 가능)
     → 401 / 403(기능 꺼짐) / 404(Day 없음)
     → 422 "route endpoint items must belong to this day"
            "start and end points must be different items"

POST /api/trips/{trip_id}/sort-itinerary
     body {"day_ids": number[], "style": "nearest"|"farthest"|"balanced"}
     → 200 {
         trip_id, style,
         sorted_days:  [{day_id, date, item_count, changed, unlocatable_item_count}],
         skipped_days: [{day_id, date, reason_code, message}],   // 조치 불필요(회색 안내)
         failed_days:  [{day_id, date, reason_code, message}],   // 조치 필요(경고 강조)
         warnings: string[]                                      // 이미 한국어
       }
     → 401 / 403 / 404(여행 없음)
     → 422 "the first day of this trip must have its start and end points designated"
            "all day_ids must belong to this trip" / "day_ids must not be empty"
            "style must be one of: nearest, farthest, balanced"

GET|PATCH /api/settings   // 기존 API에 필드 추가
     응답에 route_sort_enabled: boolean
     PATCH body {"route_sort_enabled": false}   // 참가자 이름과 독립적으로 보낼 수 있다
```

- `ItineraryItemRead`에 **`route_role: "start" | "end" | null`** 필드가 추가됐다 → 일정 카드에
  시작/끝 배지를 붙일 수 있다. `types/models.ts` 갱신 필요.
- `skipped_days`/`failed_days`/`warnings`의 문구는 **서버가 이미 한국어로 준다.** 그대로 띄우면
  된다(`lib/errorMessages.ts` 매핑 대상이 아니다).
- **422 `detail`은 영어**이므로 위 4종을 `lib/errorMessages.ts`에 한국어로 매핑해야 한다.
  특히 첫 번째("the first day…")는 **에러가 아니라 "시작점과 끝점을 잘 정했는지 확인하세요"
  안내/확인 알림**으로 띄우라는 것이 사용자 요구다.
- **403 `detail`**: `"itinerary sort is disabled in app settings"` → "마스터 환경설정에서 이
  기능이 꺼져 있습니다" 정도로 매핑.

### B. 화면 요구사항

1. **진입점**: 여행 상세(Day 편집) 페이지. 여행 목록의 "✨ AI 추천" 플로팅 버튼과 **다른 기능**이니
   문구로 구분할 것(예: "동선 정렬" / "AI 정렬"). z-index는 같은 페이지의 기존 모달들과 충돌하지
   않게(2026-09-13에 실제로 겪은 이슈).
2. **첫날 시작점/끝점 지정 UI**: 그 여행에서 **날짜순으로 가장 이른 Day**의 일정 목록에서
   "시작"/"끝"을 고르게 한다(두 개를 함께 보내는 PUT 1회). 같은 항목을 둘 다로 고르면 422이므로
   클라이언트에서 미리 막는 편이 낫다. 지정된 항목에는 배지(`route_role`)를 표시.
3. **날짜 다중 선택**: 체크박스 등으로 **비연속 선택**이 가능해야 하고 "전체 선택"도 필요하다.
4. **정렬 스타일 선택**: "가까운곳 먼저 / 먼곳 먼저 / 적당하게" 3지선다(값은 `nearest`/`farthest`/
   `balanced`). 기본값은 `nearest`.
5. **확인 알림**: 422(첫날 미지정)를 받으면 실행하지 말고 "시작점과 끝점을 잘 정했는지" 확인하는
   알림을 띄운다. (실행 전에 클라이언트가 선제적으로 확인 모달을 띄우는 것도 요구에 부합한다 —
   서버 422는 마지막 방어선이다.)
6. **결과 표시**: `sorted_days`(성공, `changed=false`면 "이미 정리되어 있었습니다") /
   `skipped_days`(회색 안내) / `failed_days`(**빨간 경고 + 어느 날짜인지 + 서버가 준 문구**) /
   `warnings`. 부분 성공이 정상 경로이므로 "성공/실패" 이분법으로 만들지 말 것.
7. **캐시 무효화**: 성공 시 `sorted_days`의 `day_id`들에 대해 `['days', dayId, 'items']`를
   invalidate. 응답에 항목 배열은 들어 있지 않다(의도적 — ADR-0012).
8. **마스터 환경설정 토글**: `AppSettingsModal.tsx`에 "일정 AI 정렬 사용" 스위치 추가
   (`PATCH /api/settings {"route_sort_enabled": ...}`, 성공 시 `['settings']` invalidate).
   꺼져 있으면 Day 편집 페이지의 진입점을 숨긴다(서버도 403으로 막지만 UI에서 먼저 가린다).
9. 이 API는 외부 호출이 없어 **빠르다**(밀리초 단위). AI 추천처럼 75초 대기 UI를 만들 필요가 없다.

## 작업: 신규 기능 "일정(장소) AI 정렬" — 프론트 구현 (ui-dev)

오케스트레이터가 위 "ui-dev 후속 스펙"을 그대로 위임. **프론트 전용**(백엔드 API 계약은 위 내용
그대로 사용, 변경 없음). git 커밋은 하지 않았다(CLAUDE.md 규칙 — 명시적 요청 시에만).

### 1. 진입점 — Day 편집 페이지 헤더

`DayEditorPage.tsx`의 여행 이름 옆에 "🧭 AI 정렬" 버튼을 추가했다. 여행 목록의 "✨ AI 추천"
(`TripListPage.tsx`, 우하단 플로팅, indigo)과 라벨/색상(teal)을 분명히 구분했다 — 같은 화면에
동시에 뜨지 않아 z-index 충돌은 없지만, 혼동 방지가 이번 요구의 핵심이라 문구/색을 다르게 했다.
`route_sort_enabled === false`(마스터 환경설정)면 버튼 자체를 숨긴다 — 서버도 403으로 막지만
프론트에서 먼저 가리는 편이 UX상 낫다는 스펙 §8을 그대로 따랐다. `settings`가 아직 로딩 중일
때는 서버 기본값(true)과 같게 취급해 버튼이 깜빡이며 나타나는 것을 막았다.

### 2. 정렬 모달 — `components/ItinerarySortModal.tsx`

- 날짜 목록에 체크박스(개별 토글 + "전체 선택/해제") — 기본값은 **전체 선택**으로 시작한다
  (가장 흔한 사용 패턴인 "등록해둔 걸 한 번에 정리"에 맞춤).
- 정렬 스타일 라디오 3종(`nearest`/`farthest`/`balanced`), 기본값 `nearest`.
- 첫째 날이 선택돼 있고 항목이 2개 이상인데 시작/끝 배지가 둘 다 없으면(= 서버가 422를 낼
  조건과 같은 기준, ADR-0012 결정 6과 동일한 "항목 1개 이하면 지정 불필요" 예외 포함) 노란
  힌트 문구를 미리 보여준다. **차단하지는 않는다** — 스펙 §5가 "선제적으로 막는 것도 요구에
  부합하지만, 서버 422가 마지막 방어선"이라고 했으므로 제출 자체는 항상 허용하고, 실제로
  서버가 거부하면 아래 확인 알림으로 안내한다.
- 제출 시 422이고 `detail`이 정확히 `FIRST_DAY_ENDPOINTS_REQUIRED_DETAIL`
  (`"the first day of this trip must have its start and end points designated"`)이면, 일반
  에러(빨강)가 아니라 **amber 톤의 확인 알림**("❓ 시작점과 끝점을 확인해주세요")으로 표시하고
  모달은 닫지 않는다 — 사용자가 바로 첫째 날 목록으로 가서 지정한 뒤 다시 시도할 수 있게.
  이 판별은 `axios.isAxiosError(err) && err.response?.data?.detail === FIRST_DAY_ENDPOINTS_REQUIRED_DETAIL`로
  원문 문자열을 직접 비교한다(번역 매핑을 거치지 않음 — 번역 문구가 바뀌어도 판별 로직이
  깨지지 않게).
- 외부 API 호출이 없어 응답이 밀리초 단위라(ADR-0012), `AiSuggestionModal`의 "최대 75초" 대기
  UI 같은 건 두지 않았다(스펙 §9).

### 3. 시작점/끝점 지정 — 카드의 "동선" 메뉴

- `components/RouteRoleControl.tsx`(신규) — `ItineraryItemCard`의 이동/삭제 버튼 옆에 "동선"
  드롭다운을 추가했다. `MoveItemControl`의 dropdown variant와 같은 z-index 체계(10/20)를
  그대로 재사용했다(이 페이지에서 이미 검증된 값이라 새 스태킹 레벨을 만들지 않음).
- 이 메뉴는 **첫날 카드에서만** 렌더된다(`ItineraryItemCard`의 `canDesignateRouteRole`,
  `DayEditorDesktop`/`DayEditorMobile`이 `day.id === firstDayId`로 계산해 내려줌) — 서버는
  어느 Day든 허용하지만(ADR-0012), 이번 프론트는 첫날에만 노출하기로 한 스펙 §2를 따랐다.
  `route_role` **배지**(시작=하늘색 "시작", 끝=보라색 "끝")는 첫날 여부와 무관하게 모든 카드에
  항상 표시한다 — 값이 남아있으면(예: 이전에 지정했다가 여행 기간이 늘어 그 Day가 더 이상
  첫날이 아니게 된 경우) 사용자가 알 수 있어야 한다.
- 메뉴 항목은 현재 역할에 따라 동적으로 줄어든다(이미 "시작"이면 "시작점으로 지정"이 안 보임).
  **같은 항목이 시작이면서 끝이 되는 조합(422 "start and end points must be different items")은
  메뉴 구성 자체로 막힌다** — "끝점으로 지정"을 누르면 그 항목이 시작점이었을 경우 시작점
  지정이 함께 해제되도록 `lib/routeEndpoints.ts`(신규)의 `computeNextRouteEndpoints()`가
  다음 PUT 바디 전체(`{start_item_id, end_item_id}`)를 계산한다 — 서버가 이 API를 Day 단위
  PUT(항상 전체 교체)으로만 받기 때문에(ADR-0012), 프론트도 "지금 이 Day의 시작/끝이 누구인지"를
  `itemsByDayId`에서 먼저 읽고 클릭된 항목의 역할만 바뀐 상태를 통째로 보낸다.
- `DayEditorPage.tsx`에 `setRouteEndpointsMutation`을 추가하고, 성공 시 `['days', dayId,
  'items']`를 무효화해 새 `route_role`을 반영한다. 실패하면 페이지 상단에 빨간 에러 배너
  (`routeRoleError`, 기존 `moveItemError`와 같은 패턴)로 표시한다.

### 4. 결과 표시 — `components/ItinerarySortResultBanner.tsx`

부분 성공이 정상 경로라는 ADR-0012의 전제를 그대로 반영해 **성공/실패 이분법으로 만들지
않았다** — 세 갈래를 색으로 분리했다: `sorted_days`(초록, `changed=false`면 "이미 정리되어
있었습니다"로 다르게 문구), `skipped_days`(회색, "건너뜀 — 조치 불필요"), `failed_days`(빨강,
"확인이 필요합니다"). `message`는 서버가 이미 한국어로 주므로 그대로 렌더링한다(스펙 §6 —
별도 번역 불필요). `warnings`는 amber 텍스트 리스트로 하단에 붙인다.

`DayEditorPage.tsx`의 `handleSortSuccess()`가 `sorted_days`의 `day_id`들에 대해서만
`['days', dayId, 'items']`를 무효화한다 — 응답에 항목 배열이 없는 것은 ADR-0012의 의도된
설계(스펙 §7)라, `skipped_days`/`failed_days`는 애초에 캐시를 건드릴 이유가 없다(둘 다 쓰기가
없었다).

### 5. 마스터 환경설정 토글
