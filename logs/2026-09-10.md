# 2026-09-10 작업 로그

## 모바일 Day 간 드래그 앤 드롭 — 설계 확정 + 구조 변경 (senior-dev)

담당: senior-dev (오케스트레이터 위임). 사용자 후속 요청:
**"PC에서는 날짜가 탭으로 나뉘어있으니깐 해당 기능(드롭다운)처럼 해도될거같은데, 모바일에서는 드래그로도 옮겨지면 좋겠어."**

즉 어제(2026-09-09~10) 완성한 "일정을 다른 Day로 옮기기"에서 senior-dev가 의도적으로 배제했던
드래그 앤 드롭(ADR-0004 기각 대안)을 **모바일에 한해서만** 도입하는 요청.
이번 위임 범위는 **설계 + 상태/구조 변경까지**이고, 시각 효과·UI 세부 구현은 ui-dev 후속.

### 먼저 확인한 것 (코드 기준)

- `DndContext`와 `SortableContext`가 **둘 다 `ItineraryList` 안**에 있었다. 모바일은 Day 섹션마다
  `ItineraryList`를 렌더하므로 **Day 개수만큼 독립된 DndContext**가 존재했고, dnd-kit은 DndContext
  경계를 넘는 드래그를 지원하지 않으므로 **현재 구조에서는 Day 간 드래그가 원천적으로 불가능**했다.
  → 예상대로 "여러 Day를 아우르는 단일 DndContext로 재구성"이 이 기능의 전제조건.
- 자동 스크롤: `@dnd-kit/core` 6.3.1의 `DndContext`가 `autoScroll?: boolean | AutoScrollOptions`를
  **기본 활성**으로 내장 지원(`node_modules/@dnd-kit/core/dist/components/DndContext/DndContext.d.ts`,
  `hooks/utilities/useAutoScroller.d.ts`의 `threshold`/`acceleration`/`activator` 옵션 확인).
  모바일 뷰는 window를 스크롤하므로 **별도 구현이 필요 없다.**
- 터치 센서는 이미 `PointerSensor{distance:5}` + `TouchSensor{delay:150, tolerance:5}`로 M3(2026-09-04)에서
  튜닝돼 있었고, 드래그 리스너는 핸들(`⠿`, `touch-none`)에만 붙어 있어 제목 편집/스크롤과 분리돼 있었다.
- `useActiveDayOnScroll`은 스크롤 위치를 읽기만 하므로 드래그와 상태 충돌이 없다.

### 결정 (상세는 [ADR-0005](../docs/adr/0005-mobile-cross-day-drag-and-drop.md))

1. **모바일에만** Day 간 드래그. 데스크톱은 코드·동작 그대로(드롭다운 유지).
2. `DndContext` 소유권을 `ItineraryList` → 상위 뷰(`DayEditorDesktop`/`DayEditorMobile`)로 이동.
   모바일 = Day1~DayN 전체를 감싸는 1개, 데스크톱 = 활성 Day 하나를 감싸는 1개(**트리 모양이 변경 전과 동일**).
3. 드롭 해석은 `lib/dndDrop.ts`의 순수 함수 `resolveDrop()` 단일 소스(`reorder` / `move` / `null`).
4. **빈 Day에만** 컨테이너 droppable(`day:<id>`) 등록 — 항목이 없으면 드롭 대상 자체가 없어서 영원히
   옮겨올 수 없는 Day가 생기기 때문. 항목이 있는 Day는 항목 droppable만으로 충분.
5. 충돌 판정은 기존 `closestCenter` 유지(4번 덕에 컨테이너 ↔ 항목 경합이 없어 커스텀 캐스케이드 불필요).
6. 다른 Day로 드롭 = 그 Day **맨 뒤**에 삽입. 기존 `POST /api/items/{id}/move` 그대로 → **백엔드 변경 없음**.
   `target_position`은 추가하지 않고, 삽입선 대신 **목적지 Day 섹션 전체 하이라이트**로 표시.
7. 자동 스크롤은 dnd-kit 내장(기본값) 사용.
8. `TouchSensor` 값·핸들 전용 리스너는 **무변경**(검증된 값을 구조 변경과 같은 세션에 바꾸지 않는다).
9. **`MoveItemControl`(하단 시트) 유지** — 먼 Day 이동은 드래그가 비싸고, 드래그는 실패 가능한 제스처라
   단독 수단이 될 수 없다. 데스크톱과 컴포넌트를 공유 중이라 떼어내면 오히려 분기가 는다.
10. 낙관적 업데이트는 여전히 없음. 드래그 이동에서는 `jumpToDay`(목적지 자동 스크롤)를 **호출하지 않는다**
    — 이미 목적지를 보면서 떨궜는데 화면이 또 튀면 방해.

### 실제로 변경한 파일 (프론트 구조만, 시각 효과 없음)

- **신규** `frontend/src/lib/dndDrop.ts` — `dayDroppableId()`, `resolveDayIdOfDropTarget()`, `resolveDrop()`.
  항목 droppable id는 숫자(`item.id`), Day 컨테이너는 문자열(`day:<dayId>`)로 id 공간 분리.
- **신규** `frontend/src/hooks/useItineraryDndSensors.ts` — `ItineraryList`에 있던 센서 구성을 그대로 이동(값 무변경).
- `frontend/src/components/ItineraryList.tsx` — `DndContext`/센서/`handleDragEnd` 제거, `SortableContext` + 목록만 담당.
  props에 `dayId` 추가, `onReorder` 제거. `items.length === 0`일 때 빈 상태 문구에 `useDroppable`의 `setNodeRef` 부착
  (드롭 영역 확보용으로 `py-3`만 추가).
- `frontend/src/components/DayEditorDesktop.tsx` — 활성 Day 하나를 감싸는 `DndContext` 추가, `handleDragEnd`가
  `resolveDrop(..., { [activeDayId]: items })` 결과로 기존 `onReorderItems`를 호출. `DndContext`는 DOM 노드를
  만들지 않아 2단 그리드 레이아웃에 영향 없음.
- `frontend/src/components/DayEditorMobile.tsx` — 전체를 감싸는 `DndContext`(autoScroll 기본값) 추가,
  `onDragOver`에서 `resolveDrop()` 결과가 `move`일 때만 `dropTargetDayId`를 세팅하고 각 `<section>`에
  `data-drop-target="true"`로 노출(스타일은 ui-dev 몫), `onDragEnd`에서 reorder면 `onReorderItems`,
  move면 `onMoveItem(fromDayId, itemId, toDayId)`(=`jumpToDay` 미전달).
- **무변경**: `ItineraryItemCard.tsx`(핸들/편집/삭제/`MoveItemControl` 그대로), `MoveItemControl.tsx`,
  `DayEditorPage.tsx`(mutation·에러 처리 그대로), `types/dayEditor.ts`, `api/items.ts`, 백엔드 전체.

### 검증

- `npm run build`(`tsc -b && vite build`) 통과 — 타입 에러 없음.
- `npm run lint`(oxlint) — 기존 경고 3건(AuthContext/MapView) 그대로, **신규 파일·변경 파일에서 새 경고 없음**.
- `resolveDrop()` 단위 검증 14케이스 통과 (`node --experimental-strip-types`로 실제 `.ts` 파일을 직접 임포트해 실행):
  - **같은 Day 정렬 회귀**: 위→아래/아래→위 `arrayMove` 결과, 자기 자신 위 드롭 → null, `over` 없음/null → null,
    데스크톱처럼 Day 하나만 넘긴 컨텍스트 → 기존과 동일한 `orderedItemIds`.
  - **Day 간 이동**: 다른 Day 항목 위 드롭 → `{kind:'move', fromDayId, toDayId}`, 빈 Day 컨테이너(`day:3`) 드롭 → move,
    자기 Day 컨테이너 드롭 → null(no-op).
  - **방어**: 없는 항목 id, 없는 대상 id, 깨진 컨테이너 id(`day:abc`) → 전부 null.
- 백엔드는 손대지 않았으므로 서버 기동/DB 접근 없음(`dev.db` 무변경).
- **브라우저·실기 터치 확인은 미수행**(자동화 도구 없음 + 시각 구현이 아직 ui-dev 몫이라 지금 확인해도 반쪽).

### ui-dev 후속 구현 스펙 (이 세션에서 넘기는 작업)

아래만 하면 되고, **`lib/dndDrop.ts` / DndContext 배치 / API 호출 방식은 건드리지 말 것**(ADR-0005 결정 사항).

1. **드롭 대상 Day 하이라이트** — `DayEditorMobile`의 각 `<section>`에 이미 `data-drop-target="true"`가
   드래그 중에만 붙는다. 여기에 눈에 띄는 테두리/배경(예: `data-[drop-target]:ring-2 ring-slate-400 rounded-lg`)을 준다.
   **삽입선(insertion line)은 그리지 말 것** — 실제 삽입 위치는 항상 맨 뒤라서 거짓말이 된다.
   빈 Day의 "등록된 일정이 없습니다" 영역도 이 하이라이트에 포함되도록(섹션 단위라 자동으로 포함됨) 확인.
2. **`DragOverlay` 추가(모바일)** — 현재는 카드가 제자리에서 transform만 되고 `opacity: 0.5`라,
   상단 고정 지도 블록(`sticky ... z-10`) 밑으로 들어가면 **드래그 중인 카드가 지도에 가려 보이지 않는다.**
   `DayEditorMobile`의 `DndContext` 안에 `<DragOverlay>`를 두고 `onDragStart`에서 잡은 항목의 간단한 카드
   프리뷰를 렌더할 것(DragOverlay는 기본 `z-index: 999`라 지도 위로 뜬다). 원본 카드는 지금처럼 흐리게 유지.
3. **이동 실패 피드백 위치(모바일)** — 낙관적 업데이트가 없어서 이동이 실패하면 **아무 일도 안 일어난 것처럼 보인다.**
   `DayEditorPage`의 `moveItemError`는 화면 최상단에 있어 리스트 아래쪽에서 드래그한 사용자에게 안 보인다.
   모바일일 때는 하단 고정 배너(예: `fixed bottom-4 inset-x-4 z-40`, 탭하면 닫힘)로 띄울 것.
   상태(`moveItemError`)와 mutation은 그대로 쓰고 **표시 위치만** 바꾼다.
4. **실기 터치 확인 후 필요하면 자동 스크롤만 미세조정** — `DndContext`에
   `autoScroll={{ threshold: { x: 0, y: 0.2~0.3 } }}` 정도의 값 조정만 허용(직접 구현 금지).
   상단 고정 블록이 뷰포트 상단 40% 가까이를 덮고 있어 위쪽 자동 스크롤 발동 지점이 지도 아래에 있을 수 있다.
5. **하지 말 것**: `TouchSensor` 값 변경(M3 검증값), 드래그 중 다른 Day 항목을 비켜서게 하는 크로스 컨테이너
   프리뷰(ADR-0005에서 기각 — 로컬 상태 사본이 생겨 같은-Day 정렬이 회귀 위험에 노출됨), `MoveItemControl` 제거.

### 이슈/특이사항

## 모바일 Day 간 드래그 앤 드롭 — 시각/UI 구현 (ui-dev)

담당: ui-dev (오케스트레이터 위임). 위 senior-dev 스펙(ADR-0005 결정 6/7 + 이 로그의 "ui-dev 후속 구현 스펙" 4개 항목) 그대로 구현.
`lib/dndDrop.ts`의 `resolveDrop()`, `DndContext` 배치(누가 감싸는지), `TouchSensor` 값, `MoveItemControl.tsx`는 전혀 건드리지 않음(금지 사항 그대로 준수).

### 변경 내용

1. **드롭 대상 하이라이트** (`DayEditorMobile.tsx`) — 각 Day `<section>`에 이미 배선돼 있던
   `data-drop-target="true"`(드래그 중이고 `resolveDrop()` 결과가 `move`일 때만 세팅)에
   `data-[drop-target]:bg-slate-50 data-[drop-target]:ring-2 data-[drop-target]:ring-slate-400`
   (+ `rounded-lg`, `transition-colors`, `-mx-2 px-2`로 화면 좌우 여백에 맞춰 하이라이트 박스 폭 조정)를 추가.
   Tailwind v4의 데이터 속성 "값 무관 존재 여부" variant(`data-[drop-target]:`)를 사용 — 속성이 없을 때(정렬 중이거나
   드래그가 없을 때)는 자동으로 스타일이 빠진다. **삽입선은 그리지 않음** — 실제 삽입은 항상 그 Day의 맨 뒤이므로,
   특정 위치를 가리키는 표시는 senior-dev 스펙대로 의도적으로 배제(폴더에 파일을 떨구는 상호작용으로 통일).
   빈 Day의 "등록된 일정이 없습니다" 문구도 섹션 안에 있어 자동으로 하이라이트에 포함됨.

2. **`DragOverlay` 추가** (`DayEditorMobile.tsx`) — `onDragStart`에서 `event.active.id`(숫자, 항목 id)로
   `itemsByDayId`를 순회해 해당 항목과 그 Day 안에서의 index를 찾아 `activeDragItem` state에 저장.
   `<DndContext>` 안에 `<DragOverlay>{activeDragItem && <ItineraryItemDragPreview .../>}</DragOverlay>`를 추가.
   `ItineraryItemDragPreview`는 파일 내부에 새로 만든 프리젠테이션 전용 컴포넌트로, `ItineraryItemCard.tsx`의
   카드 배치(핸들 아이콘 ⠿ + 순번 배지 + 제목, `rounded-lg bg-white p-4 shadow`)를 그대로 재사용하되
   편집/삭제/`MoveItemControl` 같은 상호작용은 없음(드래그 중 "무엇을 옮기는지"만 보여주면 되므로).
   루트 태그는 `<li>`가 아니라 `<div>` — DragOverlay는 `<ol>` 트리 밖(포탈)에 렌더되므로 `<li>`를 쓰면 잘못된
   HTML 중첩이 된다. dnd-kit `DragOverlay`의 기본 `z-index: 999`가 상단 `sticky z-10` 지도보다 높아서,
   카드를 지도 영역까지 끌고 올라가도 더 이상 가려지지 않는다. 원본 카드는 기존 그대로 `opacity: 0.5`로 제자리에 남는다.
   `handleDragEnd`/`handleDragCancel`(신규, 기존엔 인라인 화살표 함수였던 것을 이름 붙은 함수로 분리)에서
   `activeDragItem`도 `dropTargetDayId`와 함께 초기화.

3. **이동 실패 에러 배너 위치** (`DayEditorPage.tsx`, 모바일 전용) — 기존 `{moveItemError && (...)}` 한 블록을

   커버하도록 넉넉한 쪽)으로 조정. **`stickyHeight`/`window.innerHeight` 기반 동적 계산은 하지 않음** — "직접

### 결정 (상세는 [ADR-0006](../docs/adr/0006-expense-payer-and-settlement.md))

1. **참가자 테이블 없음.** 두 이름은 `app/services/settlement.py`의 상수 `PARTICIPANTS = ("희경", "재승")`
   하나가 유일한 소스(스키마 검증 + 정산 계산 + 응답의 `participants` 필드가 전부 이걸 본다).
   - `Settings`(환경변수) 안은 **기각** — 배포 환경마다 달라질 값이 아니고, 어긋나면 한쪽에서만 422가 난다.
     이름을 바꾸면 어차피 DB `UPDATE`가 필요해서 "env 한 줄로 변경" 이점이 성립하지 않는다.
   - `paid_by_index: int`(0/1) 안도 기각 — 상수 순서를 바꾸면 기존 데이터 의미가 조용히 뒤집힌다.
2. **결제자 = `ItineraryItem.paid_by: str | None`** (NULL = 미지정). DB CHECK 제약 없음(이름 변경이
   마이그레이션 사안이 되면 안 됨 — 도메인 불변식이 아니라 "지금 이 앱을 쓰는 사람 목록").
3. **명시적 null 함정은 이번엔 반대로 판단**: `paid_by`/`cost_amount`/`cost_currency`는 nullable 컬럼이고
   "지우기"가 정상 조작이라 `{"paid_by": null}`을 **200으로 허용**한다(NOT NULL인 `title`/`text`는 422가 맞다).
   빈 문자열/공백도 None으로 정규화 — 프론트 `<select>`의 "미지정" 옵션 value가 보통 `""`이기 때문.
4. **정산은 순수 함수로 매번 계산, 저장하지 않음**(파생값이라 저장하면 무효화 관리가 생긴다).
   2명 고정이므로 최소 송금 알고리즘 없이 "총액/2 기준, 덜 낸 사람이 차액의 절반을 준다" 한 줄.
   참가자가 3명 이상이면 조용히 틀린 답 대신 `transfer: null`.
5. **결제자 미지정 지출은 정산에서 제외**하고 `unassigned_amount`/`unassigned_item_count`로 보고만 한다
   (누가 냈는지 추측하지 않음). `PARTICIPANTS`에 없는 옛 이름도 같은 통에 넣어 안전하게 퇴화시킨다.
6. **통화가 섞이면 환율 변환 없이** 기준 통화(`Trip.currency`) 항목만 합산하고, 나머지는
   `excluded_currencies`(통화별 합계+건수) + `has_mixed_currency` 플래그로 경고. `cost_currency`가 비어 있으면
   기준 통화로 간주(전부 NULL인 현 데이터에서 "통화 미상" 취급하면 모든 지출이 정산에서 빠진다).
   통화 코드는 저장/계산 양쪽에서 대문자·trim 정규화("krw " → "KRW") — 대소문자 차이로 같은 통화가
   합계에서 통째로 빠지는 게 이 설계에서 가장 눈에 안 띄는 실패 모드.

```jsonc
  "transfer": {"from_participant": "희경", "to_participant": "재승", "amount": 5000.0},  // 균형/지출0이면 null
  "unassigned_amount": 7000.0,             // 결제자 미지정 지출 (정산에서 빠짐)
  "unassigned_item_count": 1,
  "excluded_currencies": [{"currency": "JPY", "amount": 800.0, "item_count": 1}],
  "has_mixed_currency": true
}
```
일정 생성/수정 시 결제자·비용 전송 (기존 엔드포인트 그대로, 필드만 추가):
```
POST  /api/days/{day_id}/items   body: {"title": "...", "cost_amount": 10000, "cost_currency": "KRW", "paid_by": "희경"}
PATCH /api/items/{item_id}       body: {"paid_by": null}      // 미지정으로 되돌리기 (200)
                                 body: {"paid_by": ""}        // 같음 (200, NULL로 저장)
                                 body: {"paid_by": "철수"}     // 422 (허용값 안내 메시지 포함)
                                 body: {"cost_amount": -1}     // 422
```
`ItineraryItemRead`(일정 조회 응답)에 `paid_by: string | null`이 추가됐다 → 프론트 `types/models.ts`의
`ItineraryItem`에 필드 추가 필요. `cost_amount`/`cost_currency`는 원래 있었다.

FastAPI `TestClient` + 임시 SQLite(`tempfile`)로 **86개 체크 전부 통과**. `dev.db`는 환경변수 오버라이드로

### 이슈/특이사항

- **`cost_amount`에 NaN을 보내면 422가 아니라 처리되지 않은 500이 나던 기존 경로 발견 → 차단.**
  파이썬 `json.loads`는 JSON 표준에 없는 `NaN`/`Infinity` 리터럴을 기본으로 받아들이는데, FastAPI 기본
  422 핸들러가 `exc.errors()`의 `input`에 그 값을 그대로 실어 응답하려다 `json.dumps`에서 터진다
  (에러 응답 직렬화 실패 → 500). `app/main.py`에 기본 핸들러와 동일하되 비유한 float만 문자열로 바꾸는
  `RequestValidationError` 핸들러를 추가했다. 응답 형태(`{"detail": [...]}`)는 그대로라 프론트
  `extractErrorMessage()`에 영향 없음. 브라우저 `JSON.stringify`는 NaN을 `null`로 바꾸므로 정상 경로에서는
  발생하지 않지만, 비용 검증을 추가하면서 도달 가능한 경로가 돼 막았다.
- `cost_amount` 음수 검증을 이번에 함께 넣었다 — 지금까지 검증이 없었는데 이 값이 **처음으로 합산**되기
  시작하므로, 음수 한 건이 "누가 누구에게 얼마"를 통째로 뒤집는다. 기존 데이터가 전부 NULL이라 안전.
- `Trip.name`/`ItineraryItem.title` 길이 상한 없음(Backlog Tier 2)은 이번에도 손대지 않았다.

## 참가자 닉네임을 마스터 환경설정으로 — 저장 방식 재설계 + 백엔드 (senior-dev)

> 작업 실행일은 2026-09-11이지만 바로 위 "예산/지출 추적 + 정산" 작업의 연속이라 이 파일에 이어서 기록한다.

### 사용자 요청 (재설계의 계기)

바로 위 섹션(ADR-0006)을 마친 직후 사용자가 두 가지를 요청했다:

1. "희경, 재승 닉네임은 **마스터 환경설정에서 변경 가능**하게 해주고"
2. "마스터 환경설정은 **웹 메인페이지에 보이게** 해줘"

ADR-0006의 설계는 **"이름 변경 = 드문 배포 이벤트"**라는 전제 위에 서 있었다(코드 상수 `PARTICIPANTS` +
`paid_by`에 표시 이름 문자열 저장, 이름 바꾸려면 상수 수정 + `UPDATE` + 배포). 이 요청으로 그 전제가
사라졌으므로 — 이름 변경이 로그인한 사람이면 언제든 누르는 **평범한 런타임 기능**이 된다 — 그 위에 세운
저장 방식을 다시 판단했다.

### 두 안을 비교하고 (B)를 택했다

| | **(A)** 표시 이름 유지 + 이름 변경 시 지출 일괄 `UPDATE` | **(B)** 슬롯 키 저장 + 이름은 설정에서 조회 **(채택)** |
|---|---|---|
| 이름 변경 시 쓰는 행 | 설정 1행 + **매칭되는 지출 전부**(상한 없음) | 설정 **1행** |
| 지금 필요한 데이터 변환 | 없음 | 없음 (둘 다 `paid_by`가 전부 NULL이라) |
| 부분 실패하면 | 설정은 새 이름 / 지출은 옛 이름 → 그 지출이 **정산에서 조용히 사라짐** | 실패할 다중 쓰기가 없음 |
| 이름 서로 맞바꾸기 | 임시값 없이는 두 사람 지출이 **뒤섞임** | 설정 값 두 개 교체로 끝 |
| 한쪽을 상대 이름으로 | 두 사람 지출이 **복구 불가능하게 병합** | 그냥 422로 거부하면 되는 표시 문제 |
| `paid_by` pydantic 검증 | 허용값이 DB에 있어 **validator가 DB를 읽어야 함** → 검증이 라우터로 흩어짐 | `PARTICIPANT_KEYS` 정적 비교 그대로 유지 |
| DB 콘솔 가독성 | `paid_by='희경'` 바로 읽힘 | `participant_1` → `app_settings` 한 행 함께 조회 |
| 이름 변경 후 프론트 캐시 | 일정 캐시에 옛 이름이 남아 전부 무효화 필요 | `['settings']`만 무효화 |

**결정적 이유는 실패 모드의 비대칭.** (A)에서 이름 변경은 개수 상한이 없는 데이터 재작성이고, 재작성을
놓친 행은 `compute_settlement`에서 "모르는 이름 → 미지정"으로 빠진다 = **에러 없이 금액이 정산에서 사라진다.**
이 앱에서 가장 눈에 안 띄는 실패 모드이며, ADR-0006 스스로 같은 종류의 위험(통화 대소문자 불일치)을
"가장 눈에 안 띄는 실패 모드"라고 부르며 양쪽에서 막았다. (B)에서는 이름 변경이 **정의상** 지출 데이터를
건드릴 수 없다.

**지금이 이 재설계가 공짜인 유일한 시점이었다**: `093074f849bc`(`paid_by` 컬럼 추가)가 운영 Neon에 아직
미적용이고, 로컬 `dev.db`에도 값이 전부 NULL이다(일정 3건 확인). 변환할 행이 0건 — 이 비용은 앞으로
올라가기만 한다.

ADR-0006이 기각했던 `paid_by_index: int`(0/1)와 다른 점: 저장값이 **순서 기반 숫자가 아니라 이름 붙은 키
문자열**이다. 배열을 재정렬해도 `participant_1`은 계속 `participant_1`이라 "순서를 바꾸면 의미가 뒤집힌다"는
그때의 기각 근거가 성립하지 않는다.

상세 근거와 기각한 대안 전체는 [ADR-0007](../docs/adr/0007-runtime-participant-names.md)
(ADR-0006 상단에는 이 프로젝트 관례대로 "후속: ADR-0007" 포인터 한 줄만 추가하고 본문은 그대로 뒀다).

### 결정 요약

1. **설정은 DB에 둔다** — 새 싱글턴 테이블 `app_settings`(`id=1` 고정 PK). `app/config.py`의
   `Settings`(pydantic-settings/`.env`)와 **다른 것**이다: 그쪽은 재배포해야 바뀌고 배포 환경마다 달라지는
   값(DB URL/시크릿/CORS)이고, 이건 화면에서 실시간으로 바뀌어야 하는 값이다.
   **조회는 행을 만들지 않는다**(행이 없으면 모델 기본값 사용) — 읽기 요청이 조용히 쓰기 트랜잭션이 되면
   동시 조회가 PK 충돌로 500이 될 수 있다. 마이그레이션이 기본값 행을 시드하므로 실제로는 처음부터 있다.
   여행(Trip)별이 아니라 **앱 전역**이다(같은 두 사람이 모든 여행을 쓰므로).
2. **`ItineraryItem.paid_by`에는 슬롯 키**(`participant_1`/`participant_2`)를 저장. 표시 이름은 표시할 때만 붙인다.
3. **`compute_settlement()`가 참가자를 인자로 받는다** — 숨은 전역을 만들지 않아 DB 없이 계산을 테스트할 수 있다는
   ADR-0006의 성질을 유지.
4. **이름은 정산 응답에는 싣고 일정 응답에는 안 싣는다.** 기준: *이름을 오래 사는 캐시에 복사하지 않는다.*
   정산은 매번 계산하는 파생 읽기 모델이라 계산 시점 이름을 함께 줘도 낡을 수 없지만, 일정은 저장된 엔티티라
   이름을 복사하면 이름 변경 후 캐시에 옛 이름이 남는다.
5. **검증**: 빈 값/공백/명시적 null/모르는 키/20자 초과/두 이름 중복 → 전부 422.
   `paid_by`(명시적 null = "미지정으로 되돌리기" = 200)와 **반대 방향**인데, 판단 기준은 ADR-0006과 동일하다
   (컬럼이 nullable인가, null이 의미 있는 상태인가 — 이름은 둘 다 아니다).
   "안 바꿈"은 null이 아니라 **키를 빼는 것**으로 표현한다. `dict[str, str]` 타입 선언만으로 pydantic이 null을 거른다.
6. **마이그레이션은 이어 붙인다**: `d6eea980ecbe` → `093074f849bc` → `0e8fd49e8ad8`.
   이미 로컬에 적용된 `093074f849bc`를 고쳐 합치지 않는다(적용된 리비전 사후 편집 = alembic에서 가장 흔한 사고).
   새 마이그레이션은 `paid_by`를 **아예 건드리지 않는다** — 변환할 데이터가 0건이라서.

### API 계약 (ui-dev에게 넘기는 부분)

```
GET   /api/settings        (세션 쿠키 필요)
→ 200 {"participants": [{"key": "participant_1", "name": "희경"},
                        {"key": "participant_2", "name": "재승"}]}
→ 401 Not authenticated

PATCH /api/settings        (세션 쿠키 필요)
body: {"participants": {"participant_1": "새이름"}}      // 바꿀 슬롯만 (부분 갱신)
      {"participants": {"participant_1": "A", "participant_2": "B"}}   // 둘 다
      {"participants": {}}                               // no-op, 200 + 현재 값
→ 200 AppSettingsRead (항상 **전체 목록**을 준다 → 응답을 그대로 캐시에 넣으면 된다)
→ 401
→ 422  빈 값/공백만 / 명시적 null / 모르는 키 / 20자 초과 / 두 사람 이름이 같아짐
```
- 요청 바디가 `{슬롯 키: 이름}` **맵**인 이유: 키가 이미 GET 응답의 어휘라, 받은 키를 그대로 돌려보내면 되고
  `participant_1_name` 같은 필드명을 따로 외울 필요가 없다.
- **두 이름 맞바꾸기(`{"participant_1": "재승", "participant_2": "희경"}`)는 정상 통과한다** — 서버가 부분 갱신을
  적용한 *결과*를 한 번에 검사하므로 중간 상태의 중복으로 거부되지 않는다.
- 에러 `detail`은 영어(기존 정책). 중복 이름은 문자열 detail, 나머지는 pydantic 배열 detail — 둘 다 기존
  `extractErrorMessage()`가 처리하는 형태다.

정산 응답(**ADR-0006 대비 깨는 변경** — 프론트 미구현이라 소비자 없음):
```jsonc
{
  "trip_id": 1,
  "currency": "KRW",
  "participants": [{"key": "participant_1", "name": "희경"}, {"key": "participant_2", "name": "재승"}],
  "per_person": [
    {"participant": {"key": "participant_1", "name": "희경"}, "paid": 10000.0, "item_count": 2}
  ],
  "total": 30000.0,
  "per_person_share": 15000.0,
  "transfer": {"from_participant": {"key": "participant_1", "name": "희경"},
               "to_participant":   {"key": "participant_2", "name": "재승"},
               "amount": 5000.0},          // 균형/지출0이면 null
  "unassigned_amount": 7000.0, "unassigned_item_count": 1,
  "excluded_currencies": [{"currency": "JPY", "amount": 800.0, "item_count": 1}],
  "has_mixed_currency": true
}
```
즉 `participants`는 `string[]` → `{key,name}[]`, `per_person[].participant`와 `transfer.from/to_participant`는
`string` → `{key,name}` 객체가 됐다.

일정 API(`paid_by`)의 **허용값이 이름에서 키로 바뀌었다**:
```
POST  /api/days/{day_id}/items   {"title":"호텔","cost_amount":10000,"paid_by":"participant_1"}
PATCH /api/items/{item_id}       {"paid_by": "participant_2"}   // 200
                                 {"paid_by": null}              // 200 (미지정으로 되돌리기)
                                 {"paid_by": ""}                // 200 (NULL로 저장)
                                 {"paid_by": "희경"}             // 422 ← 이름은 더 이상 허용값이 아님
```
`ItineraryItemRead.paid_by`도 **키**를 돌려준다(`"participant_1"`). 이름으로 보여주려면 `/api/settings`를
받아 변환해야 한다.

### ui-dev 후속 구현 스펙 (화면 구현은 이번 위임 범위 밖)

**배치 요구(사용자 명시)**: "마스터 환경설정"은 **메인페이지 = 여행 목록(`frontend/src/routes/TripListPage.tsx`)에서
진입 가능**해야 한다. 예: 페이지 헤더 우측의 톱니바퀴 아이콘 버튼. 화면 자체를 모달로 할지 인라인 섹션으로 할지는
ui-dev 판단(참고: 이 페이지는 이미 `TripChecklist` 펼치기 섹션과 `OutOfRangeDaysModal` 모달 두 패턴을 다 쓰고 있다.
설정은 여행 카드에 속하지 않는 **페이지 전역** 기능이라 카드 안 섹션은 부적절해 보인다).

1. `api/appSettings.ts` 신설 — `getAppSettings()`, `updateParticipantNames(patch: Record<string, string>)`.
   타입 `Participant = { key: string; name: string }`.
2. **react-query 키는 `['settings']`** 권장. 이름이 필요한 화면(결제자 선택박스, 일정 카드의 결제자 표시,
   정산 결과)이 전부 이 쿼리를 구독하게 한다.
3. **이름 변경 성공 후 무효화해야 하는 캐시** (이게 이 설계의 핵심 이점이자 주의점):
   - `['settings']` — **필수**. 이름 자체.
   - `['trips', tripId, 'settlement']`(정산 쿼리를 만들 때의 키) — **필수**. 정산 응답이 계산 시점 이름을
     문자열로 품고 있어서 갱신하지 않으면 옛 이름이 남는다.
   - `['days', dayId, 'items']` — **무효화 불필요**. 일정 응답에는 키만 있고 이름이 없다. 화면은 `['settings']`가
     갱신되는 순간 자동으로 새 이름을 렌더링한다. (이름을 일정 응답에 싣지 않은 이유가 정확히 이것이다.)
   - 간단히 `queryClient.invalidateQueries()`로 전부 날려도 되지만, 위 구분을 알고 있는 편이 낫다.
4. **결제자 선택박스**는 이름을 하드코딩하지 말고 `/api/settings`로 만든다:
   `<option value="">미지정</option>` + `participants.map(p => <option value={p.key}>{p.name}</option>)`.
   **서버로 보내는 값은 `p.key`이지 `p.name`이 아니다.**
5. **일정 카드에서 결제자 표시**: `participants.find(p => p.key === item.paid_by)?.name ?? item.paid_by`.
   폴백을 `item.paid_by`(키 원문)로 두면 설정 조회가 실패해도 화면이 비지 않는다.
6. **폼 검증은 클라이언트에서 1차 차단** 권장(불필요한 422 왕복 방지, `TripChecklist`의 200자 제한과 같은 패턴):
   빈 값 저장 버튼 비활성화, `maxLength={20}`, 두 이름이 같으면 저장 비활성화 + 안내. 서버도 전부 막지만
   메시지가 영어다.
7. 바뀐 값만 보내도 되고 둘 다 보내도 된다. 안 바꾼 슬롯을 `null`로 보내면 **422**다(생략하거나 현재 값을 보낼 것).
8. 위 섹션(ADR-0006)에 적어둔 ui-dev 후속 제안(비용/결제자 입력 UI, 정산 결과 표시 위치, `transfer: null` /
   `unassigned_*` / `has_mixed_currency` 안내 문구)은 **그대로 유효**하다. 단 `types/models.ts`의
   `ItineraryItem.paid_by`는 "이름"이 아니라 **키** 문자열이고, 정산 응답 타입은 위의 새 형태로 만들 것.

### 1. 마스터 환경설정 화면 (메인페이지 진입 — 사용자 명시 요구사항)

- `frontend/src/routes/TripListPage.tsx` 헤더에 `<h1>여행 목록</h1>`과 나란히 톱니바퀴(⚙️) 버튼을 추가.
  클릭하면 신규 `components/AppSettingsModal.tsx`가 뜬다. **모달로 택한 이유**: 이 페이지는 이미
  `TripChecklist`(카드 안 펼치기 섹션)와 `OutOfRangeDaysModal`(모달) 두 패턴을 쓰고 있는데, 설정은
  특정 여행 카드에 속한 정보가 아니라 **페이지 전역** 기능이라 카드 안에 넣을 자리가 없다. 스펙이 명시한
  "여행 카드 안이 아니라 페이지 전역"을 모달로 만족시켰다(`OutOfRangeDaysModal`과 같은
  `fixed inset-0 ... bg-black/40` 오버레이 패턴 재사용).
- `AppSettingsModal`은 `['settings']`를 로드하는 부모와, 데이터가 도착한 뒤에만 마운트되는
  `SettingsForm` 자식으로 나눴다. 처음엔 `useEffect(() => { setName1(data.participants[0]?.name) }, [data])`로
  로컬 input을 채웠는데, oxlint(`react/set-state-in-effect`)가 "이펙트 안에서 setState하면 렌더가
  한 번 더 발생한다"고 경고했다. `TripEditForm`(이 저장소에 이미 있는 패턴 — `trip` prop이 있어야만
  렌더되므로 `useState(trip.name)` 초기값만으로 충분)과 같은 방식으로 바꿔 이펙트 없이 해결 — 데이터가
  없으면 `SettingsForm` 자체를 렌더하지 않고, 데이터가 도착하는 순간 처음으로 마운트되면서 그 시점 값으로
  `useState`가 초기화된다.
- 저장 폼: 참가자 2명의 이름 input 두 개. 클라이언트 검증(빈 값/공백 제출 버튼 비활성화, 두 이름이 같으면
  비활성화 + 안내 문구, `maxLength={20}`)은 서버 규칙(ADR-0007 결정 6)을 그대로 미러링. 제출 시 **바뀐
  슬롯만** `{participant_1: "..."}` 형태로 `PATCH /api/settings`에 보낸다(요청 사항의 "간단하게 바뀐
  필드만" 지시대로 — 둘 다 안 바뀌었으면 API 호출 없이 그냥 닫음). 서버 422는 기존 `extractErrorMessage()`로
  표시.
- **저장 성공 시 `['settings']`만 invalidate**(지시받은 그대로, `['days', dayId, 'items']`는 건드리지
  않음 — 일정 응답엔 키만 있고 이름이 없다). 이 하나의 무효화가 결제자 선택박스(`AddItemModal`,
  `ItineraryItemCard`)와 정산 화면(`TripSettlement`) 전체에 새 이름을 자동으로 퍼뜨린다.

### 2. 일정에 비용/결제자 입력

- `AddItemModal.tsx`의 "직접 입력" 탭: 제목 입력 옆에 금액 `<input type="number" min="0">`(선택, 비우면
  `cost_amount` 필드 자체를 생략 — undefined는 axios가 JSON에서 빼줌)과 결제자 `<select>`(옵션은
  `['settings']` 쿼리로 만든 "미지정"+참가자 2명)를 추가. 통화 입력란은 지시대로 **만들지 않음** — 비우면
  서버가 여행 기준 통화로 처리한다.
- `ItineraryItemCard.tsx`: 제목 줄 아래 항상 노출되는 2번째 줄에 같은 형태의 금액 input(blur 시 커밋)과
  결제자 select(변경 즉시 커밋)를 추가했다. "편집 모드로 들어가야 보이는" 제목 인라인 수정과 달리 상시
  노출을 택한 이유: 비용/결제자는 값이 없는 상태(0/미지정)도 정상이라 "클릭해야 보이는 숨은 필드"로
  두면 존재 자체를 모르고 지나치기 쉽다.
  - 금액 draft 상태는 `null`(= "로컬 편집 중 아님")과 문자열(편집 중 입력값) 두 가지로 관리하고, 렌더 시
    `costDraft ?? String(item.cost_amount ?? '')`로 파생시켰다. `useEffect`로 `item.cost_amount`가
    바뀔 때 draft를 동기화하는 최초 구현은 위 설정 모달과 같은 `set-state-in-effect` 경고를 냈고, 커밋
    후 `setCostDraft(null)`로 되돌려 다음 렌더가 서버 값(`item.cost_amount`)에서 다시 파생되게 하는
    방식으로 바꿔 이펙트 없이 해결했다.
  - 클라이언트 1차 차단: 음수/NaN이면 서버에 보내지 않고 조용히 기존 값으로 되돌린다(불필요한 422
    왕복 방지, `TripChecklist`의 200자 제한과 같은 패턴).
- 두 곳 모두 **서버로는 `p.key`를 보내고 `p.name`은 화면 표시에만 쓴다**(ADR-0007 요구사항 그대로 —
  이름을 보내면 422).
- **일정 카드의 결제자 표시**는 `<select>`의 현재 값을 `item.paid_by ?? ''`로 두고, 옵션 라벨은
  `participants`에서 키로 찾은 이름을 쓴다(스펙의 `participants.find(p => p.key === item.paid_by)?.name`
  패턴 그대로, 다만 select라서 폴백 텍스트 대신 "미지정" 옵션이 곧 폴백 역할을 한다).

### 3. 정산 결과 표시

- `TripListPage.tsx`의 각 여행 카드에 신규 `components/TripSettlement.tsx`를 `TripChecklist` 바로 아래
  추가 — **`TripChecklist`와 완전히 같은 패턴**(`useState(false)` + `enabled: isOpen`인 `useQuery`,
  쿼리 키 `['trips', tripId, 'settlement']`)이라 접힌 카드는 API를 한 번도 부르지 않는다.
- 펼쳤을 때 반드시 보여줘야 한다고 지시받은 세 가지를 전부 구현:
  - `transfer`가 `null`이면 "정산할 것이 없습니다"(별도 에러 스타일 없이 평범한 안내 텍스트로 — 실제로
    에러가 아니므로 빨간색을 쓰지 않았다).
  - `unassigned_item_count > 0`이면 "결제자 미지정 지출 N건(금액)은 정산에서 제외됐습니다"(amber 톤 —
    기존 페이지에서 경고성 안내에 쓰던 색 그대로, `TripListPage`의 날짜 범위 경고와 같은 계열).
  - `has_mixed_currency`면 "다른 통화 지출 N건은 환율 변환 없이 합산되지 않았습니다"(`excluded_currencies`의
    `item_count`를 합산해 건수로 표시).
  - `transfer`가 있으면 지시받은 문구 형태 그대로 "{from.name}이(가) {to.name}에게 {amount}원을 보내면
    됩니다."
- **참가자 표시 이름은 정산 응답에 실린 이름보다 `['settings']` 캐시를 우선한다.** 오케스트레이터 지시가
  이름 변경 시 무효화할 캐시를 `['settings']` 하나로 한정했는데, 정산 응답은 계산 시점 이름을 값으로
  들고 있어서(ADR-0007 결정 4) 그 응답 자체는 이름이 바뀌어도 갱신되지 않는다. `TripSettlement`가
  `['settings']`도 함께 구독해(같은 캐시라 추가 API 호출 없음 — 다른 컴포넌트가 이미 채워둔 값을 그대로
  읽는 흔한 경우가 대부분) `per_person`/`transfer`의 `participant.key`로 최신 이름을 찾아 우선 표시하고,
  못 찾으면(아직 설정 쿼리가 없을 때) 응답에 실린 이름으로 폴백한다. 이렇게 하면 지시받은 범위(`['settings']`
  단독 무효화)를 넘지 않으면서도 이미 펼쳐져 있던 정산 패널이 이름 변경 직후 낡은 이름을 보여주는 사고를
  피한다.

### 1. 백엔드 — 독립 TestClient 검증 (58/58 통과)

- **핵심 시나리오 통과**: 희경(participant_1) 10,000 / 재승(participant_2) 20,000 지출을 키로 등록 →
  `GET /api/settings`로 기본 이름 확인 → `PATCH /api/settings`로 이름 변경 → 정산 재조회 시 총액(30,000)/
  1인당(15,000)/송금 방향·금액(5,000) 전부 불변, 화면 이름만 새 이름으로 바뀜, **DB의
  `ItineraryItem.paid_by` 값이 세션 내내 `participant_1`/`participant_2` 그대로임을 직접 SELECT로 확인**.
  이 설계의 핵심 주장(이름 변경이 지출 데이터를 건드리지 않는다)이 실제로 성립함.
- **정산 방향 계산 검증**: 희경 10,000 / 재승 20,000 → 총 30,000, 1인당 15,000, **희경(적게 낸 사람) → 재승
  5,000** 송금이 맞음(직접 계산으로 대조 확인).
- `paid_by`에 이름 문자열("희경")을 보내면 422로 거부됨을 확인.
- 결제자 미지정 지출(7,000원)이 `unassigned_amount`/`unassigned_item_count`로 정확히 보고되고 정산
  총액에서 제외됨을 확인.
- 통화 혼합(JPY 800) 시 `has_mixed_currency`/`excluded_currencies` 정확, 저장 시 `"jpy "` → `"JPY"`
  정규화 확인.
- `PATCH /api/settings` 검증 전수 확인 — 빈 값/공백/명시적 null(슬롯 하나)/`participants` 자체 null/
  21자/두 슬롯 이름 중복/모르는 슬롯 키 → **전부 422이고 거부 직후 값이 실제로 안 바뀌었음을 재조회로
  확인**. 정확히 20자는 허용. **두 이름 맞바꾸기(`participant_1`↔`participant_2`)는 200으로 정상 통과**
  (중간 상태가 아니라 최종 결과 기준 검증이 실제로 그렇게 동작함을 확인).
- 인증: `GET/PATCH /api/settings`, `GET /api/trips/{id}/settlement` 전부 미인증 401.
- `app_settings` 행이 없는 첫 조회에서 기본값("희경"/"재승")이 오류 없이 반환되고, **조회 자체가 행을
  만들지 않음을 DB 직접 조회로 확인**(연속 조회 2회도 정상, PK 충돌 없음).
- 트립 격리(다른 트립 지출이 섞이지 않음) 확인, 없는 트립 404 확인.

### 백엔드 422 응답 형식 교차 확인

`TestClient`로 `require_session`을 오버라이드하고 확인한 실제 응답(존재하지 않는 item/day id에도 요청 바디
검증이 라우터 로직보다 먼저 실행돼 422가 그대로 재현됨):

```
PATCH /api/items/999999 {"cost_amount": -5} -> 422
{"detail": [{"type": "value_error", "loc": ["body", "cost_amount"], "msg": "Value error, cost_amount must not be negative", ...}]}

POST /api/days/999999/items {"source": "manual", "title": "test", "cost_amount": -3} -> 422
{"detail": [{"type": "value_error", "loc": ["body", "cost_amount"], "msg": "Value error, cost_amount must not be negative", ...}]}
```

`extractErrorMessage()`는 `Array.isArray(detail) && typeof detail[0]?.msg === 'string'` 조건으로 이 형태를
정확히 처리해 `"Value error, cost_amount must not be negative"`를 화면에 뽑아낸다 — 프론트가 기대하는
포맷과 백엔드 실제 응답이 일치함을 확인.

- **보통**: 없음. 지난 라운드에서 지적한 [보통] 이슈(콜백 부재로 인한 무피드백)는 해소됨.

  1. `ItineraryItemCard.tsx`의 `commitCost()`는 성공/실패와 무관하게 `onUpdateItem(...)` 호출 직후

  2. 같은 함수에서 `parsed === item.cost_amount`(값이 실제로 안 바뀐 경우)인 분기에서는
