### 1. 원인 조사 — 앵커링 코드는 정상이었다. 깨지는 곳이 **네 군데 따로** 있었다

ADR-0009는 1번을 이미 설계했다고 적고 있어서("전날 마지막 지점을 다음날 시작 앵커로"),
먼저 **목(mock) 시나리오로 실제 재현**부터 했다(`scratchpad/repro_0914.py`, 외부 API 0회).
`order_day_places()`/`last_coords()` 자체는 설계대로 돌고 있었고, 문제는 그 앞뒤였다.

| # | 원인 | 재현된 증상 |
|---|---|---|
| A | **LLM이 같은 도시인데 날마다 다른 호텔을 제안한다.** 프롬프트에 "같은 숙소를 반복" 한 줄이 있었지만 **서버가 검사하지 않았다.** | Day1 라마다플라자 → Day2 홀리데이인 (같은 광주) |
| B | **숙소 폴백의 "1km 격자 캐시"가 연박을 보장하지 못한다.** 캐시 키가 **그날 동선의 중심 좌표**라 같은 도시라도 날마다 중심이 1km 이상 움직이면 키가 갈라져 Nearby를 또 부르고 다른 호텔이 나온다. ADR-0009 결정 5의 "자연스럽게 같은 호텔 연박이 된다"는 **사실이 아니었다.** | 폴백 호출 2회(35.1459,126.8568 / 35.1345,126.9955) → 서로 다른 호텔 |
| C | **하루 6곳 상한을 `places[:6]`로 앞에서부터 잘랐다.** LLM이 숙소를 목록 끝에 적으면(흔하다) 숙소가 조용히 사라지고 `lodging_missing` 플래그도 안 서서 **폴백조차 안 돈다.** | 그날 숙소 없음 → 다음 날 앵커가 식당 |
| D | **`departure`가 항상 "그날 맨 뒤"였다.** 도시 이동일에 출발 거점(떠나는 도시)을 넣으면 완도에서 하루를 보낸 일정 **마지막 줄에 "광주공항"**이 찍힌다. | `Day2: [arrival]완도버스터미널 → [meal]완도 전복식당 → [departure]광주공항 → [lodging]완도호텔` |

D는 **1번과 2번이 같은 뿌리에서 만나는 지점**이다(그날 숙소가 없으면 다음 날 시작 앵커가
"떠나온 도시"가 된다). 2번(이동수단)은 원인 조사가 필요 없었다 — **설계에 아예 없었다.**
ADR-0009 결정 6은 거점의 *위치*만 정했고 *종류*는 모델에 맡겼는데, 서버가 그걸 볼 방법이 없었다.

### 2. 결정 (전부 [ADR-0010](../docs/adr/0010-lodging-continuity-and-transport-terminals.md)에 기록)

ADR-0009를 뒤집지 않는 **보완**이다(append-only 원칙에 따라 ADR-0009 머리말에 "후속" 포인터만 추가).

- **숙소 연속성은 프롬프트가 아니라 서버 후처리가 강제한다** — 같은 도시에 머무는 동안
  **전날 숙소를 승계**한다(LLM이 다른 호텔을 냈어도 교체, 빠뜨렸으면 채움). 도시가 바뀌는 날에만
  새 숙소를 쓴다. 승계는 이미 확정된 항목의 복사라 **Places 호출 0회**이고, 원인 B의 중복 폴백
  호출도 함께 사라진다. 프롬프트도 같이 강화했지만(연박이 기본), **보증은 서버 쪽**이다 —
  검사 가능한 불변식을 모델 준수 확률에 맡기지 않는다(ADR-0009가 장소 존재를 Places로 확정한
  것과 같은 기준). "가까우면 같은 숙소로 간주"하는 억지 통일은 하지 않았다(임계 거리에 근거가
  없고, 승계 규칙을 쓰면 같은 도시에서 서로 다른 호텔이 남는 경우 자체가 없어진다).
- **다음 날 시작 앵커 = "전날의 숙소"** (전날 마지막 항목이 아니라). 숙소가 없거나 종점이
  `departure`인 날에 둘이 갈라지고, 하필 그때 앵커가 엉뚱해진다. `route_order.py`는 그대로
  순수 모듈로 뒀다(무엇이 앵커인가는 도메인 판단이라 호출자가 넘긴다).
- **`departure`의 고정 위치를 날짜 의존으로** — 마지막 날은 맨 뒤(종점), 그 외 날은 **맨 앞**
  ("오늘 이 도시를 떠난다"). 도시 이동일은 `departure` → `arrival` → 나머지 순이 되고 그날
  동선 기준점은 `arrival`이다(여러 `PIN_FIRST` 중 마지막을 앵커로 삼는 기존 규칙이 그대로
  맞아떨어져 `route_order.py` 로직은 무수정). `arrival`/`departure`/`lodging`은 하루 1개씩만 받는다.
- **하루 상한 절단을 우선순위 방식으로** — 거점·숙소를 먼저 확보하고 남는 자리에 관광/식사를
  채운다. **상한 값 6은 그대로 둔다**(그 값이 비용의 곱셈 인자 — ADR-0009 결정 3). 자를 대상을
  바꾸는 건 공짜다.
- **이동 거점은 `transport`(일 단위) + Places `types`로 짝을 맞춘다** — LLM 출력에
  `days[].transport`(flight/train/bus/ferry/car/none, 필수 아님) 추가. 서버는 선언된 수단(없으면
  거점 타입에서 추론, 두 쪽이 엇갈리면 후보 2개를 순서대로 시도)과 **다른 수단의 시설이라고
  Places가 명시한 거점만** 손대고, `"{도시} {공항|기차역|버스터미널|여객선터미널}"`로 **한 번만**
  다시 찾아 **전부 맞출 수 있을 때만** 교체한다(결과는 (도시,수단) 캐시로 3안 공유). 못 맞추면
  **지우지 않고** 원본 유지 + 경고. `transit_station`처럼 역·터미널에 모두 붙는 타입은 판정
  집합에서 일부러 뺐다(근거가 애매한 걸 고치면 멀쩡한 거점을 엉뚱한 곳으로 바꾼다).
- **`transport`는 DB에 저장하지 않는다** → **스키마 변경/마이그레이션 없음.** 컬럼 추가·kind
  세분화·도시↔공항 매핑 표는 전부 기각(근거는 ADR-0010 결정 6의 표). 저장 정보는 이미 거점
  이름에 들어 있다("광주공항"/"광주송정역"/"완도공용버스터미널").
- **Places 필드마스크도 그대로다** — `places.types`가 이미 `SEARCH_FIELD_MASK`에 있어서
  **타입 검증에 추가 비용이 0**이다. 늘어나는 유료 호출은 "짝이 실제로 어긋난 날"의 도시·수단당
  1회뿐이고, 정상 경로는 0회다. 반대로 연박 승계가 Nearby 폴백을 대체해 **전체적으로는 줄어든다**.

### 5. 알려진 한계 (의도적으로 감수한 것)

- **연박 강제가 사용자 의도를 이길 수 있다** — 같은 도시에서 일부러 숙소를 옮기는 여행이라면
  생성된 일정에서 숙소 항목을 편집해야 한다(AI 추천은 초안이라는 ADR-0009의 전제).
- **야간 기차/버스처럼 늦게 떠나는 이동도 `departure`가 맨 앞으로 간다**(시각 정보가 없다).
- **수단 판정은 Places 타입이 있을 때만 동작한다** — "완도항"처럼 타입이 일반 POI인 거점은
  그냥 통과하므로 어긋난 조합이 남을 수 있고 경고도 안 뜬다.
- **하루 도시 이동 1회를 전제한다**(버스로 나와 배를 타는 복합 구간은 한 수단으로 표현됨).
- **A→B→A로 되돌아오는 일정은 직전 날만 비교**하므로 A의 첫 숙소로 돌아가지는 않는다.

## QA [보통] 이슈 수정 — 숙소 승계가 하루 상한(6곳)을 초과시키던 문제 (senior-dev)

오케스트레이터 재위임. 위 qa-reviewer 지적 중 **[보통] 1건 수정 + [사소] 2건 처리 판단**.
백엔드 파일 1개 + 문서만 손댔고 **git 커밋은 하지 않았다**(CLAUDE.md 규칙).

### 1. 무엇이 문제였나

절단과 승계의 **순서**가 어긋나 있었다.

```
_places_for_day (상한 절단)  →  Places 검증  →  _assemble_day  →  _align_terminals  →  _settle_lodging (항목 추가)
        ^ 여기서 6곳으로 자르고                                                              ^ 여기서 7번째가 붙는다
```

연박 중인 날에 LLM이 숙소를 빼고 비-숙소 6곳으로 상한을 채우면(이 기능이 다루려는 바로 그
"LLM 불이행" 상황) 승계된 숙소가 7번째로 append됐다. Places 호출은 늘지 않으므로 **비용
문제는 아니었고**, ADR-0010의 "상한 6은 그대로 둔다"는 서술과 실제 동작이 어긋나는 문제였다.

### 2. 어떻게 고쳤나 — 절단을 "뒤로 옮기는" 대신 **같은 규칙을 두 번** 적용

검토한 두 안:

| 안 | 판단 |
|---|---|
| 절단 단계를 숙소 확정 **뒤로 통째로 이동** | **기각.** 첫 절단의 대상은 아직 검증하지 않은 **LLM 문자열**이고, 그 선별이 곧 유료 Places 호출 수의 곱셈 인자다(ADR-0009 결정 3). 뒤로 옮기면 LLM이 준 장소를 **전부** 조회하게 되어 이 ADR이 지키려던 비용 설계가 깨진다. |
| 승계 분기에서만 `lodging_missing`을 보고 조건부로 밀어내기 | **기각.** 폴백 경로(`_fill_lodging`)도 똑같이 항목을 추가하므로 같은 검사를 두 벌 갖게 된다. 조건이 "누가 추가했나"가 아니라 "추가된 뒤 개수"인데 추가 지점마다 판정하는 꼴. |
| **절단 규칙을 함수 하나로 뽑아, 숙소가 확정된 뒤 한 번 더 적용 (채택)** | 상한은 "**그날 항목 목록이 마지막으로 바뀌는 지점**"에서 보장된다. 두 번째 적용은 이미 확정된 항목만 다루므로 **Places 호출 0회 = 추가 비용 0**. 자를 대상 우선순위도 같은 규칙을 쓰므로 거점·숙소는 살고 **마지막 관광/식사 항목**이 나간다. |

### 4. [사소] 2건 처리

- **`MAX_PLACE_LOOKUPS`(300) 주석** — 갱신했다. 이론상 최대치를 항목별로 다시 계산해 적었다:
  장소 검증 252 + 도시 앵커 3 + 숙소 폴백 42 + **거점 재검색 12**(도시 3 × 수단 4, (도시,수단)
  캐시라 3안 공유) = **309**. 즉 300은 이론적 최대치를 **살짝 밑돈다**(ADR-0010에서 거점
  재검색이 추가되며 그렇게 됐다). **값은 올리지 않았다** — 네 항목이 동시에 최대가 되려면
  "14일 3안 내내 겹치는 장소가 하나도 없고 + 날마다 숙소 검증 실패 + 도시마다 거점 짝 불일치"가
  겹쳐야 하고, 소진돼도 `take_lookup()`이 그 조회만 건너뛰어 **크래시가 아니라 품질 저하**로
  끝난다. 무엇보다 이 값을 올리는 건 **최악 비용 상한을 올리는 결정**이라 사용자 확인 없이
  건드릴 사안이 아니다(아래 확인 항목).

### 1. 조사 — Google Places에서 무엇을 얼마에 받을 수 있나

**실호출 2회**(searchText 1 + Place Details 1, 광주 국립아시아문화전당)로 확인했다.

| 원하는 값 | 필드 | 지금 받나 | 요금 티어 |
|---|---|---|---|
| 카테고리(사람이 읽는 라벨) | `primaryTypeDisplayName` | 아니오 | **Pro** (이미 내는 티어) |
| 카테고리 원시 코드 | `primaryType` / `types` | `types`만 받고 **저장은 안 함** | **Pro** |
| 지역명 | `addressComponents` | 아니오 | **Pro** |
| 영업시간 | `regularOpeningHours` | 아니오 | **Enterprise** (더 비쌈) |

핵심은 Places API (New)가 **요청한 필드 중 가장 비싼 티어로 과금**한다는 점이다. 앞 세 줄은
지금 검색 마스크(`displayName`/`formattedAddress`/`location`/`types`)와 **같은 Pro 티어**라
넣어도 요금이 그대로고, 영업시간 한 줄을 넣는 순간 **모든 검색이 Enterprise로 올라간다** —
AI 추천 1회가 최대 ~250회 검색을 하므로(ADR-0009) 그 비용이 통째로 오른다.

확인된 실제 응답값(실호출):
- `primaryTypeDisplayName.text` = `"문화센터"` — **구글이 이미 한국어로 준다.** 우리가
  "타입 코드 → 한글" 매핑표를 만들 필요가 없다(타입이 수백 개라 매핑표는 영원히 뒤처진다).
- `addressComponents`에 `administrative_area_level_1`("광주광역시") +
  `sublocality_level_1`("동구"). 한국 광역시는 `locality`가 비어 있는 경우가 있어 폴백을 여러 개 뒀다.
- `regularOpeningHours.weekdayDescriptions` = `["월요일: 휴무일", "화요일: 오전 10:00 ~ 오후 6:00", ...]`
  (languageCode=ko 지정 시 한국어).

**그리고 위임 프롬프트의 추측이 맞았다** — 등록 시점에 응답에 있던 `types`조차 저장하지
않았고 나머지는 요청조차 안 했다. 즉 **과거 일정은 이 정보를 가질 방법이 없다.**

### 2. 결정 — "공짜로 받을 수 있는 건 등록할 때, 비싼 건 열어볼 때 한 번만"

상세는 [ADR-0011](../docs/adr/0011-itinerary-place-details.md). 요약:

1. **카테고리·지역명은 등록 시점에 저장(추가 비용 0).** 검색 필드마스크에 Pro 티어 필드
   3개를 추가하고 `_summarize_place()`가 `category`/`region`을 함께 돌려준다. 수동 검색과
   AI 추천이 이 함수를 공유하므로 **양쪽 다 호출 증가 없이** 채워진다.
2. **영업시간만 on-demand + 저장.** 신규 `POST /api/items/{item_id}/place-details`가
   Details를 1회 호출해 빈 필드를 채운다. 프론트는 `place_id`가 있고
   `place_details_synced_at`이 null인 항목에 한해 상세보기를 열 때 부른다 →
   **항목당 평생 최대 1회 과금.**
3. **과거 데이터는 백필하지 않는다.** 열어보는 항목만 채워진다(안 볼 항목까지 전부 유료
   조회하는 백필은 이 앱의 비용 성향과 반대).
4. **출처 플래그(구글/사용자)를 두지 않는다.** 서버는 **빈 칸만** 채우므로 사용자가 고친 값이
   덮이지 않는다. 플래그를 두면 컬럼이 3개 늘고 화면은 그걸로 아무것도 다르게 하지 않는다.
5. **자유 입력칸은 기존 `notes` 재사용**(새 컬럼 없음). 메모가 두 군데로 갈라지면 ICS
   DESCRIPTION과 AI 저장 경로가 함께 갈라진다. 대신 이번에 처음으로 사용자가 직접 타이핑하는
   칸이 되므로 길이 상한 2,000자를 신설했다(기존 name/title/checklist와 같은 정책).
6. **기존 `category` 컬럼은 재사용하지 않는다.** 이름은 맞아 보이지만 거기엔 AI 추천의
   **동선 역할 코드**(`arrival`/`departure`/`lodging`/`activity`/`meal`/`cafe`)가 들어 있고
   ADR-0010의 거점 정합성 로직이 그 의미에 의존한다. 덮어쓰면 그 정보가 사라진다.
7. **Places 언어(`ko`) 지정을 앱 전체로 확대.** ADR-0009는 "일반 검색 결과는 한 번 보고
   버리는 값"이라 AI 경로에만 지정했는데, **이번 변경으로 그 전제가 깨졌다**(이제 일반 검색이
   준 카테고리/지역명이 DB에 남는다). 부수 효과로 검색 장소명도 한국어로 온다.

기각한 대안 6가지(영업시간을 검색 마스크에 포함 / 경로별 마스크 분리 / 저장 안 하는 순수
on-demand / 정기 백필 잡 / `category` 재사용 / 영업시간 구조화)는 ADR-0011에 근거와 함께 기록.

### 3. 백로그 4번(시작 시간)은 **백엔드가 이미 다 돼 있었다**

`ItineraryItem.start_time` 컬럼도 `ItineraryItemCreate`/`Update`/`Read` 스키마도 전부 있었고,
빠져 있던 건 **입력 UI뿐**이다. `PATCH /api/items/{id}`로 `"09:30"` 저장과 `null`로 지우기가
모두 정상 동작함을 검증에 포함했다. → **순수 프론트 작업.**

단, 지금까지 값이 항상 NULL이라 **한 번도 실행되지 않던 경로**가 깨어난다: ICS 내보내기의
"시간 있는 일정 = 시각 이벤트" 분기(ADR-0008). 회귀 검증에 넣어 정상 동작을 확인했다
(`DTSTART:20261001T090000` / 시간 없는 일정은 `DTSTART;VALUE=DATE:...`).

### 5. 검증 (실 Places 호출은 조사 2 + 통합 확인 1 = 총 3회)

임시 SQLite(`%TEMP%`)로 오버라이드해 실행, **`dev.db` 데이터 무변경**(마이그레이션 적용만
별도로 함). 외부 호출은 전부 목. **76개 체크 전부 통과.**

1. 신규 필드 저장/조회(POST→GET, 목록 조회 포함), 줄바꿈 보존, `start_time` 왕복.
2. 값 없음 안전성 — 필드 생략 시 전부 null, **raw SQL로 "마이그레이션 이전 행"을 직접
   INSERT**해 컬럼이 전부 NULL인 구 데이터도 200으로 직렬화되는 것 확인.
3. PATCH 수정/지우기(명시적 null·공백 문자열 둘 다 "지움"), 길이 상한 경계값(50/100/1000/2000
   → 한 글자 넘으면 422), 기존 정책 회귀(`title: null` 422 / 음수 비용 422 / 결제자 이름
   문자열 422 / 통화 대문자 정규화).
4. `place-details` 엔드포인트 — place_id 없으면 422이고 **외부 호출 0회**, 정상 항목은 1회
   호출 + `languageCode=ko` 전달, **재호출 시 외부 호출이 늘지 않음**(비용 상한 확인),
   사용자가 이미 고친 값은 보존하고 빈 값만 채움, **영업시간이 없는 장소도 `synced_at`을
   남겨 재호출을 막음**, 없는 item 404.
5. 순수 함수 — 카테고리 퇴화(`primaryTypeDisplayName` → `primaryType` → None), 지역명
   조립(한국식 "광주광역시 동구" / 일본식 "大阪府 大阪市" / 광역만 / 중복 이름 제거 / 정보
   없으면 None), **검색 마스크에 영업시간이 없다는 것 자체를 테스트로 고정**(요금 티어 회귀 방지).
6. AI 경로 — `_to_hit()`/`_make_resolved()`가 카테고리·지역을 실어 나르는지.
7. **ICS 회귀** — 위 3절의 잠들어 있던 분기.
8. 기존 엔드포인트 회귀 — reorder / move(이동 후에도 신규 필드 유지) / 정산.

추가로 **통합 경로 실호출 1회**(`search_places("오사카성", language_code="ko")`)로 코드에
적힌 필드마스크가 실제로 수락되는지 확인: `category`가 "성곽"/"역사 박물관"/"공원"으로 한국어로
왔다. **다만 지역명은 항상 한국어가 아니다** — 같은 요청에서 오사카성은 `"Osaka Chuo Ward"`,
오사카성 공원은 `"오사카부 오사카시"`로 왔다(구글의 주소 구성요소 현지화가 장소마다 다름).
사용자가 고칠 수 있는 필드라 보정 로직을 넣지 않았다(ADR-0011 "알려진 한계").

마이그레이션은 **로컬 `dev.db`에만** 적용했고(`DATABASE_URL`을 명령줄에서 sqlite로 명시해
운영 DB를 건드릴 여지를 없앰), 사본으로 downgrade→upgrade 왕복 + `alembic check`
("No new upgrade operations detected" = 모델과 마이그레이션 일치)까지 확인했다.

### 6. ui-dev 후속 작업 스펙 (API 계약)

**`ItineraryItem` 타입에 추가할 필드** (`frontend/src/types/models.ts`):

```ts
place_category: string | null        // "문화센터" — 사람이 읽는 분류, 사용자 수정 가능
region_name: string | null           // "광주광역시 동구" — 사용자 수정 가능
opening_hours: string | null         // 요일별 문구를 개행(\n)으로 이은 텍스트 → whitespace-pre-line
place_details_synced_at: string | null  // ISO datetime. null = 구글 상세를 아직 안 받아옴
```

`ItemCreateInput`/`ItemUpdateInput`에는 앞의 **3개만** 추가한다(`place_details_synced_at`은
서버 전용이라 보내도 무시된다). `start_time`/`notes`는 이미 `ItemCreateInput`에 있고,
`ItemUpdateInput`에는 **없으므로 추가해야 한다**(`start_time?: string | null`,
`notes?: string | null`).

**상세보기 모달이 열릴 때**:

```
if (item.place_id && item.place_details_synced_at === null) {
  POST /api/items/{id}/place-details   // 성공 시 응답으로 캐시 갱신
}
```

- **이 호출은 유료다.** 조건 없이 부르거나, 목록을 그리며 여러 건을 부르거나, 모달을 열 때마다
  부르면 안 된다(서버가 2·3중으로 막고 있지만 첫 방어선은 프론트다).
- 실패해도 **모달은 그대로 떠야 한다** — 이미 가진 값으로 렌더하고 영업시간 자리에만
  "영업시간을 불러오지 못했습니다" 정도. 기존 `extractErrorMessage()` 패턴 사용.
- `place_id`가 없는 수동 입력 일정은 **호출하지 않는다**(부르면 422).

**모달 표시 규칙** (요청의 "못 가져오면 사용자 직접 입력"에 대응):

| 항목 | 값이 있을 때 | null일 때 |
|---|---|---|
| 장소명 | `title` | (항상 있음) |
| 카테고리 / 지역 | `place_category` · `region_name` | **빈 입력칸으로 직접 입력** ("정보 없음" 회색 문구 + 입력) |
| 영업시간 | `opening_hours`(개행 유지) | "영업시간 정보 없음" — 수동 항목은 직접 입력 허용 |
| 시작 시간 | `start_time`(`"09:30:00"` → `<input type="time">`에는 **앞 5글자만**) | 빈 입력 |
| 자유 입력칸 | `notes` | 빈 textarea |

- 저장은 `PATCH /api/items/{id}`로 **바뀐 필드만**. 입력칸을 비워서 보내면(빈 문자열) 서버가
  "지움(null)"으로 처리하므로 프론트에서 null 변환을 할 필요가 없다.
- `<input type="time">`은 `"09:30"`을 보내고 서버는 `"09:30:00"`으로 돌려준다. 표시할 때
  `slice(0, 5)` 필요.
- 길이 상한: 카테고리 50 / 지역명 100 / 영업시간 1000 / 자유 입력칸 2000자. 초과 시 422이므로
  체크리스트처럼 **제출 전에 프론트에서 막아** 불필요한 왕복을 줄이는 편이 좋다.
- AI로 만든 일정은 `notes`에 LLM의 한 줄 이유가 이미 들어 있다(빈 칸이 아닐 수 있음 — 정상).

**"수정" 버튼 분리 / 목록 시작 시간**(백로그 3·4번의 화면 몫, 백엔드 추가 작업 없음):

### 2. 영업시간 자동 동기화 — 비용 상한 조건 그대로 준수

`ItineraryItemDetailModal`이 마운트될 때(딱 1회, `item.id` 기준 effect) 아래 조건을 **프론트에서

방어선은 여기다. 성공 응답은 `queryClient.setQueryData(['days', item.day_id, 'items'], ...)`로
캐시에 바로 반영해 목록/카드가 재조회 없이 최신 상태를 보게 했다. 실패해도 모달은 정상적으로
뜨고 영업시간 자리에만 "영업시간을 불러오지 못했습니다. 직접 입력할 수 있습니다." 표시.

### 3. 저장 — 변경된 필드만 PATCH, `start_time` 지우기는 `null`

카테고리/지역/영업시간/메모는 문자열 필드라 서버 정책대로 **빈 문자열도 지움으로 처리**되므로
별도 null 변환이 필요 없다(스펙 그대로). 다만 `start_time`은 `dt.time` 타입이라 빈 문자열을
보내면 파싱 실패(422)가 날 것으로 판단해, 입력을 비우면 명시적으로 `null`을 보내도록 분기했다

### 4. 회귀 방지 확인

## qa-reviewer 검증 (2026-09-14, orchestrator_pjt 위임) — 일정 상세보기(백로그 3·4번, ADR-0011)

senior-dev/ui-dev의 76체크(백엔드)·npm build/lint(프론트) 재실행 보고는 신뢰하지 않고, **전부 새로 작성한 독립 검증**을 수행했다. 백엔드는 임시 SQLite(`%TEMP%\travel_pjt_qa_placedetails.db`, `travel_pjt_qa_fields.db`)로 `DATABASE_URL`을 덮어써 `venv312\Scripts\python.exe`로 직접 실행(외부 Google API는 전부 목, **추가 실호출 0회**), `dev.db`는 전혀 열지 않았다(파일 접근 자체가 없음 — mtime 확인 불필요할 정도로 별도 엔진). 검증 스크립트는 세션 전용 스크래치 디렉토리에만 있고 이 저장소에는 없다. 프론트는 `git diff` 코드 추적 + `npm run build`/`npm run lint` 재실행.

### 검증 방식
- `httpx.AsyncClient` + `ASGITransport`로 FastAPI 앱을 직접 구동해 `POST /api/items/{id}/place-details`를 순차/동시 양쪽으로 호출(`app.routers.items.get_place_details`를 목으로 교체해 호출 횟수 카운트) — 14체크.

- `AddItemModal.tsx`/`ItineraryItemDetailModal.tsx`/`ItineraryItemCard.tsx`/`api/items.ts`/`api/places.ts` 코드 직접 확인 + `git diff`로 `MoveItemControl`/드래그/비용·결제자 인라인/삭제 영역 변경 여부 확인.

### 결과: 치명적 1건, 보통 없음, 사소 1건

**[치명적] `POST /api/items/{item_id}/place-details`가 동시(경합) 요청에서 "평생 1회"를 지키지 못하고 유료 외부 호출을 2회 이상 낼 수 있다.**
- **문제**: `sync_place_details()`가 "읽고(`place_details_synced_at` 확인) → 비동기 외부 호출 → 쓰기(commit)" 순서를 **원자적으로 묶지 않는다**. 두 요청이 거의 동시에 들어오면 둘 다 `item.place_details_synced_at is not None` 체크를 통과(둘 다 아직 None을 봄)한 뒤 **둘 다** `get_place_details()`(Enterprise 티어 유료 호출)를 실행한다. ADR-0011이 이 컬럼을 "편의 메타데이터가 아니라 비용 상한 장치"라고 명시한 바로 그 불변식이 깨진다.
- **재현/근거**: `httpx.AsyncClient`로 같은 item에 `asyncio.gather()`로 동시에 2번 POST(외부 호출 목은 `await asyncio.sleep(0.1)`로 지연 삽입해 두 요청이 서로 커밋 전에 겹치게 함) → 두 응답 모두 200, **목 카운터가 2**로 찍힘(기대값 1). 순차 호출(1차 완료 후 2차 호출)은 정상적으로 1회로 막힘 — 문제는 "이미 동기화됨" 분기 자체가 아니라 **동시성 처리의 부재**다. 검증 스크립트: `qa_place_details.py`(세션 스크래치 전용, 저장소에는 없음).
- **왜 실사용에서도 현실적인가**: (1) 프론트 `ItineraryItemDetailModal.tsx`의 동기화 `useEffect`는 의존성 배열이 `[]`이고 요청 취소(`AbortController`) 없이 `detailsMutation.mutate()`를 호출하는데, 이 프로젝트는 `main.tsx`에서 `<StrictMode>`를 쓰고 있다 — 개발 모드에서는 React가 마운트를 의도적으로 두 번 실행(mount→unmount→mount)하므로, **개발 중에는 상세보기를 열 때마다 이 레이스가 실제로 발생할 가능성이 높다**(정리 함수가 없어 첫 호출이 취소되지 않음). (2) 이 앱은 2인이 같은 여행을 동시에 보는 구조라, 방금 AI가 만든 항목을 두 사람이 거의 동시에 열어보는 시나리오도 현실적이다. 프로덕션 빌드(React 프로덕션 런타임)에서는 StrictMode의 이중 마운트가 사라지지만, 서버 쪽 경합 조건 자체는 프로덕션에서도 그대로 남는다(두 기기/두 탭 동시 클릭이면 여전히 유효).
- **영향 평가**: 크래시나 데이터 오염은 없다(둘 다 같은 값으로 덮어써 최종 상태는 정상) — 순수하게 **비용 상한이 깨지는 문제**다. 다만 이 기능 전체의 존재 이유가 "Enterprise 티어 호출을 항목당 평생 1회로 제한"하는 것이므로 사소한 흠이 아니라 설계 목표 자체의 실패로 보고 치명적으로 분류했다. 수정 방향 제안(참고용, 강제 아님): 외부 호출 **전에** "동기화 예약"을 원자적 UPDATE(`UPDATE ... SET place_details_synced_at = now() WHERE id = :id AND place_details_synced_at IS NULL` 후 영향받은 행 수 확인)로 먼저 선점하고, 실패(0행)면 즉시 현재 상태를 멱등 반환 — 지금처럼 "읽기 후 판단"이 아니라 "쓰기로 판단"해야 진짜 원자성이 생긴다. 프론트 쪽 `useEffect`에 `AbortController`/`isMounted` 가드를 추가하는 것도 StrictMode발 이중 호출을 줄이는 보완책이지만, 서버가 경합에 안전하지 않은 한 근본 해결은 아니다.

**[사소] `ItineraryItemDetailModal`이 동기화 성공 시 로컬 draft를 `prev === '' ? updated.value : prev`로 채우는데, 사용자가 그 사이 공백만 입력했다면(빈 문자열이 아니라 공백 문자열) 방금 받아온 값을 덮어쓰지 못하고 서버 값이 무시된다.** 코드 추적으로 확인(`ItineraryItemDetailModal.tsx` 56~58행), 실사용 빈도가 매우 낮고(그 짧은 순간에 공백만 타이핑) 저장 시 어차피 `_normalize_optional_text()`가 공백을 지움으로 처리하므로 데이터 오염으로 이어지지 않아 사소로 분류.

## [치명적] 이슈 수정 — place-details 동시 요청 시 유료 호출 2회 (senior-dev, orchestrator_pjt 위임)

위 qa-reviewer 검증에서 나온 **[치명적] 1건**(동시 요청에서 `POST /api/items/{id}/place-details`가
Google Places Enterprise 호출을 2회 낼 수 있음)과 **[사소] 1건**(draft 채우기의 공백 처리)을 수정했다.
Google Places 실호출은 하지 않았고(전부 목), `dev.db`는 열지 않았다(임시 SQLite로 `DATABASE_URL` 오버라이드).

### 1. 근본 원인

`sync_place_details()`가 "읽고(`if item.place_details_synced_at is not None`) → `await` 외부 호출 →
commit" 순서라 **판정과 쓰기 사이에 `await`가 있었다**. 그 틈에 다른 요청이 같은 NULL을 보고 통과하면
둘 다 유료 호출을 실행한다. 즉 문제는 "이미 동기화됨" 분기 자체가 아니라 **그 분기가 원자적이지 않다는
것**이고, ADR-0011이 `place_details_synced_at`을 "편의 메타데이터가 아니라 비용 상한 장치"로 못박은
불변식이 바로 여기서 깨졌다.

### 2. 수정 — 외부 호출 **전에** 원자적으로 선점(claim)한다

`backend/app/routers/items.py`의 `sync_place_details()`를 다음 순서로 바꿨다.

1. 404 / `place_id` 없음(422) 확인 — 여기서는 아무것도 쓰지 않는다(호출 0회, 선점 0회).
2. **원자적 선점**: `UPDATE itinerary_item SET place_details_synced_at = :now, updated_at = :now
   WHERE id = :id AND place_details_synced_at IS NULL` 후 `rowcount` 확인 → 즉시 commit.
3. `rowcount == 0` → 이미 동기화됐거나 다른 요청이 방금 선점했다. **외부 호출 없이** 현재 DB 상태를
   그대로 반환(기존 멱등 동작과 동일).
4. `rowcount == 1` → 이 요청이 유일한 승자. 외부 호출 후 비어 있는 필드만 채워 저장.

조건 판정과 쓰기가 DB 안에서 한 문장으로 일어나므로 끼어들 틈이 없다. 선점 직후 곧바로 commit하는 것도
의도적이다 — 다른 요청/워커가 선점을 볼 수 있어야 하고, 10초짜리 외부 HTTP 호출 동안 DB 쓰기 잠금을
잡고 있으면 안 된다. 선점 블록 안에 `await`가 없다는 점도 같은 이유로 중요하다(단일 프로세스에서는
이벤트 루프가 여기서 제어를 넘기지 않아 DB 잠금 경합조차 생기지 않는다).

**SQLite/Postgres 호환성**: DB 고유 기능(`ON CONFLICT`, 어드바이저리 락 등)을 쓰지 않아 두 엔진에서
코드가 갈리지 않는다. SQLAlchemy가 만드는 SQL을 두 방언으로 컴파일해 구조가 동일함을 확인했고
(바인드 파라미터 표기만 `?` vs `%(name)s`), SQLite에서는 **서로 다른 Session 8개를 스레드로 동시에**
날려 승자가 정확히 1명(패자 7, `database is locked` 오류 0건)임을 실측했다. Postgres도 같은 의미로
동작한다(두 번째 UPDATE가 첫 번째 커밋을 기다린 뒤 조건을 재평가해 0행).

### 3. 외부 호출 실패 정책 — 선점을 **되돌린다**(NULL 복원)

판단이 필요한 트레이드오프라 근거를 남긴다.

- **그대로 두면**: 비용은 절대 안전하지만 일시적 네트워크 오류 하나가 그 항목의 영업시간을 **영구히
  "정보 없음"**으로 못박는다. `force` 옵션이 없으므로 되살릴 경로 자체가 없다.
- **되돌리면(채택)**: 다음에 상세보기를 열면 다시 시도한다.

되돌리는 쪽을 택한 이유 — (1) `place_details_synced_at`의 정의가 모델 주석/ADR대로 **"성공적으로
조회한 시각"**이다. 실패를 여기 적으면 "가져왔는데 영업시간이 없는 장소(공원 등)"와 "가져오다 실패한
장소"가 다시 구분 불가능해져, 이 컬럼을 비용 상한 장치로 만든 그 구분이 흐려진다. (2) 실패한 호출은
구글이 과금하지 않는다(비 200). (3) 재시도가 자동 루프가 아니라 **사용자가 상세보기를 다시 열 때만**
일어나므로 사용자 두 명의 수동 조작이 곧 상한이다 — `force`를 거부했던 이유("프론트가 무심코
새로고침마다 부르게 되는 손잡이")에 해당하지 않는다.

롤백은 `WHERE ... place_details_synced_at = :my_claim`으로 **자기 선점일 때만** 지우고, `updated_at`도
원래 값으로 복원한다(실패한 시도가 "수정됨"으로 보이면 안 된다).

### 4. 프론트 — 보조 방어선 (`frontend/src/components/ItineraryItemDetailModal.tsx`)

### 검증 방식 및 결과 — 요청받은 6개 항목

**1. 핵심 재현(동시 2/5/10건) — 통과.** 같은 item에 `asyncio.gather()`로 동시 POST(목 응답에
`asyncio.sleep(0.08)` 지연을 넣어 커밋 전에 겹치게 함) → 2건/5건/10건 모두 **외부 호출이
정확히 1회**, 전부 200, DB에 영업시간 저장 확인. (수정 전에는 이 자리에서 목 카운터가
동시 건수만큼 그대로 찍혔던 것과 대비됨.)

**2. 선점→즉시 커밋→외부 호출 실패→롤백, 그리고 "자기 선점일 때만" — 통과 + 구조 분석 결과 별도 기록.**
- 실패 시 `place_details_synced_at`이 정확히 `NULL`로, `updated_at`도 원래 값으로 복원됨을
  확인(전/후 값 직접 비교). 이후 재시도가 실제로 외부 호출을 다시 내고 성공하는 것도 확인.
- "A가 선점→실패, 그 사이 B가 선점→성공, A의 롤백이 B의 성공 데이터를 지우지 않는지"를
  코드/DB 레벨로 재현하는 과정에서, **이 정확한 순서의 진짜 동시 경합은 현재 설계상 구조적으로
  발생할 수 없음을 먼저 확인했다** — A가 클레임을 쥐고 있는 동안(성공이든 실패든 롤백 전까지)
  `WHERE ... IS NULL` 조건 때문에 B는 애초에 클레임 자체를 얻지 못하고 즉시 rowcount=0으로
  돌아간다(직접 실행해 확인). 즉 두 요청이 동시에 "선점에 성공"하는 상태 자체가 없다.
  그래서 의미 있는 형태로 바꿔 재검증했다: A 선점→실패→정상 롤백(NULL 복원, rowcount=1)
  → **그 뒤** B가 정상적으로 새로 선점해 성공적으로 데이터를 채움 → **A의 지연되거나 중복된
  재롤백 시도**(같은 `claimed_at` 값으로 다시 시도한다고 가정)가 `WHERE place_details_synced_at
  = :claimed_at`(펜싱 토큰) 조건 때문에 rowcount=0이 되어 **B가 채운 데이터를 지우지 않음**을
  확인했다. 즉 요청하신 시나리오의 실질적 방어(펜싱 토큰의 특정성)는 정상 동작하고, 그 시나리오가
  묘사한 정확한 "동시" 형태는 애초에 이 설계에서 나올 수 없는 상태임을 코드로 확인했다(사소한
  안심 포인트로 기록, 문제 아님).

**3. 기존 정상 케이스 회귀 — 전부 통과.** 순차 호출(외부 호출 1회, 두 응답 동일=멱등) /
`place_id` 없는 항목 422(외부 호출 0회, 선점 자체도 안 일어남) / 영업시간 없는 장소(공원 등)도
`synced_at` 세팅되어 재호출 시 외부 호출 0회 / 없는 item 404(외부 호출 0회) / 사용자가 이미
채운 값(`place_category`)은 보존되고 비어 있던 필드만 채워짐.

**4. 프론트 `useRef` 가드 — 코드로 구조 확인, 정당함.** `ItineraryItemDetailModal.tsx` 70~80행의
`detailsRequestedRef`는 `useEffect(..., [])` 안에서 `if (detailsRequestedRef.current) return;
detailsRequestedRef.current = true` 순서로 동작한다. **`useState` 대신 `useRef`를 쓴 이유가
실제로 유효하다**: React 18 StrictMode의 개발 모드 이중 실행은 같은 커밋 내에서
effect→cleanup→effect를 **리렌더 없이 연속으로** 재실행하므로, 그 사이에 `setState`를 호출해도
두 번째 effect 실행은 아직 그 상태 갱신이 반영되지 않은 **이전 렌더의 클로저**를 그대로 보고
돈다(리렌더가 끼어들 시간이 없음). 즉 `useState` 기반 플래그였다면 두 번째 실행에서도 플래그가
여전히 `false`로 보여 요청이 두 번 나갔을 것이다. `ref.current` 직접 대입은 렌더 사이클과
무관하게 즉시 반영되므로 이 용도에 유일하게 맞는 선택이다 — 주석의 근거가 기술적으로 정확함을
직접 검증했다.

**5. SQLite/Postgres 동일 컴파일 — 통과.** 같은 `update(ItineraryItem).where(...).values(...)`
문을 `sqlalchemy.dialects.sqlite`/`postgresql` 양쪽으로 `.compile()`해 비교 →
`WHERE itinerary_item.id = ? AND itinerary_item.place_details_synced_at IS NULL` 구조가
완전히 동일하고, 차이는 바인드 파라미터 표기(`?` vs `%(id_1)s`)뿐임을 확인. DB 고유 기능
미사용 주장이 코드로도 확인됨.

**6. `dev.db`/실호출 — 준수.** 위에 기술한 대로 mtime 무변화, Google Places 실호출 0회.

### [보통] 신규 발견 — 외부 호출이 `asyncio.CancelledError`로 실패하면 롤백이 스킵되어 클레임이 영구히 고아 상태(orphaned)로 남는다

- **문제**: `sync_place_details()`의 실패 처리부(`backend/app/routers/items.py` 146행)가
  `except Exception:`으로 롤백(NULL 복원)을 걸고 있는데, **`asyncio.CancelledError`는 Python
  3.8부터 `BaseException`을 상속하고 `Exception`을 상속하지 않는다**(`issubclass(asyncio.
  CancelledError, Exception)`가 `False`임을 직접 실행해 확인). 즉 외부 호출이 취소로 실패하면
  이 `except` 블록 자체가 실행되지 않아 **롤백이 통째로 스킵**되고, 이미 선점 단계에서
  커밋해 둔 `place_details_synced_at`(non-null)만 영구히 남는다.
- **재현/근거**: `app.routers.items.get_place_details`를 `raise asyncio.CancelledError()`로
  교체하고 `POST /api/items/{id}/place-details` 호출 → 예외가 라우터 밖으로 그대로 전파됨
  (실제로 `httpx`/스타렛 스택을 통해 클라이언트까지 전파돼 `asyncio.run()`이 죽는 것으로 1차
  확인, `except BaseException`으로 감싸 재확인). 호출 뒤 DB를 직접 조회한 결과:
  `place_details_synced_at`은 클레임 시각 그대로 남아 있고(`2026-09-13 12:09:23...`),
  `place_category`/`opening_hours`는 둘 다 `None`(외부 호출이 성공하지 못했으니 당연히 비어
  있음). 이어서 **정상 동작하는 목으로 같은 item에 재요청**했더니 응답은 200이었지만 **외부
  호출 카운터가 0**으로 유지됨 — 즉 이 항목은 "이미 동기화됨(`claimed_rows == 0`)" 분기로
  영원히 빠지게 되어, **다시는 영업시간을 가져올 방법이 없다**(스크립트: `qa_cancelled_error_
  check.py`).
- **왜 이론이 아니라 현실적인가**: `CancelledError`는 클라이언트가 요청 도중 연결을 끊거나,
  타임아웃으로 태스크가 취소되거나, **가장 실질적으로는 배포 서버(Render)가 재배포 시 보내는
  SIGTERM에 대해 Uvicorn이 graceful shutdown 과정에서 진행 중인 요청 태스크를 취소**할 때
  발생한다. 이 엔드포인트는 내부에 최대 10초짜리 실제 외부 HTTP 호출(`get_place_details`,
  `timeout=10.0`)을 갖고 있어 그 창이 좁지 않다 — 이 프로젝트가 실제로 Render에 배포돼 있고
  운영 중 재배포가 발생하는 프로젝트이므로, "누군가 상세보기를 여는 순간과 재배포가 겹치는"
  시나리오는 드물어도 현실적으로 발생 가능하다. 발생하면 **그 항목 하나가 영구히 "정보
  없음"으로 고정**되고, `force` 옵션이 없으므로(ADR-0011의 명시적 결정) 사용자/서버 어느
  쪽에서도 재시도할 방법이 없다 — 이는 바로 이번 정정 섹션이 "실패 시 롤백"을 택한 근거
  ("일시적 오류 하나가 정보를 영구히 못박으면 안 된다")를 정확히 무력화하는 경로다.
- **영향 평가**: 크래시나 다중 과금은 없다(취소된 호출은 대체로 응답을 못 받았거나 처리
  전이라 이중 과금 경로는 아니다 — 다만 취소 시점이 "구글 응답을 이미 받은 직후, 커밋 전"일
  가능성도 완전히 배제할 순 없어 그 경우 한 번의 유료 호출이 헛되이 소모된다). 블라스트
  반경은 **항목 1개**로 좁고 트리거 확률도 낮다(정상적인 네트워크 실패는 `HTTPException`으로
  오지 `CancelledError`로 오지 않는다 — 이 경로는 취소성 실패에 한정된다). 이 좁은 범위와
  낮은 빈도 때문에 치명적까지는 아니라고 보았지만, (1) 이 기능이 명시적으로 해결하려 한 바로
  그 문제(재시도 불가능한 영구 고정)가 다른 트리거로 재발할 수 있고, (2) 수정이 매우
  간단하다는 점(예: `except Exception:` → `except (Exception, asyncio.CancelledError):`,
  둘 다 어차피 `raise`로 그대로 전파하므로 취소 자체를 삼키지 않으면서 정리만 먼저 함 —

## QA [보통] 이슈 수정 — `asyncio.CancelledError`로 인한 클레임 고아 상태 (junior-dev)

오케스트레이터 위임. 위 qa-reviewer가 새로 발견한 [보통] 이슈("외부 호출이
`asyncio.CancelledError`로 실패하면 롤백이 스킵되어 `place_details_synced_at` 클레임이
영구히 고아 상태로 남는다") 수정. 백엔드 파일 1개만 손댔고 **git 커밋은 하지 않았다**
(CLAUDE.md 규칙).

### 1. 무엇을 고쳤나

`backend/app/routers/items.py`의 `sync_place_details()` 실패 처리부:

```python
try:
    details = await get_place_details(place_id, language_code=PLACES_LANGUAGE_CODE)
except (Exception, asyncio.CancelledError):
    ...(기존 롤백 로직 그대로: 자기 선점 시각일 때만 NULL/이전 updated_at으로 복원)
    db.commit()
    raise
```

- `except Exception:` → `except (Exception, asyncio.CancelledError):`로 변경. `asyncio.
  CancelledError`는 Python 3.8+에서 `Exception`이 아니라 `BaseException`을 직접 상속하므로
  별도로 명시해야 잡힌다.
- 롤백 로직(자기 클레임(`claimed_at`)일 때만 NULL/이전 `updated_at`으로 되돌리는 조건부
  UPDATE)은 그대로 재사용 — 새 분기를 만들지 않았다.
- 블록 끝의 `raise`는 이미 있었으므로 그대로 둠 — **예외를 삼키지 않고 그대로 재전파**한다
  (asyncio 공식 권장 패턴과 일치: 취소는 반드시 전파해야 태스크 취소/graceful shutdown이
  정상 동작한다).
- `import asyncio`가 파일에 없어 상단에 추가했다.

### 2. 검증

`venv312\Scripts\python.exe`로 실행. **`dev.db`/운영 Neon은 전혀 거치지 않았다** — 별도
in-memory SQLite 엔진(`create_engine("sqlite:///:memory:")`)을 직접 만들어 `Session`을
넘기는 방식으로 `sync_place_details()`를 함수 그대로 호출했다(FastAPI 라우팅/인증 레이어를
거치지 않음). `app.routers.items.get_place_details`를 세 가지로 교체해 3개 시나리오를
순서대로 실행(스크립트: 세션 스크래치 전용, 이 저장소에는 없음).

- **`asyncio.CancelledError` 발생** — 예외가 삼켜지지 않고 그대로 `asyncio.CancelledError`로
  전파됨을 확인. 롤백 후 DB 조회 결과 `place_details_synced_at`이 정확히 `NULL`로,
  `updated_at`도 클레임 이전 원래 값으로 복원됨(`place_category` 등도 미변경).
- **일반 `Exception`(`RuntimeError`) 발생 — 회귀 확인.** 기존과 동일하게 예외가 그대로
  전파되고 같은 롤백(`synced_at` NULL, `updated_at` 원복)이 일어남을 확인 — 이번 수정이
  `except`에 타입을 하나 추가한 것뿐이라 기존 실패 경로의 동작은 바뀌지 않았다.
- **정상 성공 — 회귀 확인.** 목이 성공 응답(category/region/opening_hours)을 돌려주면 예외
  없이 정상적으로 `place_category`/`region_name`/`opening_hours`가 채워지고
  `place_details_synced_at`/`updated_at`이 갱신됨을 확인.
- Google Places 실호출 0회(전부 목). `dev.db`는 아예 import 경로에서 사용되지 않았다
  (별도 in-memory 엔진).

### 3. 결과

3개 시나리오 전부 기대대로 동작(CancelledError 롤백 + 재전파, 일반 Exception 회귀 없음,
정상 성공 회귀 없음). 위 QA가 지적한 "클레임 영구 고아 상태" 문제가 해소됨.

- [ ] **git 커밋 안 했음**(규칙대로). 이번 수정분: `backend/app/routers/items.py`(1줄 import +
      `except` 타입 추가 + 주석), 이 로그 파일. qa-reviewer 재검증을 원하면 별도로 요청.
- [ ] 기존에 남아있던 다른 확인 항목(운영 Neon 마이그레이션 미적용, `MAX_PLACE_LOOKUPS` 300
