## M7 Tier 1: 여행 기간(PATCH) 수정 시 Day 동기화 — 설계 + 백엔드 구현

담당: senior-dev (오케스트레이터 위임). `docs/PROJECT.md` Backlog Tier 1의 마지막 미완 항목.
2026-09-07에 "실제 동기화가 필요해지면 `build_days_for_range()`를 재사용해 확장할 것"으로 남겨뒀던 후속 작업.

### 설계 결정 (ADR-0001)

핵심 질문은 **"새 기간 밖으로 밀려난 기존 Day를 어떻게 할 것인가"**였다. Day는 `ItineraryItem`을
`ondelete="CASCADE"`로 물고 있어서 Day를 지우면 그날 일정이 전부 사라지고, 이 앱엔 되돌릴 수단이 없다.

세 후보를 비교했다.

| | (a) 2단계 (응답에 경고 정보 → 별도 삭제 API) | (b) `force=true` 한 번에 | (c) 남겨두고 UI 표시만 |
|---|---|---|---|
| 데이터 손실 위험 | 낮음 (PATCH가 삭제를 안 함) | **높음** (클라 실수 한 줄 = 손실) | 없음 |
| 새 엔드포인트 | **0개** (`DELETE /api/days/{id}` 재사용) | 0개 | 0개 |
| 경고에 필요한 왕복 | 1회 (응답에 다 있음) | 사전 조회 필요 → 결국 2회 | - |
| 정리 수단 | 있음 | 있음 | **없음** |

**(a) 채택.** 서버는 "사실"(무엇이 범위 밖이고 거기 일정이 몇 개인지)만 알려주고, 파괴적 결정은 사람이 내린다.
(b)는 위험한 동작을 일반 수정 요청에 묶는 게 근본 문제 — 두 사람이 같이 쓰는 공유 여행 계획이라 한쪽 실수가
상대 작업을 날린다. 게다가 "일정 2개가 사라집니다"라고 경고하려면 어차피 사전 조회가 필요해서 왕복 1회 이점도 없다.
(c)는 5일→3일로 줄인 사용자에게 영원히 정리할 방법을 안 준다 — 다만 (a)에서 사용자가 "삭제 안 함"을 고른
결과가 곧 (c)이므로 (a)를 택하면 (c)는 폴백 동작으로 자동 포함된다.

상세 근거 + 기각한 대안(빈 Day만 자동 삭제 / 소프트 삭제 / 미리보기 전용 엔드포인트)은
[`docs/adr/0001-patch-trip-date-day-sync.md`](../docs/adr/0001-patch-trip-date-day-sync.md) 참고.
**이 프로젝트의 첫 ADR 파일이며, `docs/adr/` 폴더를 이번에 신설했다.** 2026-09-08까지의 결정들은
`docs/PROJECT.md`의 Architecture Decisions에 인라인으로 그대로 두고, 앞으로의 되돌리기 어려운 결정만
`docs/adr/NNNN-*.md`로 분리한다(PROJECT.md엔 요약+링크).

### 진행한 작업 (백엔드)

**1) `backend/app/services/trip_days.py`**
- `MAX_TRIP_TOTAL_DAYS = MAX_TRIP_DAYS * 2` (=180) 상수 추가. 범위 밖 Day를 안 지우기 때문에
  기간을 통째로 옮기는 PATCH를 반복하면 Day가 무한 누적된다 — 기존 `MAX_TRIP_DAYS`(90)는 "한 번의 요청"만
  막을 뿐 이 누적을 못 막는다. 기간을 한 번 통째로 옮기는 정상 시나리오(범위 밖 90 + 신규 90)는
  통과시켜야 하므로 2배로 잡았다.
- `DayRangeDiff` 데이터클래스(`to_add` / `out_of_range`)와 순수 함수
  `diff_days_for_range(trip_id, start, end, existing)` 추가. 내부에서 기존 `build_days_for_range()`를
  그대로 호출한 뒤 이미 있는 날짜를 걸러내는 방식이라 "날짜 범위 → Day" 변환 규칙의 단일 소스가 유지된다.
  **삭제 대상은 애초에 계산하지 않는다** — 범위 밖 Day는 `out_of_range`로 분류만 하고, 판단은 호출자(사용자)에게 넘긴다.
  수동 생성 Day와 날짜가 겹쳐도 중복 생성하지 않는다.

**2) `backend/app/schemas.py`**
- `OutOfRangeDayRead(DayRead)` — `item_count: int` 추가. 프론트가 "이 날짜를 지우면 일정 N개도 사라진다"고
  경고하는 근거.
- `TripUpdateResult(TripDetailRead)` — `added_day_ids: list[int]`, `out_of_range_days: list[OutOfRangeDayRead]` 추가.
  `TripRead`의 **상위집합**이라 기존 프론트 `updateTrip()`(응답을 `Trip`으로 받음)은 그대로 동작한다
  (추가 필드는 무시). 백엔드/프론트 배포 순서 의존성 없음.

**3) `backend/app/routers/trips.py` — `update_trip`**
- `response_model`을 `TripRead` → `TripUpdateResult`로 변경.
- **기존 흐름은 손대지 않고 뒤에 이어붙였다**: `patch` + DB 기존값 병합 → `validate_date_range()`(역전/90일 초과 → 422)
  → `setattr` → **그다음에** Day 동기화. 검증 실패 시 세션에 잘못된 값이 안 올라가는 기존 보장 그대로.
- 동기화 조건 2개: ① 요청 본문에 `start_date` 또는 `end_date` 키가 있을 것(`exclude_unset` 기준),
  ② 병합 후 두 날짜가 다 있을 것. ①은 이름만 바꾸는 PATCH가 Day를 건드리는 예상 밖 부수효과를 막기 위한 것
  (이 기능 이전에 만들어져 날짜는 있고 Day는 없는 여행이 이름 한 글자 고쳤다고 Day 수십 개를 갖게 되는 상황).
  ②는 `create_trip`/`validate_date_range`의 기존 정책과 같은 기준.
- 총 Day 수가 `MAX_TRIP_TOTAL_DAYS`를 넘으면 `db.rollback()` 후 422
  (`"trip cannot hold more than 180 days (delete out-of-range days first)"`).
- `out_of_range` Day들의 일정 개수는 `func.count` + `group_by`로 **commit 전에** 한 번에 집계(N+1 회피).
- 응답의 `days`는 동기화 후 전체 Day 목록(범위 밖 Day 포함 — 안 지웠으므로). `POST /api/trips`가
  `TripDetailRead`를 주는 것과 같은 패턴이라 프론트가 PATCH 후 별도 GET을 할 필요가 없다.

**DB 스키마 변경 없음 → Alembic 마이그레이션 불필요.** 프론트 코드도 무변경(별도 위임 대상).

### 검증

FastAPI `TestClient` 스크립트로 8개 시나리오 / **46개 체크 전부 통과**.
`dev.db`를 건드리지 않도록 임시 SQLite 파일 DB로 `get_db`를 오버라이드해서 실행
(`require_session`도 오버라이드). 실행: `venv312\Scripts\python.exe`, cwd = `backend/`.

1. **기간 확장** (10/01~10/03 → 10/01~10/06): Day 6개로 확장, `added_day_ids` 3개, 기존 Day id 전부 보존, `out_of_range` 없음.
2. **기간 축소 + 일정 있는 Day가 범위 밖** (11/01~11/05 → 11/01~11/03, 11/04에 일정 2개):
   Day는 **여전히 5개**(자동 삭제 안 함), `out_of_range` 2개가 날짜순으로 반환,
   11/04의 `item_count == 2` / 11/05의 `item_count == 0`, DB에 일정 2개 그대로 남아있음 확인.
   이어서 2단계 확인 흐름 재현 — `DELETE /api/days/{11/05 id}` → 204, 재조회 시 Day 4개.
3. **시작일 앞당김** (12/10~12/12 → 12/08~12/12): 앞쪽 2일 추가되고 응답 `days`가 날짜순 정렬 유지.
4. **날짜 미변경 PATCH (회귀)**: `{"name": ...}`만 보냈을 때 Day id 목록 완전 동일,
   `added_day_ids`/`out_of_range_days` 모두 빈 배열, 기존 `TripRead` 필드 8개 전부 응답에 존재(하위호환).
   4b) 같은 날짜를 그대로 다시 보내는 **멱등성** 케이스도 추가 0건/범위밖 0건.
5. **기존 검증 회귀**: 날짜 역전 → 422, 90일 초과 → 422, 그리고 **422일 때 Day·기간이 전혀 안 바뀜** 확인.
6. **날짜 한쪽만 / 날짜 지우기**: 한쪽만 있으면 Day 생성 안 함 → 나머지 채우면 그때 3개 생성 →
   `{"start_date": null, "end_date": null}`로 지우면 Day는 유지하고 `out_of_range`도 보고하지 않음.
7. **기간 통째 이동 + 총개수 상한**: 90일 → 다른 90일로 이동 시 200(총 180, 범위밖 90),
   한 번 더 이동하면 422 + "delete out-of-range days" 안내, **롤백되어 Day 180개·기간 그대로** 확인.
8. **수동 생성 Day와 날짜 중복**: 범위 밖에 수동 Day(2/04, `label="수동추가"`)를 만들어두고 기간을 2/05까지 늘렸을 때
   2/04를 재생성하지 않고(총 5개), `added`는 2/03·2/05 두 개, 수동 `label`도 보존.

검증 후 `dev.db` 확인 — 기존 트립 id 1(오사카 여행)·2(안동 여행)와 Day 개수 그대로, 변화 없음.
테스트 스크립트는 임시 폴더에만 두고 저장소에 커밋하지 않았다(이 프로젝트에 아직 테스트 스위트 규약이 없어

### 프론트엔드(ui-dev) 후속 작업 스펙

`PATCH /api/trips/{id}` 응답(`updateTrip()`)이 이제 아래 필드를 추가로 준다. `frontend/src/api/trips.ts`의
`updateTrip` 반환 타입을 `Trip` → 새 타입(예: `TripUpdateResult`)으로 넓히고 `types/models.ts`에 정의할 것.

```ts
// PATCH /api/trips/{id} 응답 = TripDetail + 아래 2개
added_day_ids: number[]
out_of_range_days: Array<{
  id: number; trip_id: number; date: string; label: string | null;
  sort_order: number; item_count: number   // 그 Day에 딸린 일정 수
}>
// days: Day[] — 동기화 후 전체 목록(범위 밖 Day도 포함). 별도 GET 불필요.
```

해야 할 일:
1. **`out_of_range_days.length > 0`이면 확인 모달**을 띄운다. 예:
   "수정한 기간을 벗어나는 날짜가 2개 있습니다: 11/04(일정 2개), 11/05(일정 없음). 삭제할까요?"
   — `item_count > 0`인 항목은 **일정이 함께 삭제된다는 점을 반드시 명시**할 것(되돌릴 수 없음).
2. 사용자가 삭제를 확정하면 각 Day에 대해 **기존 `DELETE /api/days/{id}`**를 호출한다(새 API 없음).
   `api/days.ts`에 삭제 함수가 없으면 기존 `deleteTrip` 패턴대로 추가. 부분 실패는 허용된다
   (Day 삭제는 서로 독립적이고, 실패하면 남아있을 뿐 다음에 다시 지우면 됨) — 다만 실패 시
   `extractErrorMessage()` 패턴으로 사용자에게 알릴 것.
3. 사용자가 "유지"를 고르면 아무것도 안 한다(= 종전 동작). 이 경우 Day 탭/모바일 목록에
   범위 밖 Day가 그대로 보이므로, `trip.start_date`~`end_date`와 `day.date`를 비교해
   **"여행 기간 밖" 배지**를 다는 걸 권장(선택). `lib/dayLabel.ts`의 Day 순번 표시와 어떻게 어울릴지 확인 필요.
4. **`added_day_ids.length > 0`이면 "N일이 추가되었습니다" 안내**(토스트/인라인 텍스트).
5. **삭제/추가 후 `queryClient.invalidateQueries`**로 `['trips']`와 해당 트립의 Day 캐시를 갱신.
   응답에 `days`(동기화 후 전체 목록)가 들어있으므로 목록 갱신에 바로 쓸 수 있다
   (`createTrip` 응답의 `days`를 쓰는 기존 패턴과 동일).
6. **`TripListPage.tsx`의 `TripEditForm` 안내 문구 수정** — 현재 "기간을 바꿔도 이미 만들어진 날짜는
   유지됩니다"인데, 이제 부족한 날짜는 자동 추가되므로 "기간을 늘리면 날짜가 자동으로 추가되고,
   줄어들면 범위 밖 날짜를 지울지 물어봅니다" 취지로 고칠 것.

## M7 Tier 1: QA [보통] 이슈 수정 — Day 중복 생성 레이스 컨디션 차단 (이어서, 같은 날)

담당: senior-dev (오케스트레이터 재위임). 위 QA가 찾은 **[보통] `Day(trip_id, date)` 유니크 제약 부재로
동시 PATCH 시 같은 날짜 Day가 2개 생길 수 있음**을 수정. 설계 근거는 후속 ADR
[`docs/adr/0002-day-unique-constraint-and-conflict-handling.md`](../docs/adr/0002-day-unique-constraint-and-conflict-handling.md).
ADR-0001은 뒤집지 않고(결정 자체는 유효) 상단에 "후속: ADR-0002" 포인터 한 줄만 추가했다(ADR은 append-only).

### 판단 근거 요약 (상세는 ADR-0002)

**동시성이 실제로 가능한지부터 확인했다.** 라우터가 `async def`가 아니라 **`def`**라서 FastAPI/Starlette이
이들을 anyio 워커 스레드풀에서 돌린다 — Render 인스턴스가 1개여도 두 PATCH가 서로 다른 스레드에서
서로 다른 DB 세션으로 동시에 진행된다. "인스턴스 1개니까 직렬"이 아니다. 게다가 유니크 제약이 없어서
**동시성과 무관한 중복 경로**도 열려 있었다 — `POST /api/trips/{trip_id}/days`로 같은 날짜를 한 번 더
추가하면 그냥 중복 Day가 생겼다.

핵심 결정 4가지:
1. **DB 유니크 제약으로 막는다.** 앱 레벨 "커밋 직전 재확인"은 확인~INSERT 사이 창을 좁힐 뿐 못 없앤다.
2. **자동 재시도하지 않고 409를 준다.** 충돌한 상대 요청은 Day만 추가한 게 아니라 **기간 자체를 바꿨을 수
   있어서**, 내 요청을 최신 상태에 다시 얹으면 상대 기간을 last-write-wins로 덮어쓴다. ADR-0001이
   "파괴적/모호한 판단은 사람이"로 정한 것과 같은 기준. 게다가 `IntegrityError` 이후 SQLAlchemy 세션은
   사용 불가 상태라 제대로 재시도하려면 핸들러 전체 재실행이 필요하고, 발생 빈도는 사실상 0이다.
   422가 아니라 409인 이유: 요청은 멀쩡했고 **그 사이 서버 상태가 바뀐 것**이라 409 Conflict의 정의 그대로.
3. **`MAX_TRIP_TOTAL_DAYS`(180) 동시 우회는 락 대신 문서화만.** 유니크 제약을 깔면 우회가 성립하는 건
   두 요청의 추가 날짜가 **완전히 서로소**일 때뿐이고(같은 방향이면 겹쳐서 한쪽이 409),
   그때도 요청당 90일 상한 때문에 **최대 270에서 멈춘 뒤 다음 요청부터 기존 422가 막아 자가 수복**된다.
   이 상한은 보안 경계가 아니라 무료 티어 낭비 방지 가드레일이다. 반면 `SELECT ... FOR UPDATE`는
   **SQLite에서 무시돼** 로컬 검증이 불가능하다 — 검증할 수 없는 락은 문서화된 한계보다 나쁘다고 판단.
4. **에러 `detail`은 영어 유지.** 백엔드 `detail` 18곳이 전부 영어라 여기만 한국어를 섞으면 계약 언어가
   둘이 된다. 한국어 안내는 프론트가 상태 코드로 매핑하는 게 맞고, 기존 422 문구들도 같은 문제라
   Backlog Tier 2에 한 항목으로 정리했다(ui-dev 후속).

### 진행한 작업

**1) `backend/app/models.py`** — `Day.__table_args__`에
`UniqueConstraint("trip_id", "date", name="uq_day_trip_id_date")` 추가.

**2) `backend/alembic/versions/73a697fa5fee_add_unique_constraint_on_day_trip_id_.py` (신규)**
- `alembic revision --autogenerate`로 생성. `alembic/env.py`에 이미 `render_as_batch`(SQLite)가 있어서
  `op.batch_alter_table`로 잘 렌더됐다. Postgres에서는 batch가 그냥 `ALTER TABLE ... ADD CONSTRAINT`로
  나가므로 테이블 재생성이 없다.
- **`upgrade()` 첫머리에 중복 사전 확인 가드를 직접 추가**했다. 중복이 있으면 DB 메시지는
  `"UNIQUE constraint failed"` 수준이라 어느 행이 문제인지 알 수 없으므로, `(trip_id, date, count)`를
  전부 찍고 `RuntimeError`로 중단한다. **자동으로 지우지 않는다** — Day 삭제는 CASCADE로 일정까지
  날리므로 어느 걸 남길지는 사람이 판단할 문제다(ADR-0001의 원칙과 동일).
- SQLite batch가 `day` 테이블을 재생성하는데도 `itinerary_item`이 CASCADE로 안 날아가는 이유
  (`alembic/env.py`가 `app.db.engine`이 아닌 자체 엔진을 써서 `PRAGMA foreign_keys`가 OFF)를 주석으로 남김.

**3) `backend/app/services/trip_days.py`** — `DAY_UNIQUE_CONSTRAINT` 상수와
`is_duplicate_day_error(exc)` 판별 함수 추가. **`IntegrityError`를 무조건 409로 바꾸지 않는다** —
NOT NULL/FK 위반 같은 진짜 버그까지 "다른 사용자와 충돌"로 덮으면 문제가 숨는다. 유니크 위반 메시지가
DB마다 달라(Postgres는 제약 이름 포함, **SQLite는 제약 이름을 아예 안 알려주고** 컬럼만 알려줌)
제약 이름과 `"day.trip_id, day.date"` 둘 다 본다. False면 예외를 그대로 올려보내 500으로 드러낸다.

**4) `backend/app/routers/trips.py`**
- `update_trip`: `db.commit()`을 try/except로 감싸 `IntegrityError` → `db.rollback()` → 409.
  트랜잭션 전체가 롤백되므로 "Day는 안 늘었는데 이름만 바뀐" 부분 반영 상태가 없다.
- `create_trip`: 예외 처리를 **일부러 넣지 않고** 왜 도달 불가능한지 주석으로 남김
  (`trip.id`가 방금 발급된 새 값이라 다른 트랜잭션이 같은 `trip_id`로 Day를 넣을 수 없고,
  `build_days_for_range()`가 만드는 날짜도 서로 중복 없음).

**5) `backend/app/routers/days.py`** — `_commit_day()` 헬퍼로 `create_day`/`update_day`의 커밋을 감싸
같은 방식으로 409(`"this trip already has a day with that date"`) 반환. 유니크 제약 도입으로
**같은 날짜 수동 추가가 201 → 409로 바뀌는 API 계약 변화**가 생긴다(현재 이 API를 부르는 프론트 화면은 없음).

### 이슈/특이사항
- **처음엔 E(스레드) 테스트가 실패했다.** 배리어를 `diff_days_for_range` 안(= `select(Day)` 시
  autoflush로 trip UPDATE가 이미 나간 뒤)에 걸었더니 한쪽이
  `sqlite3.OperationalError: database is locked`로 죽었다. SQLite는 **DB 파일 전체 쓰기 락**이라
  먼저 쓴 쪽이 커밋할 때까지 다른 쪽이 진입 자체를 못 하는데, 배리어가 그 커밋을 막아 교착이 된 것.
  운영 Postgres에는 없는 제약이고 이번 변경과도 무관하므로, 배리어를 **아무도 아직 쓰지 않은 지점**
  (`validate_date_range` 직후)으로 옮겨 정상적인 동시 진입을 재현했다. 대신 **결정적인 409 경로 검증은
  D 시나리오**가 담당한다(스레드 타이밍에 의존하지 않음).
- 프론트 코드는 전혀 건드리지 않았다(스코프 밖).
- `MAX_TRIP_TOTAL_DAYS` 동시 우회는 **의도적으로 수정하지 않고** 알려진 한계로 남겼다
  (`docs/PROJECT.md` Backlog Tier 2 + ADR-0002 "결과 > 감수하는 것").

  직접 만들어 "둘 다 커밋 전 snapshot을 읽는다"를 결정적으로 재현: A 커밋 성공, B 커밋 시
  `sqlite3.IntegrityError: UNIQUE constraint failed: day.trip_id, day.date` 발생,
  `is_duplicate_day_error()` → `True`, 롤백 후 최종 Day는 날짜당 정확히 1개(중복 0건) 확인.
- **`is_duplicate_day_error()`의 오분류 방지** — `PATCH /api/days/{id}`에 `{"date": null}`을 보내
  실제 `NOT NULL constraint failed: day.date` `IntegrityError`를 발생시켰을 때 `is_duplicate_day_error()`가
  `False`를 반환해 예외가 그대로 올라가 500(TestClient 기준 unhandled exception)으로 드러남 — 409로
  잘못 감춰지지 않음을 확인. (참고: `DayUpdate.date`에 `{"title": null}` 명시 거부용 `field_validator`
  같은 게 없어서 이 경로가 422가 아니라 500이 되는 건 이번 기능과 무관한 기존 스키마 설계이고, 별도
  이슈로 다루는 게 맞다고 판단해 이 리포트의 등급에는 포함하지 않음 — 필요하면 백로그로 판단 요망.)
- **`create_trip`에 예외 처리를 안 넣은 근거** — `trip.id`가 `db.flush()`로 방금 발급된 새 auto-increment
  값이라 다른 트랜잭션이 절대 같은 값을 가질 수 없고, `build_days_for_range()`가 만드는 날짜 리스트도
  서로소이므로 구조적으로 유니크 위반이 불가능하다는 설명이 타당함을 확인.
- **기존 정상 흐름 회귀 없음** — 기간 확장/축소(+`out_of_range`/`item_count`), 이름만 변경(Day 안 건드림),
  멱등 PATCH(동일 날짜 재전송 시 추가 0건), 90일 초과 422, 180일 총합 상한(정확히 180 통과/181 거부 +
  롤백) 전부 TestClient로 재현해 통과.
- **마이그레이션 왕복 안전성** — `downgrade -1` → `upgrade head`를 복사본에서 실행, `trip`/`day`/
  `itinerary_item` 행 수와 `itinerary_item.day_id` FK 매핑이 전후 완전히 동일함을 직접 대조.
- **마이그레이션 중복 가드** — 복사본에 `(trip_id=1, date=2026-09-04)` 중복을 수동 주입한 뒤
  `upgrade head` 실행 → `RuntimeError`로 즉시 중단, 스키마 변경 없음(`day` 테이블에 제약 미적용),
  `day` 행 4개 그대로(자동 삭제 없음), `alembic_version`이 이전 리비전에 그대로 머묾 — 전부 확인.
- **`update_trip`의 409 문구는 프론트에서 영어 원문 그대로 노출됨(`TripEditForm`의 `setError`)** —

## M7 Tier 1: 일정 메모/체크리스트 — 설계(ADR-0003) + 백엔드 구현 (이어서, 같은 날)

사용자 확인으로 범위가 확정된 상태에서 착수 — **여행(Trip) 단위**, **자유 텍스트가 아니라 진짜 체크리스트**
(항목 여러 개 + 각 항목 체크박스 + 삭제).

### 설계 결정 (ADR-0003)

새 테이블이 필요한 작업이라 되돌리기 어렵다(스키마 + 마이그레이션 + 운영 Neon 적용). 그래서 컬럼 구성을
[`docs/adr/0003-trip-checklist-model.md`](../docs/adr/0003-trip-checklist-model.md)에 근거와 함께 남겼다.

**1) 왜 `Day`가 아니라 `Trip` 직속인가.** "여권 챙기기"는 여행 전체 준비물이라 특정 날짜에 귀속시킬
대상이 아니다. 게다가 Day에 매달면 기간 PATCH로 그 Day가 범위 밖이 되거나(ADR-0001) 사용자가 범위 밖
Day를 지울 때 CASCADE로 준비물까지 사라진다 — 명백한 오동작이다.

**2) 순서 변경(드래그 정렬)을 이번 스코프에서 뺐다.** 세 후보를 비교했다.

| | (a) 생성 순서 고정 **(채택)** | (b) 위/아래 이동 버튼 | (c) dnd-kit 드래그 |
|---|---|---|---|
| 스키마 | 정렬 컬럼 **불필요** | `position` 필요 | `position` 필요 |
| API | CRUD 4개 | + 재정렬 | + 재정렬 |
| 모바일 제스처 | 문제 없음 | 문제 없음 | **체크박스 탭 ↔ 드래그 경합**(M3에서 겪은 `TouchSensor` 튜닝 비용) |

`ItineraryItem`에 이미 dnd-kit 정렬이 있다는 게 재사용 근거처럼 보이지만, 그 화면은 **하루 동선의
방문 순서**라 순서 자체가 데이터의 의미다. 준비물 목록은 "여권"이 "환전"보다 위에 있어야 할 이유가 없다.
(b)는 중간 타협이라 양쪽 비용만 가져온다. **결정적인 건 되돌리기 비용의 비대칭**이다 — 나중에 정렬이
필요해지면 `position int DEFAULT 0` 마이그레이션 하나 + `ORDER BY position, id`면 되고, **기존 행은
`id` 보조 정렬 덕에 현재 순서가 그대로 유지돼 데이터 백필이 필요 없다.** 반대로 지금 컬럼을 넣어두면
아무도 안 쓰는 값이 계속 유지보수 대상으로 남는다(ADR-0002의 "도달 불가능한 예외 처리는 넣지 않는다"와 같은 기준).

**3) 정렬은 `created_at`이 아니라 `id`.** `datetime.utcnow()`는 이론적으로 동률이 가능해 정렬이
불안정해질 수 있다. `id`는 SQLite rowid / Postgres serial 양쪽에서 삽입 순서 단조 증가 + 유일이 보장된다.

**4) 체크 토글은 전용 엔드포인트가 아니라 일반 PATCH.** `POST /api/checklist/{id}/toggle`은 바디가
없어 짧아 보이지만 **현재 상태를 모른 채 뒤집으므로 멱등하지 않다** — 네트워크 재시도나 더블탭이 그대로
상태 반전 2회가 되고, 두 사람이 같이 쓰는 앱에서 "내가 껐는데 왜 켜져 있지"가 재현 불가능한 형태로
발생한다. `PATCH {"is_checked": true}`는 멱등하고 텍스트 수정과 엔드포인트를 공유한다.

**5) 상한 2개(개수 100 / 텍스트 200자).** `MAX_TRIP_DAYS`(90)는 "연도 오타로 수천 행"이라는 **자동
일괄 생성 사고**를 막는 장치였는데, 체크리스트엔 그런 경로가 없다(항상 사용자가 한 줄씩 만든다).
그래도 두는 이유는 다르다 — 개수는 클라이언트 재시도 루프 버그가 무료 티어 DB를 채우는 걸 막고,
길이는 수 MB짜리 붙여넣기를 막는다. **개수만 있으면 "100개 × 무제한 길이"라 개수 상한이 무의미해지므로
둘은 세트로만 의미가 있다.** 길이 제한은 DB 컬럼 제약이 아니라 pydantic 검증으로만 뒀다(UX 판단에
가까운 값이라 바꿀 때 마이그레이션이 필요하면 안 된다).

**6) Trip 삭제 시 CASCADE는 기존과 완전히 동일**(`ondelete="CASCADE"` + SQLite는 `app/db.py`의 기존
`PRAGMA foreign_keys=ON` 리스너, Postgres는 엔진이 강제). 삭제 규칙에 예외가 늘지 않는다.

기각한 대안(Day 단위/양쪽 지원 nullable FK, `Trip.memo` 단일 텍스트, `position`만 미리 넣기,
체크 완료 항목 자동 하단 이동, 소프트 삭제)은 ADR 참고.

### 진행한 작업 (백엔드)

**1) `backend/app/models.py`** — `ChecklistItem`(`__tablename__ = "checklist_item"`) 추가.
컬럼: `id` / `trip_id`(FK `trip.id`, `ondelete="CASCADE"`, NOT NULL — `Day.trip_id`와 같은 선언 방식) /
`text` / `is_checked`(기본 False) / `created_at`. **`updated_at`은 일부러 넣지 않았다** — 어떤 화면도
읽지 않는데 토글마다 갱신 코드가 붙는다(필요해지면 무손실 컬럼 추가).

### 검증

`dev.db`를 건드리지 않도록 임시 SQLite 파일 DB로 `get_db`/`require_session`을 오버라이드한
`TestClient` 스크립트 — **61개 체크 전부 통과**. 실행: `venv312\Scripts\python.exe`, cwd = `backend/`.
(콘솔이 cp949라 `PYTHONIOENCODING=utf-8`이 필요했음.)

1. **생성/목록/순서**: 빈 목록 200+`[]`, 3건 생성, 응답 필드 구성, 기본 `is_checked=False`, **생성 순서 유지**.
2. **텍스트 검증(생성)**: trim 정규화, 빈 문자열/공백만/명시적 `null`/필드 누락/201자 → 전부 422,
   정확히 200자는 201, **거부된 요청이 저장되지 않음**.
3. **체크 토글**: True/False 왕복, 토글 시 `text` 보존, 텍스트만 수정 시 `is_checked` 보존(체크된 항목
   포함), 둘 동시 수정, 빈 PATCH(`{}`)는 200 + 무변화.
4. **PATCH 검증(회귀 방지)**: `{"text": null}` / 빈 / 공백 / 201자 / **`{"is_checked": null}`** 전부 422,
   거부 후 기존 값 그대로 — **500이 아니라 422로 떨어지는 것까지 확인**.
5. **삭제**: 204, 목록에서 사라짐, 나머지 순서 유지, 이미 지운 항목 재삭제 → 404.
6. **404**: 없는 트립 목록조회/생성, 없는 항목 PATCH/DELETE (detail 문구까지 확인).
7. **인증**: `require_session` 오버라이드를 **해제하고** 4개 엔드포인트 전부 401,
   그리고 **401 요청이 DB를 전혀 바꾸지 않음** 확인.
8. **Trip 삭제 CASCADE**: 체크리스트 + Day + 일정이 있는 트립을 지웠을 때 셋 다 삭제되고(기존 CASCADE 회귀 포함)
   **다른 트립의 체크리스트는 무영향**.
9. **트립 간 격리**: 다른 트립 목록에 남의 항목이 섞이지 않음.
10. **개수 상한**: 100개까지 201, 101번째 422 + 안내 문구 + 미저장, **하나 지우면 다시 추가 가능**.
11. **기존 API 회귀**: `GET /api/trips`, `GET /api/trips/{id}`, `PATCH /api/trips/{id}`
    (`added_day_ids`/`out_of_range_days` 빈 배열 유지) 정상.

**마이그레이션 실기 검증**: 로컬 `dev.db`에 `alembic upgrade head` 적용 → `checklist_item` 테이블 생성
확인(FK `ON DELETE CASCADE` 포함), 기존 행 수 무변화(`trip 2 / day 3 / itinerary_item 3`).
추가로 **`dev.db` 복사본**에서 `downgrade -1` → 테이블 사라지고 기존 데이터 그대로 → `upgrade head` →
테이블 복구, 데이터 그대로 **왕복 확인**(복사본은 삭제). 검증 스크립트는 스크래치패드에만 두고 저장소에
넣지 않았다(이 프로젝트에 아직 테스트 스위트 규약이 없어 `backend/tests/`를 임의로 신설하지 않음 —
이전 세션들과 동일한 판단).

**API 계약** (전부 기존과 동일하게 세션 쿠키 필요, `apiClient` 그대로 사용)

```ts
// types/models.ts 에 추가
export interface ChecklistItem {
  id: number
  trip_id: number
  text: string
  is_checked: boolean
  created_at: string
}

// api/checklist.ts (신규) — api/days.ts 스타일 그대로
GET    /api/trips/{tripId}/checklist   -> ChecklistItem[]   // 생성 순서, 없는 트립이면 404
POST   /api/trips/{tripId}/checklist   -> 201 ChecklistItem // body: { text: string, is_checked?: boolean }
PATCH  /api/checklist/{itemId}         -> 200 ChecklistItem // body: { text?: string } | { is_checked?: boolean } (부분)
DELETE /api/checklist/{itemId}         -> 204
```

에러 응답:
- `422` — 빈/공백 텍스트, 200자 초과, 명시적 `null` 전송, 트립당 100개 초과

- `401` — 세션 없음

  최소한 이 화면에서는 한국어 fallback 문구를 넣을 것(Tier 2의 "409/422 한글 매핑"과 같은 맥락).

     하나로 딱 자르기보다, **별도의 "개수만 미리 조회" API나 로컬 상태 복제를 전혀 추가하지 않고** React
     Query의 기존 캐시 읽기 동작만으로 (a)와 (b)의 장점을 동시에 얻을 수 있어 이 방식을 택했다 — 코드
