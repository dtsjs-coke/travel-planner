오케스트레이터(orchestrator_pjt)가 사용자 요청을 받아 위임. 같은 날 junior-dev가 처리한 백엔드 항목(길이 상한 2건, 위 섹션)과는 독립적이며 `backend/`는 건드리지 않음. 프론트 전용 3건 모두 완료, 백엔드/DB 변경 없음.

### 1) `useTripItems`의 `isError`를 화면에 반영

- **문제**: `hooks/useTripItems.ts`가 `isError`(전체 Day 중 하나라도 실패했는지)를 계산만 하고 어디서도 쓰지 않아, Day의 일정 조회가 실패해도 "일정이 없는 빈 Day"와 "로드 실패"를 구분할 수 없었음.
- **결정**: 단일 집계 `isError`만으로는 "어느 Day가 실패했는지" 알 수 없어 화면에서 Day별로 안내하기 부족하다고 판단, `useTripItems`에 `errorDayIds: number[]`(조회 실패한 Day id 목록)를 신규로 추가(기존 `isError` 필드는 그대로 유지, 하위 호환).
- **배선**: `types/dayEditor.ts`의 `DayEditorViewProps`에 `itemsErrorDayIds: number[]` 추가 → `routes/DayEditorPage.tsx`가 `useTripItems`에서 받아 `viewProps`에 실어 `DayEditorDesktop`/`DayEditorMobile`에 전달 → 각 뷰가 현재 보고 있는 Day(데스크톱: `activeDayId`, 모바일: 반복 중인 `day.id`)가 `itemsErrorDayIds`에 포함되는지 확인해 `ItineraryList`에 신규 `hasError` prop으로 전달.
- **표시 방식**: `components/ItineraryList.tsx`의 빈 목록(`items.length === 0`) 분기에서 `hasError`면 기존 "등록된 일정이 없습니다. 위에서 추가해보세요."(회색) 대신 "일정을 불러오지 못했습니다."(빨간 `text-red-600`)를 표시. 재시도 버튼 등은 넣지 않음(과설계 방지, 요청 스펙대로 상태 구분만).
- **의도적으로 다루지 않은 엣지케이스**: 실패했지만 캐시에 이전 데이터가 남아 `items.length > 0`인 경우는 기존 목록을 그대로 보여줌(별도 배너 없음) — 빈도가 낮고 "빈 상태 vs 로드 실패" 구분이라는 요청 범위를 넘어서는 과설계로 판단.

### 2) ADR 문구 `isPending` vs 코드 `isLoading` 불일치 해소

- `docs/PROJECT.md`의 모바일 연속 스크롤 ADR 요약 문구(`isLoading = results.some(r => r.isPending)`)는 이미 `isPending` 기준으로 적혀있었고, 실제 코드만 `result.isLoading`을 쓰고 있어 어긋나 있었음.
- `hooks/useTripItems.ts`의 `isLoading` 계산을 `results.some((result) => result.isLoading)` → `results.some((result) => result.isPending)`로 수정(반환 필드명 `isLoading`은 ADR 문구·기존 소비자 코드와 동일하게 유지, 내부 판정 기준만 교체). TanStack Query v5에서 `isLoading`은 `isPending && isFetching`의 축약형이라 `fetchStatus: 'paused'`(오프라인 등) 상태에서 `isPending`이 true여도 `isLoading`이 false가 돼 로딩 표시가 조기에 꺼질 수 있는데, `isPending` 기준이 이 문제를 피한다.
- **영향 범위 확인**: 이 훅의 소비자는 `routes/DayEditorPage.tsx`(→ `itemsLoading`으로 `DayEditorDesktop`/`DayEditorMobile`에 전달) 한 곳뿐이라, 단순 개명 수준의 변경이 맞음을 확인. 다른 화면(`TripListPage`/`TripChecklist`/`TripSettlement` 등)은 각자 별도 `useQuery`를 쓰고 이 훅과 무관해 영향 없음.
- `docs/PROJECT.md` 문서 쪽은 이미 `isPending`으로 적혀있어 변경하지 않음(지시대로).

### 3) `useActiveDayOnScroll`의 `registerSection`이 언마운트를 처리하지 않던 문제

- **문제**: `registerSection(el)`이 `el`이 있을 때만 등록하고, React가 언마운트 시 `null`로 호출해도 아무 것도 안 해 `IntersectionObserver` 구독과 내부 `Set<HTMLElement>`가 해제되지 않았음. 지금은 Day 삭제 UI가 없어 도달 불가능하지만 나중에 생기면 메모리 누수.
- **근본 원인 겸 수정**: 기존엔 `ref={registerSection}`로 모든 Day `<section>`이 **같은 함수 참조**를 공유해서, 설령 null 분기를 만들어도 "어떤 Day가 언마운트됐는지" 알 방법이 없었음(ref 콜백은 언마운트 시 이전 엘리먼트를 넘겨주지 않고 `null`만 전달). 그래서 `registerSection`의 시그니처를 `(el: HTMLElement | null) => void` → `(dayId: number, el: HTMLElement | null) => void`로 바꾸고, 내부 추적 자료구조도 `Set<HTMLElement>` → `Map<number, HTMLElement>`(dayId 키)로 교체. `el === null`이면 해당 `dayId`로 저장해둔 엘리먼트를 찾아 `observer.unobserve()` 후 `elementsRef`/`entriesRef` 양쪽에서 제거.
- **호출부 변경**: `components/DayEditorMobile.tsx`의 `<section ref={registerSection}>` → `<section ref={(el) => registerSection(day.id, el)}>`(다른 곳에서 이 훅을 쓰는 컴포넌트 없음, grep으로 확인).
- **회귀 확인**: `IntersectionObserver` 생성/판정 로직(밴드, `boundingClientRect.top` 최솟값 선택, "교차 없으면 이전 활성 Day 유지")은 무변경. 마운트 시 등록 흐름(`el` 있을 때 `observer.observe`)도 동일해 활성 Day 추적/지도 핀 전환 동작은 그대로.
