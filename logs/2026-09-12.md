오케스트레이터(orchestrator_pjt)가 사용자 요청을 받아 위임. 같은 날 junior-dev가 처리한 백엔드 항목(길이 상한 2건, 위 섹션)과는 독립적이며 `backend/`는 건드리지 않음. 프론트 전용 3건 모두 완료, 백엔드/DB 변경 없음.

### 1) `useTripItems`의 `isError`를 화면에 반영

- **문제**: `hooks/useTripItems.ts`가 `isError`(전체 Day 중 하나라도 실패했는지)를 계산만 하고 어디서도 쓰지 않아, Day의 일정 조회가 실패해도 "일정이 없는 빈 Day"와 "로드 실패"를 구분할 수 없었음.
- **결정**: 단일 집계 `isError`만으로는 "어느 Day가 실패했는지" 알 수 없어 화면에서 Day별로 안내하기 부족하다고 판단, `useTripItems`에 `errorDayIds: number[]`(조회 실패한 Day id 목록)를 신규로 추가(기존 `isError` 필드는 그대로 유지, 하위 호환).
- **배선**: `types/dayEditor.ts`의 `DayEditorViewProps`에 `itemsErrorDayIds: number[]` 추가 → `routes/DayEditorPage.tsx`가 `useTripItems`에서 받아 `viewProps`에 실어 `DayEditorDesktop`/`DayEditorMobile`에 전달 → 각 뷰가 현재 보고 있는 Day(데스크톱: `activeDayId`, 모바일: 반복 중인 `day.id`)가 `itemsErrorDayIds`에 포함되는지 확인해 `ItineraryList`에 신규 `hasError` prop으로 전달.
- **표시 방식**: `components/ItineraryList.tsx`의 빈 목록(`items.length === 0`) 분기에서 `hasError`면 기존 "등록된 일정이 없습니다. 위에서 추가해보세요."(회색) 대신 "일정을 불러오지 못했습니다."(빨간 `text-red-600`)를 표시. 재시도 버튼 등은 넣지 않음(과설계 방지, 요청 스펙대로 상태 구분만).
- **의도적으로 다루지 않은 엣지케이스**: 실패했지만 캐시에 이전 데이터가 남아 `items.length > 0`인 경우는 기존 목록을 그대로 보여줌(별도 배너 없음) — 빈도가 낮고 "빈 상태 vs 로드 실패" 구분이라는 요청 범위를 넘어서는 과설계로 판단.

### 2) ADR 문구 `isPending` vs 코드 `isLoading` 불일치 해소

- `docs/PROJECT.md`의 모바일 연속 스크롤 ADR 요약 문구(`isLoading = results.some(r => r.isPending)`)는 이미 `isPending` 기준으로 적혀있었고, 실제 코드만 `result.isLoading`을 쓰고 있어 어긋나 있었음.
- `hooks/useTripItems.ts`의 `isLoading` 계산을 `results.some((result) => result.isLoading)` → `results.some((result) => result.isPending)`로 수정(반환 필드명 `isLoading`은 ADR 문구·기존 소비자 코드와 동일하게 유지, 내부 판정 기준만 교체). TanStack Query v5에서 `isLoading`은 `isPending && isFetching`의 축약형이라 `fetchStatus: 'paused'`(오프라인 등) 상태에서 `isPending`이 true여도 `isLoading`이 false가 돼 로딩 표시가 조기에 꺼질 수 있는데, `isPending` 기준이 이 문제를 피한다.
- **영향 범위 확인**: 이 훅의 소비자는 `routes/DayEditorPage.tsx`(→ `itemsLoading`으로 `DayEditorDesktop`/`DayEditorMobile`에 전달) 한 곳뿐이라, 단순 개명 수준의 변경이 맞음을 확인. 다른 화면(`TripListPage`/`TripChecklist`/`TripSettlement` 등)은 각자 별도 `useQuery`를 쓰고 이 훅과 무관해 영향 없음.
- `docs/PROJECT.md` 문서 쪽은 이미 `isPending`으로 적혀있어 변경하지 않음(지시대로).

### 3) `useActiveDayOnScroll`의 `registerSection`이 언마운트를 처리하지 않던 문제

- **문제**: `registerSection(el)`이 `el`이 있을 때만 등록하고, React가 언마운트 시 `null`로 호출해도 아무 것도 안 해 `IntersectionObserver` 구독과 내부 `Set<HTMLElement>`가 해제되지 않았음. 지금은 Day 삭제 UI가 없어 도달 불가능하지만 나중에 생기면 메모리 누수.
- **근본 원인 겸 수정**: 기존엔 `ref={registerSection}`로 모든 Day `<section>`이 **같은 함수 참조**를 공유해서, 설령 null 분기를 만들어도 "어떤 Day가 언마운트됐는지" 알 방법이 없었음(ref 콜백은 언마운트 시 이전 엘리먼트를 넘겨주지 않고 `null`만 전달). 그래서 `registerSection`의 시그니처를 `(el: HTMLElement | null) => void` → `(dayId: number, el: HTMLElement | null) => void`로 바꾸고, 내부 추적 자료구조도 `Set<HTMLElement>` → `Map<number, HTMLElement>`(dayId 키)로 교체. `el === null`이면 해당 `dayId`로 저장해둔 엘리먼트를 찾아 `observer.unobserve()` 후 `elementsRef`/`entriesRef` 양쪽에서 제거.
- **호출부 변경**: `components/DayEditorMobile.tsx`의 `<section ref={registerSection}>` → `<section ref={(el) => registerSection(day.id, el)}>`(다른 곳에서 이 훅을 쓰는 컴포넌트 없음, grep으로 확인).
- **회귀 확인**: `IntersectionObserver` 생성/판정 로직(밴드, `boundingClientRect.top` 최솟값 선택, "교차 없으면 이전 활성 Day 유지")은 무변경. 마운트 시 등록 흐름(`el` 있을 때 `observer.observe`)도 동일해 활성 Day 추적/지도 핀 전환 동작은 그대로.

## 작업: 409/422 에러 문구 한국어 매핑 (ui-dev, 오케스트레이터 위임)

오케스트레이터(orchestrator_pjt)가 사용자 요청을 받아 위임. ADR-0002 "왜 에러 문구를 영어로
두는가"가 이미 지정해둔 후속 작업(상태 코드/문구 → 한국어 안내 매핑은 프론트 담당)을 처리.
백엔드 `detail`/pydantic validator 문구는 건드리지 않음(API 계약 언어는 영어로 유지, 백엔드
파일 무변경).

### 1) 전수 조사

`backend/app/routers/`, `backend/app/schemas.py`, `backend/app/services/`를 `HTTPException(detail=...)`와
`raise ValueError(...)` 기준으로 grep해 새로 목록을 뽑음. 2026-09-09 ADR-0002 작성 시점의 "18곳"보다
늘어나 있었다 — 체크리스트/정산/마스터 설정/ICS 내보내기/일정 이동 등 그 사이 추가된 기능들이
각자 검증 문구를 갖고 있었음.

- **정적 문구(동적 값 없음, 17종)**: `Invalid passcode`, `Not authenticated`(auth.py/deps.py 2곳),
  `Trip not found`(trips.py/days.py/checklist.py/settlement.py/export.py 5곳), `Day not found`(days.py/items.py),
  `Item not found`, `Checklist item not found`, `end_date must be on or after start_date`,
  `this trip already has a day with that date`(409, ADR-0002),
  `another request just changed this trip's days; refresh and try again`(409, ADR-0002),
  `target day must belong to the same trip as the item`, `ordered_item_ids must match exactly the items in this day`,
  `name must not be null`, `title must not be empty`, `text must not be empty`, `is_checked must not be null`,
  `cost_amount must be a finite number`, `cost_amount must not be negative`,
  `participant names must be different from each other`, `GOOGLE_PLACES_SERVER_KEY is not configured`.
- **동적 문구(상한값/필드명/원문이 메시지에 섞임, 8종)**:

### 2) 매핑 설계 — `frontend/src/lib/errorMessages.ts`(신규 파일)

- 기존 `errors.ts`를 직접 비대하게 만들지 않고 매핑 테이블만 담은 신규 모듈로 분리.
- **정적 문구**: `EXACT_MESSAGES: Record<string, string>`로 문자 그대로 일치 매칭.
- **동적 문구**: `DYNAMIC_MESSAGE_RULES: Array<{ pattern: RegExp; translate: (match) => string }>`로
  정규식 매칭 후 캡처한 숫자/값만 한국어 문장에 그대로 끼워 넣는다(상한값이 나중에 바뀌어도
  이 파일을 다시 고칠 필요가 없게). `{name|title|text} must be at most N characters`는 필드명이
  같은 템플릿을 공유하므로 정규식 하나(`^(name|title|text) must be at most (\d+) characters$`)로
  통합하고 필드별 한글 라벨만 내부 맵으로 분기.
- **pydantic 배열 형태 처리**: 422 검증 에러의 `detail`이 `[{"msg": "Value error, <메시지>", ...}]`
  형태로 오고 `msg`가 `"Value error, "` 접두사를 달고 온다는 사실(이전 세션 QA에서 이미 확인됨)을
  실제 로컬 백엔드 응답으로 재확인 후, `translateErrorDetail()` 내부에서 매칭 전에 이 접두사를
  벗겨내는 `stripValueErrorPrefix()`를 항상 먼저 적용(HTTPException의 단순 문자열 `detail`에는
  이 접두사가 없으므로 그대로 통과해도 무해).
- **구글 Places 연동 실패 문구**는 응답 본문(`response.text`)이 임의의 텍스트라 정확히 매칭할 수
  없어 접두사 정규식(`^Google Places? (search|details) failed:`)으로만 판별해 일반화된 안내로
  치환. 참고로 현재 `AddItemModal.tsx`의 장소 검색 실패 경로는 이 함수를 안 타고 자체 하드코딩
  문구("검색 실패. 잠시 후 다시 시도해주세요.")를 이미 쓰고 있어 당장 영향은 없지만, 나중에 이
  경로가 `extractErrorMessage()`로 통합되더라도 안전하게 동작하도록 방어적으로 넣어둠.
- **매핑 없는 문구는 `null` 반환** → 호출자가 폴백. "매핑 누락 = 에러 안 보임"을 원천 차단.

### 3) `extractErrorMessage()` 수정 (`frontend/src/lib/errors.ts`)

기존 로직(axios 에러에서 `detail` 배열/문자열을 뽑는 부분)은 그대로 두고, 뽑아낸 원문을
`translateErrorDetail()`에 먼저 넣어보고 `null`이면 **원문 그대로**(호출부가 넘긴 fallback이
아니라 기존과 동일하게 백엔드 원문) 반환하도록만 바꿨다 — 요청 지시("매핑에 없으면 기존 동작
그대로")를 그대로 지키기 위해 미매칭 시 caller의 `fallback` 인자로 바꿔치기하지 않음(원래도
문자열 `detail`이 있으면 fallback을 쓰지 않고 원문을 그대로 보여주는 게 기존 동작이었음).
함수 시그니처/호출 규약은 무변경이라 `extractErrorMessage(err, fallback)`을 쓰는 6개 파일,
12개 호출부(`TripListPage.tsx`, `DayEditorPage.tsx`(3곳), `AddItemModal.tsx`,
`AppSettingsModal.tsx`, `TripChecklist.tsx`(3곳), `OutOfRangeDaysModal.tsx`) 전부 코드 변경 없이
한글화된 메시지를 받게 됨. `ItineraryItemCard.tsx`는 이 함수를 직접 부르지 않고 `DayEditorPage.tsx`가
넘겨주는 `onUpdateItem(..., onError)` 콜백을 통해 간접적으로 같은 함수를 거치므로 마찬가지로 자동 반영.

## QA 검증: 409/422 에러 문구 한국어 매핑 (qa-reviewer)

오케스트레이터(orchestrator_pjt) 위임으로 바로 위 "409/422 에러 문구 한국어 매핑" 섹션(ui-dev)의
산출물을 재검증. ui-dev 자체 검증을 신뢰하지 않고 `backend/app/routers/`, `backend/app/schemas.py`,
`backend/app/services/`를 새로 grep해 재대조, 별도 임시 sqlite DB로 백엔드를 새로 기동해 5개 신규
시나리오를 curl로 재현, Node로 `translateErrorDetail()`/`extractErrorMessage()`를 직접 호출해 정상/
방어 경로를 폭넓게 테스트.

### 1) 전수 조사 재확인
`HTTPException(detail=...)`/`raise ValueError(...)`를 라우터 전체(`trips.py`, `days.py`, `items.py`,
`checklist.py`, `settlement.py`, `export.py`, `app_settings.py`, `auth.py`, `deps.py`) + `schemas.py` +
`services/`(`trip_days.py`, `google_places.py`, `app_settings.py`)에서 새로 뽑아 `EXACT_MESSAGES`(19개
정적 문구)/`DYNAMIC_MESSAGE_RULES`(8개 정규식, `google_places`의 search/details 2종과 name·title·text
3종 템플릿이 각각 정규식 하나로 묶여 있음)와 전부 대조 — **커버리지 자체는 누락 없음**. 다만 ui-dev
로그의 "정적 17 + 동적 8 = 25종" 집계는 실제로 세어보면 정적 문구가 19개라 총합이 25가 아니다(집계
방식 차이로 보이며, 코드 커버리지에는 영향 없음 — 아래 "사소" 항목 참고).

### 2) 동적 매핑 정확성
8개 정규식을 백엔드 f-string 원문과 한 줄씩 대조 — 전부 정확히 일치(`^...$`로 양끝 앵커링돼 있어
느슨한 매칭 없음). 필드명 템플릿(`^(name|title|text) must be at most (\d+) characters$`)이 "participant
name for 'x' must be at most N characters"(참가자 이름 템플릿)와 우연히 겹칠 가능성을 특히 확인했으나,
후자는 "participant"로 시작해 앵커링된 전자 패턴과 매칭되지 않음을 확인. 구글 Places 정규식만 접두사
매칭(`$` 없음)인데, 이는 응답 본문이 임의 문자열이라 의도된 설계임(문서화돼 있음).

### 3) pydantic 배열 형식 처리
`stripValueErrorPrefix()`가 `"Value error, "` 접두사가 있으면 벗기고 없으면 그대로 통과하는 방식이라,
- pydantic 모델 검증 경로(예: `TripCreate`의 `model_validator`, `AppSettingsUpdate`의 `field_validator`)는
  배열 + 접두사 있는 `msg`로 오고,
- 반면 `update_trip`(PATCH `/api/trips/{id}`)처럼 라우터가 `try/except ValueError as exc: raise
  HTTPException(422, detail=str(exc))`로 **직접 감싸는 경로**는 접두사 없는 단순 문자열로 온다
  (실제로 `end_date must be on or after start_date`를 이 경로로 재현해 `{"detail":"end_date must be on
  or after start_date"}`를 확인) —
둘 다 동일하게 정확히 매칭됨을 확인. 접두사 없는 일반 pydantic 타입 에러(예: 필드 누락 `"Field
required"`, 타입 불일치)는 매핑 대상이 아니고 `EXACT_MESSAGES`/`DYNAMIC_MESSAGE_RULES` 어디에도 걸리지
않아 `null`을 반환하고 원문 그대로 폴백됨을 Node 직접 호출로 확인(의도대로 동작).

### 4) 폴백 안전성 (Node로 `translateErrorDetail`/`extractErrorMessage` 직접 호출, 총 17+12개 케이스)
- 매핑에 없는 임의 문자열, 빈 문자열, 접두사만 있는 문자열, 대소문자/부분 문자열이 다른 유사 문구 →
  전부 `null` 반환(느슨한 오매칭 없음).
- `detail`이 없음(500 등), `null`, 객체, 배열인데 `msg`가 없거나 빈 배열, `response`가 아예 없는 네트워크
  에러, axios 에러가 아닌 일반 `Error`/`undefined`/문자열이 그대로 throw된 경우, `data`가 HTML 문자열인
  경우 — 모두 예외 없이 `fallback` 인자로 안전하게 폴백함을 실제 호출로 확인. 크래시 없음.

### 5) 회귀 (호출부 6개 파일)
`git diff --stat` 결과 이번 변경은 `frontend/src/lib/errors.ts`(수정)+`frontend/src/lib/errorMessages.ts`
(신규)뿐이고, `TripListPage.tsx`/`DayEditorPage.tsx`/`AddItemModal.tsx`/`AppSettingsModal.tsx`/
`TripChecklist.tsx`/`OutOfRangeDaysModal.tsx` 6개 호출부는 diff에 전혀 나타나지 않음 — 호출부 무변경

### 6) 실제 재현 (임시 포트 8124 + 임시 sqlite DB, `backend/dev.db`는 건드리지 않음)
ui-dev가 이미 확인한 9개 시나리오 외에 **신규 5개**를 재현, 전부 기대한 raw `detail`이 나오고
`translateErrorDetail()`이 올바른 한국어 문구로 변환함을 확인:
- `PATCH /api/trips/{id}`에 날짜 역전(422, 접두사 없는 경로) → `"end_date must be on or after start_date"`
  → "종료일은 시작일과 같거나 이후여야 합니다."
- 참가자 두 이름을 같게 PATCH(422) → `"participant names must be different from each other"`
  → "두 참가자의 이름은 서로 달라야 합니다."
- 알 수 없는 참가자 키(422, 배열+접두사) → `"...unknown participant key 'participant_9' (allowed: ...)"`
  → "알 수 없는 참가자입니다. 새로고침 후 다시 시도해주세요."
- 참가자 이름 공백만(422) → `"...participant name for 'participant_1' must not be empty"`
  → "참가자 이름을 입력해주세요."
- 체크리스트 텍스트 201자(422) → `"...text must be at most 200 characters"`
  → "내용은(는) 최대 200자까지 입력할 수 있습니다."
- (덤) 존재하지 않는 Day로 일정 이동(404) → `"Day not found"` → "날짜(Day)를 찾을 수 없습니다."

테스트 후 임시 트립은 DELETE로 정리했고, 임시 sqlite 파일/쿠키/로그는 전부 스크래치패드에서 삭제.
`backend/dev.db`는 이번 세션에서 전혀 열지 않음(별도 `DATABASE_URL` 오버라이드로 완전히 격리).
