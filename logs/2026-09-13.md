### 사용자와 사전 확정된 전제 (재논의 없이 구현)
1. 입력은 자유 프롬프트가 아니라 **구조화된 조건**(프롬프트는 서버가 조립).
2. 동선 최적화는 서버 담당(LLM에게는 "그날 갈 곳 후보"만 받는다).
3. 숙소는 LLM이 구체적 이름 제안 → Places 존재 검증 → 없으면 Nearby Search(lodging, 인기도순) 폴백.
4. 일반 장소도 동일하게 Places 검증(환각 방지).
5. 최대 3개 안을 전부 자동으로 각각 Trip 등록(미리보기/선택 UI 없음 — 기존 삭제로 정리).
6. 제목은 `(추천일정{N}) {국가}, {도시} 외 {M}곳`.
7. LLM은 Gemini Flash 계열. **API 키 미발급 상태** → 키 없이도 나머지가 정상 동작해야 하고 목 검증 가능해야 한다.

### 이번에 판단해서 내린 결정 (전부 [ADR-0009](../docs/adr/0009-ai-trip-suggestion.md)에 기록)
- **API 계약**: `POST /api/ai/trip-suggestions`, **동기 처리**, 201. 비동기 잡+폴링을 기각한 이유는
  Render 무료 티어에서 백그라운드 작업이 신뢰할 수 없고(인스턴스 1개 + 유휴 슬립 → 잡이 `running`으로
  영원히 남는 경로), 새 테이블/마이그레이션과 폴링 UI가 필요한 반면, **요청당 75초 시간 예산 +
  안별 병렬 호출 + 부분 성공 허용**으로 충분하다는 것. 타임아웃이 실제 문제가 되면 **먼저 기간/안 개수
  상한을 낮추고**, 그래도 안 되면 잡 큐를 새 ADR로 도입한다.
- **비용 안전장치**: AI 전용 상한을 기존보다 **낮게 따로** 뒀다 — 기간 **14일**(`MAX_TRIP_DAYS` 90 대신),
  도시 3곳, 국가 2개, 안 3개, 하루 6곳, 요청당 Places 조회 300회 서킷브레이커. 근거는 비용이
  `일수 × 하루장소 × 안개수`로 **곱해진다**는 것(90일 허용 시 클릭 한 번 = 1,620회 유료 호출).
  추가로 **3개 안이 검증 캐시를 공유**해 실제 호출을 줄인다(같은 도시의 같은 명소를 3번 조회하지 않음).
- **LLM 응답 검증/재시도**: 구조화 출력(`responseMimeType` + `responseSchema`)으로 받고 pydantic으로
  **한 번 더** 검증. Gemini 스키마는 pydantic 자동 생성이 아니라 손으로 썼다(responseSchema가
  OpenAPI 3.0 부분집합이라 `$defs`/`anyOf`를 거부) — 두 벌이 어긋나도 pydantic이 반드시 잡는다.
  **재시도 1회**(타임아웃/429/5xx/빈 응답/파싱 실패/스키마 불일치에만, 400·403은 재시도 안 함),
  재시도 프롬프트에 교정 문구를 덧붙인다. **일수 불일치는 실패가 아니다** — 많으면 잘라내고
  적으면 빈 Day로 채우고 경고.
- **이동일 표현**: `arrival`(그날 맨 앞) / `departure`(맨 뒤) 두 kind로 통합. 이 규칙 하나로
  "첫 시작·최종 종점은 공항", "도시 간 이동일", "국내 여행에서 공항이 안 맞는 경우"(→ KTX역/터미널을
  같은 자리에 넣게 지시)가 동시에 처리된다. **"이동"을 좌표 없는 별도 항목으로 넣는 안은 기각**
  (`ItineraryItem`은 좌표 있는 장소를 전제로 만들어져 있다 — 지도 핀/드래그/ICS의 LOCATION·GEO).
- **연속성**: 동선은 최근접 이웃이며 **전날 마지막 지점(=보통 전날 숙소)이 다음 날의 시작 앵커**.
- **검증 실패 처리**: 해당 항목을 **버리고 개수만 보고**(`dropped_place_count` + 경고). 좌표 없는
  "이름만 있는 항목"은 지도/동선/ICS에서 쓸 수 없으면서 실제 데이터와 구분되지 않는다
  (ADR-0006/0008의 "없는 값을 지어내지 않는다"와 같은 기준). **숙소만 예외로 폴백**.
- **환각 판정은 이름 유사도가 아니라 거리**: Text Search는 거의 항상 무언가를 돌려주므로 실제 위험은
  "없는 이름"이 아니라 **동명 이소**(서울 N타워가 광주 일정에 섞이는 종류)다. 도시 앵커 좌표를
  1회 조회해 `locationBias`로도 쓰고, `selected_only` 60km / `include_nearby` 180km로 판정한다.
  앵커를 못 구하면 판정을 포기하고 통과시킨다(근거 없이 버리지 않음 + 경고).
- **의존성**: `google-genai` SDK 미도입, 기존 `httpx`로 REST 직접 호출(ADR-0008의 `icalendar` 기각과
  같은 판단). 키는 `x-goog-api-key` **헤더**로 전송(URL은 로그에 남는다).
- **스키마 변경 없음**: `source`는 기존 `"google_places"`(이름/주소/좌표가 전부 Places 값이라 사실에
  맞고, 새 값을 만들면 프론트 `ItemSource` 유니온과 분기를 함께 고쳐야 한다), `Day.label`은 비워
  자동 라벨링("Day1 10/1(수)")을 살린다, `Trip.currency`는 건드리지 않는다.

### 실호출 검증 (위임 시점 정보와 달랐던 부분 — 중요)

작업 중 **`backend/.env`에 이미 `GEMINI_API_KEY`가 들어있는 것을 발견**했다(위임문에는 "미발급"으로
적혀 있었다). 키가 유효했으므로 목 검증에 더해 **실제 API로 최소 호출 검증**을 했고, 그 결과가
기본값 두 개와 Places 호출 하나를 바꿨다. 셋 다 코드를 읽어서는 알 수 없고 호출해야만 드러나는
종류라 여기에 남긴다.

1. **`gemini-2.5-flash`는 쓸 수 없다** — `404 "This model models/gemini-2.5-flash is no longer
   available to new users. Please update your code to use models/gemini-3.6-flash"`.
   → 기본 모델을 **`gemini-3.6-flash`**로 확정(모델명을 env로 뺀 결정이 첫날부터 값을 했다).
2. **`thinkingConfig.thinkingBudget: 0`은 400 INVALID_ARGUMENT**, `512`는 정상.
   → 기본값을 **`-1`(필드 생략 = 모델 기본값)**으로 확정.
3. **`languageCode` 없이는 한국 장소가 영어 이름으로 온다** — `펭귄마을`→"Penguin Village",
   `국립아시아문화전당`→"National Asian Culture Center", `홀리데이 인 광주`→"Holiday Inn Gwangju,
   Korea". 기존 검색 화면에서는 한 번 보고 버리는 값이라 티가 안 났지만 **AI 추천은 이 이름을 일정
   제목으로 DB에 저장**한다. → `search_places()`/`search_nearby()`에 `language_code` 키워드 인자를
   추가(기본값 None = 기존 동작 무변경)하고 AI 경로만 `"ko"`를 넘긴다. 재호출로 한국어 이름/주소
   확인 완료.
4. **전체 파이프라인 실동작 확인** (임시 SQLite, 실 Gemini + 실 Places, 광주 2일/1안):
   **14.0초**에 201, 항목 9개 전부 실존 장소(`place_id`/좌표/한국어 주소), `dropped_place_count: 0`,
   `warnings: []`.
   - 1일차: `arrival` 광주송정 → `meal` 형제송정떡갈비 본점 → `activity` 펭귄마을 →
     `activity` 국립아시아문화전당 → `lodging` 홀리데이 인 광주
   - 2일차: 전날 호텔에서 가까운 순으로 정렬 → 마지막이 `departure` 광주송정
   - 즉 **고정 위치 규칙과 "전날 숙소 = 다음날 시작 앵커"가 실제 데이터에서 의도대로 동작한다.**
   - 실행 전후 `dev.db` mtime 동일(무오염).

**여전히 미측정**: 14일 × 3안(최대 부하)의 실제 소요 시간. 1안 2일이 14초였으므로 단순 비례는
아니어도 상당히 길어진다. 끊기면 1차 대응은 **기간/안 개수 상한을 더 낮추는 것**이다.

### ui-dev 후속 스펙 (프론트 미착수)

**API 계약**
```jsonc

{

  "pace": "normal",                     // "relaxed" | "normal" | "packed"
  "themes": ["food", "heritage"],       // "food"|"heritage"|"landmark"|"cafe" (다중, 빈 배열 허용)
  "extra_notes": "아이와 함께 갑니다",    // 선택, 200자 이내 (생략/null 가능)
  "plan_count": 3                       // 1~3
}
→ 201 {"created_trips": [{"id": 12, "name": "(추천일정1) 대한민국, 광주 외 1곳",
                          "start_date": "2026-10-01", "end_date": "2026-10-03",
                          "day_count": 3, "item_count": 13}],
       "requested_plan_count": 3, "failed_plan_count": 0,
       "dropped_place_count": 2, "warnings": ["실제 장소를 확인하지 못한 2곳은 ..."]}
→ 422 조건 위반 / 401 미인증 / 503 키 미설정 / 502 모든 안 실패
```

**UI 요구사항**
- **진입점**: 여행 목록 화면(`TripListPage.tsx`)의 **플로팅 버튼**(우하단 고정, `fixed bottom-4 right-4`
  계열). 모바일에서 하단 고정 요소와 겹치지 않게 배치할 것 — `DayEditorPage`의 모바일 에러 배너가
  `fixed inset-x-4 bottom-4`를 쓰고 있으니 같은 자리를 피하거나 화면이 달라 충돌하지 않음을 확인.
  기존 "+ 여행일정 추가" 접기/펼치기 폼과 역할이 다르므로 그 폼에 탭으로 섞지 말고 별도 진입점으로 둘 것.
- **폼 필드**(모달 또는 전체화면 시트 권장 — 필드가 많아 인라인 펼치기는 목록을 밀어낸다):
  ① 국가+도시: 기본은 국가 1개 + 도시 입력(칩 추가 방식, 최대 3), "여러 나라" 토글을 켜면 두 번째
  국가 블록 추가(총 국가 2, 도시 총합 3 유지). ② 기간: 시작/종료 date input(기존 생성 폼과 같은 패턴,
  **최대 14일**을 제출 전에 클라이언트에서 막아 불필요한 422 왕복 방지 — 기존 체크리스트 200자
  선차단과 같은 정책). ③ 지역 제한: 라디오 2개("선택한 도시만" / "주변 도시 포함").
  ④ 여행 밀도: 라디오 3개(느긋/적당/빡빡 — 단일 선택). ⑤ 여행 스타일: 체크박스 4개(맛집탐방/
  유적지탐방/명소탐방/카페탐방 — 다중). ⑥ 추가 요청: textarea 1개, 200자 카운터.
  ⑦ 안 개수: 1~3(기본 3). **한국어 라벨 ↔ 서버 값 매핑은 프론트에 둔다**(서버는 영문 enum).
- **대기 처리(중요)**: 이 요청은 **수 초~1분 이상** 걸린다(LLM 3회 + Places 수십~수백 회). 반드시
  ① 버튼 비활성 + 스피너, ② "AI가 일정을 만들고 있습니다. 최대 1분 정도 걸릴 수 있어요" 안내,
  ③ **중복 클릭 차단**(멱등하지 않다 — 다시 누르면 또 3개가 생긴다), ④ axios 타임아웃이 기본값으로
  잘리지 않는지 확인(필요하면 이 호출만 `timeout: 120000`). Render 콜드 스타트가 겹치면 더 걸린다.
- **결과 처리**: 성공 시 ① 모달 닫기, ② `queryClient.invalidateQueries(['trips'])`로 목록 갱신
  (응답의 `created_trips`를 캐시에 직접 넣지 말 것 — 목록은 `TripRead` 전체 필드를 쓴다),
  ③ 목록 상단에 "여행 3건이 추가되었습니다" 인라인 안내(기존 "N일이 추가되었습니다" 패턴 재사용).
  `warnings`가 있으면 그 문구들을 함께(작은 회색 텍스트) 보여줄 것 — 서버가 이미 **한국어 문장**으로
  준다. `failed_plan_count > 0`이면 "3개 중 2개만 만들어졌습니다"를 함께 안내.
- **에러 처리**: 기존 `extractErrorMessage()` 사용. 단 이 엔드포인트의 `detail`은 영어이므로
  `lib/errorMessages.ts`에 매핑 추가가 필요하다:
  `"GEMINI_API_KEY is not configured"` → "AI 추천 기능이 아직 설정되지 않았습니다(관리자 확인 필요)",
  `"AI suggestion failed for all plans"` → "AI 추천 생성에 실패했습니다. 잠시 후 다시 시도해 주세요",
  그리고 422 동적 문구 `"ai suggestion cannot span more than 14 days"` /
  `"at most 3 cities are allowed in total"` / `"at most 2 countries are allowed"` /
  `"plan_count must be between 1 and 3"` /
  `"extra_notes must be at most 200 characters"`(기존 `DYNAMIC_MESSAGE_RULES` 정규식 패턴 활용).
- **생성된 여행 자체는 기존 화면이 그대로 처리한다** — 별도 화면/배지 없음. 일정 항목에
  `place_id`/좌표/주소가 모두 채워져 있어 지도 핀, 드래그 정렬, 다른 Day로 이동, ICS 내보내기가
  기존대로 동작한다. 마음에 안 드는 안은 **기존 삭제 버튼**으로 지운다(이 설계의 전제).

## AI 여행 추천 기능 — QA 검증 (qa-reviewer)

담당: qa-reviewer (오케스트레이터 위임). ADR-0009, 위 senior-dev/ui-dev 섹션을 정독 후 검증.
**비용이 실제로 발생하는 외부 API(Gemini/Places)는 이번 QA에서 한 번도 호출하지 않았다** —
`.env`의 `DATABASE_URL`이 `dev.db`가 아니라 실제(Neon 추정) DB를 가리키고 있어, 실호출 시 운영
데이터가 오염될 위험이 있다고 판단해 생략. senior-dev가 이미 같은 세션에서 실호출 1건(광주 2일/1안,
14초, 9개 항목 전부 실존)을 검증했고, 이번 목 기반 검증이 그 파이프라인과 동일한 코드 경로를
합성 좌표로 정밀 재현하므로 추가 실호출의 필요성이 낮다고 판단.

### 검증 방법
저장소에 지속되는 테스트 파일이 없어(이 프로젝트 관행 — 휘발성 검증 스크립트) senior-dev의
"114개 체크"를 그대로 재현할 수 없었고, 독립적으로 새 검증 스크립트(97개 체크)를 작성해
`venv312\Scripts\python.exe`로 실행(임시 SQLite, `dev.db` 무접촉). 60/180km 환각 판정 경계는
haversine 역산으로 정확한 경계 좌표를 만들어 재현, 동선 재정렬은 별도로 다시 짠
haversine+brute-force로 교차검증.

### 결과: 백엔드 이슈 없음. 프론트 [보통] 1건.

**백엔드**: 비용 상한 4종(기간/도시/국가/안개수) 경계+초과, 60/180km 거리 판정, 동선 재정렬
(arrival 고정 시작·전날 숙소가 다음날 시작 앵커), 부분 실패(3안 중 1안 실패 시 201+2건 생성+
`failed_plan_count=1`), 재시도(429/5xx/timeout/빈응답/파싱실패=재시도, 400/403=미재시도),
일수 불일치(부족 시 패딩+경고, 초과 시 자름), 숙소 폴백, 하루 6곳 상한, 같은 날 중복 제거,
401 — 전부 ADR-0009 설계대로 동작. **버그 없음.**

**TripListPage에서 실제로 렌더되는 오버레이 스태킹 순서**(코드 확인, `frontend/src/components/`
전체에서 `z-\d+` 검색으로 교차확인):
- `OutOfRangeDaysModal` — z-20 (가장 낮음)
- `AppSettingsModal` — z-30
- `AiSuggestionModal` — z-40 (가장 높음)
- (참고) `MoveItemControl`(z-10/20/30)과 `AddItemModal`(z-10)은 `DayEditorPage` 전용이라
  이 페이지에서는 동시에 렌더되지 않음 — 이번 수정 범위 밖.

**원인**: 플로팅 "AI 추천" 버튼이 `z-20`이라 가장 낮은 모달인 `OutOfRangeDaysModal`(z-20)과
**동일한 스태킹 레벨**이었다. JSX 트리에서 버튼이 모달보다 뒤에 위치해 같은 레벨에서는 나중
렌더링된 쪽이 위로 오므로, 모달이 열려 있어도 버튼이 반투명 배경 위로 노출·클릭 가능했다.

**수정**: 버튼을 페이지에서 뜨는 모든 모달보다 낮은 `z-10`으로 내렸다(모달 쪽 z-index는 상대
순서를 포함해 전혀 건드리지 않음 — QA 제안 두 가지 중 "버튼을 낮추는 쪽"을 채택, 위임 지시대로).
코드 리뷰로 조합을 확인: 수정 폼 → `OutOfRangeDaysModal`(z-20) 열림 시 버튼(z-10)이 항상 아래,
`AppSettingsModal`(z-30)·`AiSuggestionModal`(z-40) 열림 시에도 마찬가지 — 이 페이지에서 발생
가능한 모든 모달 조합에서 버튼이 항상 최하단.
